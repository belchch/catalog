# Skill: Plane → Todo Loop (Claude)

Автономно обрабатывает задачи проекта **CATALOG** из Plane: каждую задачу в статусе **Todo** переводит в **In Progress** и создаёт для неё заполненный файл плана выполнения (на основе анализа кода). Цикл повторяется, пока есть задачи в Todo и не превышен лимит итераций. После цикла планы переименовываются с префиксом очереди `NN-` по зависимостям Plane.

## Инструменты

Доступ к Plane — двумя путями, использовать по назначению:

- **MCP `plane`** (`mcp__plane__*`): `list_states`, `update_issue`, `get_issue_comments`, `get_issue_using_readable_identifier`. Если тулы не загружены — загрузить через ToolSearch (`select:mcp__plane__list_states,mcp__plane__update_issue,mcp__plane__get_issue_comments`).
- **REST через curl** — для того, чего в MCP-сервере (@makeplane/plane-mcp-server 0.1.5) нет или что он отдаёт неподъёмно:
  - список задач с пагинацией (MCP `list_project_issues` не умеет фильтр по статусу и на 148 задачах выдаёт 75К+ символов);
  - **relations** — в MCP отсутствуют вовсе.

  **Преамбула — обязательна в каждом вызове Bash с `curl`.** Состояние shell между вызовами Bash не сохраняется: сохраняется только рабочий каталог, переменные — нет. Поэтому `B=` (база API) и `KEY=` (ключ) присваиваются **в том же самом вызове Bash**, что и сам `curl`; отдельный блок с одним `KEY=` бесполезен — в следующем вызове `$KEY` будет пуст, а `$B` без присваивания пуст всегда.
  ```bash
  B="https://api.plane.so/api/v1/workspaces/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc"
  KEY=$(python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude.json')))['mcpServers']['plane']['env']['PLANE_API_KEY'])")
  ```
  Заголовок `x-api-key: $KEY` — **во всех** запросах к API, без него 401. Ключ не светить: только внутри `-H "x-api-key: $KEY"`; не делать `echo "$KEY"`, не подставлять в URL, не печатать в ответ и не записывать в файлы планов.

  Список Todo (фильтр на клиенте, курсорная пагинация `?per_page=100&cursor=...` пока `next_page_results`):
  ```bash
  B="https://api.plane.so/api/v1/workspaces/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc"
  KEY=$(python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude.json')))['mcpServers']['plane']['env']['PLANE_API_KEY'])")
  curl -sS -H "x-api-key: $KEY" "$B/issues/?per_page=100"
  # следующая страница: "$B/issues/?per_page=100&cursor=<next_cursor>"
  ```
  Relations задачи:
  ```bash
  B="https://api.plane.so/api/v1/workspaces/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc"
  KEY=$(python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude.json')))['mcpServers']['plane']['env']['PLANE_API_KEY'])")
  curl -sS -H "x-api-key: $KEY" "$B/issues/<id>/relations/"
  # → {"blocking":[...],"blocked_by":[...],"start_after":[...],...}
  ```

## Параметры запуска
- **PLANS_DIR** — папка для файлов планов.
  - Если пользователь указал папку в запросе — использовать её (например «в docs/plan/night-shift/» → `docs/plan/night-shift/`).
  - Иначе — по умолчанию `docs/plan/auto/`.
  - Создать каталог, если его нет.
- **MAX_ITER** = 30 — лимит итераций (обработанных задач) за один запуск.

## Подготовка (один раз перед циклом)
1. Определить **PLANS_DIR** и **MAX_ITER = 30**.
2. Зафиксировать константы Plane:
   - workspace slug: `belchch`
   - project: `catalog-app`, identifier `CATALOG`, id `84997489-c485-4448-9ebe-0a06c4fa3cbc`
3. `mcp__plane__list_states` с `project_id=84997489-c485-4448-9ebe-0a06c4fa3cbc`, по полю `name` найти:
   - **TODO_STATE_ID** = state с `name == "Todo"` (ожидаемо `a81f8cef-f7d7-471a-b3f1-a6e9a457e5f9`, group `unstarted`)
   - **INPROGRESS_STATE_ID** = state с `name == "In Progress"` (ожидаемо `bc19d2fb-0962-4cb0-96de-15a8478daf4d`, group `started`)
   - Если какого-то статуса нет — сообщить об ошибке и остановиться.
4. Один раз снять **весь список задач** через curl (с пагинацией), отфильтровать `state == TODO_STATE_ID`, `deleted_at == null`, `is_draft == false`, отсортировать по `sequence_id` по возрастанию → это **QUEUE** (FIFO). Держать в памяти `id, sequence_id, name` каждой.
5. `mkdir -p <PLANS_DIR>`.
6. ITER = 0. **CREATED** = пустой список путей файлов, созданных за этот запуск (пополняется на шаге 2.6).

## Цикл (повторять, пока ITER < MAX_ITER)

### ШАГ 1 — Взять задачу
- Взять первую необработанную задачу из QUEUE (наименьший `sequence_id`).
- **Если QUEUE исчерпана** → выйти из цикла: «Задач в Todo больше нет».
- Идентификатор задачи: `CATALOG-<sequence_id>`.

### ШАГ 2 — Перевести в In Progress, собрать ТЗ и определить тип

1. `mcp__plane__update_issue` с `project_id`, `issue_id=<id>`, `state=<INPROGRESS_STATE_ID>` — задача переходит в In Progress. Если тул требует иные имена полей — свериться со схемой; фолбэк (преамбула + curl в одном вызове Bash):
   ```bash
   B="https://api.plane.so/api/v1/workspaces/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc"
   KEY=$(python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude.json')))['mcpServers']['plane']['env']['PLANE_API_KEY'])")
   curl -sS -X PATCH -H "x-api-key: $KEY" -H "Content-Type: application/json" \
     -d '{"state":"<INPROGRESS_STATE_ID>"}' "$B/issues/<id>/"
   ```
2. Полное описание задачи:
   ```bash
   B="https://api.plane.so/api/v1/workspaces/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc"
   KEY=$(python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude.json')))['mcpServers']['plane']['env']['PLANE_API_KEY'])")
   curl -sS -H "x-api-key: $KEY" "$B/issues/<id>/"
   ```
   → `description_html` (счистить теги → plain text). `description_stripped` можно использовать как черновой вариант, но HTML-версия полнее (списки, заголовки).
3. Комментарии: `mcp__plane__get_issue_comments`; фолбэк — curl (ответ постраничный, комментарии в `results`):
   ```bash
   B="https://api.plane.so/api/v1/workspaces/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc"
   KEY=$(python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude.json')))['mcpServers']['plane']['env']['PLANE_API_KEY'])")
   curl -sS -H "x-api-key: $KEY" "$B/issues/<id>/comments/?per_page=100"
   ```
   Отсортировать по `created_at`.
4. Определить **ТЗ** и **ПРЕДЫСТОРИЮ**:
   - **Комментарии есть** → ТЗ = текст *последнего* комментария (счистить HTML). ПРЕДЫСТОРИЯ = описание задачи + все комментарии, кроме последнего, в хронологическом порядке.
   - **Комментариев нет** → ТЗ = описание задачи. ПРЕДЫСТОРИИ нет (секция в плане: «_нет — комментариев к задаче не было_»).
5. Определить **тип(ы) шага** по ТЗ (при неоднозначности — по названию и предыстории):
   - `ui` — задача про интерфейс/`frontend/` (новый экран, компонент, поведение UI). Маркер `ui` включает в pipeline фазу дизайна (`catalog-designer`) и UI-ревью (`catalog-ui-reviewer`).
   - `code` — всё остальное (backend, API, скрипты, инфраструктура).
   - **Оба аспекта** → два отдельных файла плана: `code` (backend-часть) и `ui` (интерфейсная часть). В каждом — только его часть работы; планы ссылаются друг на друга в «Контексте», `code`-план — предусловие `ui`-плана.
6. Создать каркас файла плана в PLANS_DIR — по одному файлу на каждый тип из п. 5.
   - Имя файла (черновое, до префиксов): `CATALOG-<sequence_id>-<type>-<slug>.md`, `<slug>` — короткий английский kebab-case транслит ТЗ (~3–5 слов). Если транслит затруднён — `CATALOG-<sequence_id>-<type>.md`. Пометка типа обязательна.
   - Содержимое-каркас:
     ```markdown
     # <CATALOG-NN> — <название задачи>

     - **Задача Plane:** [CATALOG-NN](https://app.plane.so/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc/issues/<id>) (id: `<id>`, state: In Progress)
     - **Статус плана:** Draft
     - **Тип шага:** <code | ui>
     - **Очередь:** _(заполняется после цикла)_
     - **Цель:** _(заполняется на шаге 3)_

     ## Постановка задачи (актуальное ТЗ)
     _(источник: последний комментарий от <дата> | описание задачи — заполнить текстом ТЗ)_

     ## Предыстория
     > Это уже было: старое описание и предыдущие обсуждения. Приведено для контекста, НЕ является актуальным заданием.

     _(описание и комментарии, кроме последнего, в хронологическом порядке с датами; либо «нет — комментариев к задаче не было»)_

     ## Контекст
     _(заполняется на шаге 3)_

     ## Затрагиваемые файлы
     _(заполняется на шаге 3)_

     ## План действий
     _(заполняется на шаге 3)_

     ## Критерии приёмки (Definition of Done)
     _(заполняется на шаге 3)_
     ```
   - Записать каркас (Write); «Постановка задачи» и «Предыстория» заполнить сразу из п. 4. Каждый записанный путь добавить в **CREATED**.

### ШАГ 3 — Проанализировать код и заполнить план

1. **Анализ кодовой базы.** Из ТЗ (+ название, предыстория) выделить ключевые слова/сущности и найти релевантный код: Grep/Glob/Read по `backend/`, `frontend/` и др. Найти модули, функции, маршруты, типы, файлы, которые затронет задача. Оценить текущую реализацию и место изменения.
2. **Заполнить план** (Edit по плейсхолдерам) — при разбиении на `code` + `ui` заполнить оба файла, каждый в рамках своей части:
   - **Цель:** 1–3 предложения на основе ТЗ.
   - **Контекст:** почему/как сейчас устроено, ссылки `path/to/file.py:NN`. При разбиении — ссылка на парный план и порядок (`code` раньше `ui`).
   - **Затрагиваемые файлы:** конкретные файлы (существующие и новые) с пометкой, что меняется.
   - **План действий:** нумерованные исполнимые шаги.
   - **Критерии приёмки:** чек-лист `[ ]` проверимых условий (тесты, lint, typecheck, ручные проверки).
3. **Статус плана** → `Analyzed` — в каждом созданном файле.

### Конец итерации
- ITER += 1.
- Если ITER >= MAX_ITER → выйти из цикла: «Достигнут лимит итераций (30)».
- Иначе — к **ШАГУ 1** (обработанная задача уже In Progress и в QUEUE не вернётся).

## После цикла — префиксы по зависимостям Plane (обязательно)

Выполняется **один раз после выхода из цикла**, до финального отчёта — **всегда**, в том числе при ITER = 0.

Уже пронумерованные файлы (`^[0-9]{2}-CATALOG-`) **не переименовывать и не перенумеровывать**: их имена — ключи `STATE.steps` файла состояния `catalog-pipeline` и порядок очереди. Снимать префиксы со всей папки запрещено.

### 0. Состав батча

Ключ плана: `(sequence_id, type)` из имени `CATALOG-<n>-<code|ui>-…` или `NN-CATALOG-<n>-<code|ui>-…`. Если имя не парсится — из шапки (`CATALOG-NN` + **Тип шага**).

- **EXISTING** — файлы в PLANS_DIR с именем `NN-CATALOG-*.md` (`NN` = две цифры). Заморожены.
- **CANDIDATES** — объединение: (a) пути из **CREATED** без префикса `NN-`; (b) любые другие `CATALOG-*.md` в PLANS_DIR без префикса `NN-` (хвосты прошлого сбоя). `*.design.md` и `_dup-*` сюда не входят.
- **Orphan-дубликат** — кандидат, чей ключ уже есть в EXISTING. В BATCH не включать, не нумеровать. Переименовать в `_dup-<старый basename>` (`git mv` / `mv`). Канон — файл EXISTING. В карту ссылок: старый basename и путь → basename и путь канона. Если `_dup-…` занято — суффикс `-2`, `-3`, ….
- **Дубликаты внутри кандидатов:** несколько файлов с одним ключом без пары в EXISTING → в BATCH один канон (сначала из CREATED, при нескольких/только хвостах — меньший basename), остальные — orphan-дубликаты (тот же `_dup-` и карта на канон, который ещё получит `NN-`).
- **BATCH** — что осталось: не больше одного файла на ключ.
- BATCH пуст — шаг всё равно выполнен: в отчёте «непронумерованных планов нет» + список `_dup-`, если были. Relations для пустого батча не вызывать. EXISTING не трогать.

Стартовый номер: `START = max(NN из EXISTING) + 1`, если EXISTING пуст — `0`. Вставка «в середину» EXISTING запрещена.

### 1. Снять граф из Plane

Для каждой **уникальной** задачи BATCH (поле `id` в шапке плана):
```bash
B="https://api.plane.so/api/v1/workspaces/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc"
KEY=$(python3 -c "import json,os;print(json.load(open(os.path.expanduser('~/.claude.json')))['mcpServers']['plane']['env']['PLANE_API_KEY'])")
curl -sS -H "x-api-key: $KEY" "$B/issues/<id>/relations/"
```
Ответ — объект со списками `blocking`, `blocked_by`, `start_after`, `finish_before` и т.п.; элементы — задачи (id / объекты с id — смотреть фактическую форму ответа).

Ребро **тикетов** — только `blocking` / `blocked_by`:
- `A blocking B` или `B blocked_by A` → тикет A раньше тикета B.
- `relates_to`, `duplicate`, `start_*`, `finish_*` — не использовать.

Соседа-тикета нет ни в BATCH, ни в EXISTING → ребро отбросить. Сосед только в EXISTING → в топосорт BATCH ребро не входит (новые файлы и так после всех EXISTING), но в строку **Очередь** соседа записать. Если тикет BATCH **blocking** тикет EXISTING — EXISTING не переименовывать; в отчёте явно: зависимость «новый блокирует уже пронумерованный» в префиксе EXISTING не отражена.

Запомнить по каждому тикету BATCH списки `blocked_by` / `blocking` (соседи из BATCH ∪ EXISTING) — для строки **Очередь**.

### 2. Тикет → рёбра между файлами

Узел сортировки — **файл плана** из BATCH.

1. **Внутри тикета:** ребро от каждого `code`-файла тикета к каждому его `ui`-файлу (`ui` не стартует без `code`). Однотипные файлы (не должны остаться после §0) — рёбер нет, порядок по tie-break Kahn.
2. **Между тикетами:** для каждого ребра тикетов `A → B` из §1, где оба имеют файлы в BATCH — рёбра от каждого файла A к каждому файлу B. Итог: любой файл B ждёт все файлы A; вместе с внутритикетным: `A-code → A-ui → B-code → B-ui`.
3. Файлы EXISTING в граф BATCH не добавлять.

Входящее ребро у файла есть только если построено правилами 1–2. Не подменять это «у тикета есть blocked_by».

Алгоритм Kahn. Среди готовых (и при дописывании хвоста цикла) ключ сортировки, все три уровня обязательны:
1. меньший `sequence_id`;
2. при равенстве — `code` раньше `ui`;
3. при равенстве типа — меньший basename (лексикографически).

Хвост цикла — в отчёте как циклический граф.

Результат: упорядоченный список файлов BATCH `F0, F1, …`.

### 3. Переименовать, шапка, ссылки

Построить **RENAME_MAP** (старое → новое) до первого `mv`. Для каждого `Fi`:
- `NN = START + i` (две цифры: `00`, `01`, …).
- Новое имя: `NN-CATALOG-<sequence_id>-<type>-<slug>.md`. Stem после `NN-` не менять.
- В карту: basename старый → новый; относительный путь от корня репо старый → новый; то же для соседнего `<stem>.design.md`, если есть.

По каждому `Fi`:
1. Переименовать: `git mv`, если файл в индексе git; иначе `mv`. Соседний `<stem>.design.md` — тем же способом.
2. В шапке (после **Тип шага**) выставить **Очередь:**
   - есть `blocked_by` / `blocking` → `NN · blocked_by CATALOG-X · blocking CATALOG-Y` (соседи из BATCH ∪ EXISTING; лишние куски опустить);
   - рёбер нет и не парный `ui` → `NN · независимый`;
   - парный `ui` после своего `code` → `NN · предусловие: MM (code того же тикета)`; Plane-рёбра тикета — через `·`.

**Ссылки — отдельный проход по всей PLANS_DIR** (все `*.md`, включая EXISTING, `_dup-*` и `*.design.md`), после всех `mv`. Для каждой пары из RENAME_MAP **и** карт orphan→канон заменить все вхождения: basename; путь от корня репо; тот же stem у `.design.md`. Существующие `NN-…` имена EXISTING не подменять. Осталась ссылка на имя без префикса из RENAME_MAP — ошибка шага, исправить до отчёта.

Префикс `NN-` — продолжение очереди после EXISTING. Номер CATALOG-NN для очереди не использовать.

## Итог (финальный отчёт)

- причина остановки: «нет задач в Todo» | «достигнут лимит 30 итераций»;
- сколько задач обработано (= ITER);
- BATCH: список файлов уже с новыми префиксами (пути) и `START`;
- EXISTING: сколько файлов не трогали;
- orphan-дубликаты: какие файлы ушли в `_dup-` и на какой канон схлопнуты;
- граф Plane, учтённый в префиксах (цепочки `blocked_by` / независимые; цикл — если был);
- если тикет BATCH blocking уже пронумерованный EXISTING — перечислить;
- сколько задач в Todo осталось (если лимит, а не исчерпание).

## Жёсткие правила

- **Одна задача за итерацию.** Не объединять задачи в один план. Разбиение на `code` + `ui` — два файла в рамках одной итерации (ITER += 1).
- **Последний комментарий главнее описания.** Требования описания и старых комментариев сами по себе не исполняются, если не подтверждены последним комментарием.
- **Брать только статус Todo.** Backlog / In Progress / Done / Cancelled не трогать.
- **Без вопросов** — действовать автономно. Не останавливаться на уточнениях внутри цикла.
- **Не реализовывать задачу** — только перевод в In Progress и создание/заполнение плана. Код не правится (кроме файла плана).
- **Не коммитить.** Файлы планов остаются в working tree; решение о коммите — за человеком.
- **Идемпотентность по статусу:** обработанная задача уходит в In Progress, повторный запуск продолжит с оставшихся Todo.
- Дубликат существующего плана — всё равно создать план и сослаться в «Контексте»; после цикла дубликат с ключом EXISTING — orphan → `_dup-`, не второй `NN-`.
- **После цикла всегда префиксы**, и при ITER = 0. Не оставлять `CATALOG-*.md` без `NN-` (кроме `_dup-*`). Не пропускать relations, если BATCH не пуст. Не сортировать по номеру CATALOG-NN.
- **EXISTING не перенумеровывать.** Новые префиксы только у BATCH, начиная с `max(EXISTING)+1`.
- **Один слот на ключ** `(sequence_id, type)` в BATCH и в очереди pipeline.
- **Ссылки после rename** — проход по всей PLANS_DIR по RENAME_MAP.
- **API-ключ Plane не светить:** не выводить в ответ и не записывать в файлы; `$KEY` используется только в `-H "x-api-key: $KEY"`.
- **`B=` и `KEY=` — в том же вызове Bash, что и `curl`.** Переменные shell между вызовами Bash не переживают; запрос без `-H "x-api-key: $KEY"` или с пустым `$B` — это 401 / битый URL, а не «пустой ответ».
