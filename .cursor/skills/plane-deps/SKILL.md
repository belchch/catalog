# Skill: Plane → Dependencies

Автономно анализирует задачи в статусе **Todo** проекта **CATALOG** и записывает рёбра `blocking` / `blocked_by` в Plane. Статусы, описания и приоритеты не меняет. Код не правит.

Инструменты — MCP-сервер **`user-plane`**: `state` (action `list`), `workitem` (`list`, `retrieve`), `workitem_comment` (`list`), `workitem_relation` (`list`, `create`). Перед вызовом сверь схему через GetMcpTools. Если сервер в `needsAuth` — аутентифицируй через `mcp_auth`, затем повтори.

## Параметры запуска
- **SCOPE** — по умолчанию все задачи Todo проекта CATALOG. Если пользователь передал список идентификаторов (`CATALOG-12`, `CATALOG-15`) — работать только с ними (пересечение с Todo).
- Режим — **auto**: агент сам решает и сам пишет. Без вопросов и подтверждений.

## Константы Plane
- workspace slug: `belchch`
- project: `catalog-app`, identifier `CATALOG`, id `84997489-c485-4448-9ebe-0a06c4fa3cbc`

## Алгоритм

### 1. Резолв статуса Todo
Вызвать `state` action `list` с `project_id=84997489-c485-4448-9ebe-0a06c4fa3cbc`. Найти state с `name == "Todo"` → **TODO_STATE_ID** (ожидаемо `a81f8cef-f7d7-471a-b3f1-a6e9a457e5f9`). Если нет — стоп с ошибкой.

### 2. Выгрузить задачи Todo
```
workitem action=list
  project_id = "84997489-c485-4448-9ebe-0a06c4fa3cbc"
  pql        = "state = \"<TODO_STATE_ID>\""
  order_by   = "sequence_id"
  fields     = "id,name,sequence_id"
```
Пагинировать, пока не кончатся результаты. Для каждой задачи:
1. `workitem` action `retrieve` — `description_html` (счистить теги → plain text).
2. `workitem_comment` action `list` — отсортировать по времени создания.
3. **ТЗ** = текст последнего комментария, если комментарии есть; иначе описание. (То же правило, что в `plane-todo-loop`.)

Если задач ноль — отчёт «Todo пуст, рёбер нет» и выход без записи.

### 3. Снять существующие рёбра
Для каждой задачи из набора:
```
workitem_relation action=list
  project_id   = "84997489-c485-4448-9ebe-0a06c4fa3cbc"
  workitem_id  = <id>
```
Запомнить пары `blocking` / `blocked_by` внутри SCOPE (для идемпотентности и проверки циклов). Рёбра к задачам вне SCOPE игнорировать при записи новых, но учитывать при детекции циклов, если обе вершины в SCOPE.

### 4. Анализ кода и текстов
По ТЗ (+ название) каждой задачи выделить сущности, файлы, API. Grep / Glob / Read по `backend/`, `frontend/` и др. Цель — пары «B невозможен без A».

### 5. Критерии ребра (жёсткие)
Ребро `A blocking B` (A раньше B) ставить **только** если выполняется хотя бы одно:
1. **API-контракт:** A меняет/добавляет backend API или схему, B — UI/клиент поверх него.
2. **Конфликт файлов:** обе задачи правят один и тот же файл/компонент так, что порядок важен (B опирается на результат A).
3. **Явная ссылка в тексте:** в ТЗ/названии B есть «после CATALOG-N», «зависит от CATALOG-N», «blocked by CATALOG-N» и т.п.

Не ставить ребро:
- похожая тема без жёсткой зависимости;
- «желательно сделать раньше» без контракта;
- задачи, затрагивающие разные независимые модули.

Лимит: **не более 3 исходящих** рёбер (`blocking`) на одну задачу. При переполнении оставить самые сильные по критериям 1→2→3.

### 6. Проверка на цикл
Построить граф = существующие рёбра SCOPE ∪ предлагаемые. Для каждого кандидата проверить топосорт (Kahn). Ребро, которое замыкает цикл, **не писать** — добавить в отчёт как отклонённое. Существующие рёбра не удалять.

### 7. Запись
Для каждой новой пары `A → B` (A блокирует B), которой ещё нет среди существующих:
```
workitem_relation action=create
  project_id    = "84997489-c485-4448-9ebe-0a06c4fa3cbc"
  workitem_id   = <id A>
  workitem_ids  = [<id B>]
  relation_type = "blocking"
```
Существующие пары пропускать (идемпотентность). Custom relations, `relates_to`, `duplicate`, `start_*`, `finish_*` — не создавать и не трогать.

### 8. Отчёт
Сообщить:
- сколько задач Todo рассмотрено;
- таблица созданных рёбер: `CATALOG-A → CATALOG-B` + краткая причина (один из критериев);
- пропущенные дубли (уже были);
- отклонённые из-за цикла;
- задачи без исходящих/входящих рёбер (независимые).

## Жёсткие правила
- Только dependencies `blocking` / `blocked_by`. Никаких custom relations.
- Не менять статусы, описания, приоритеты, assignees, labels.
- Не создавать и не удалять задачи. Не удалять существующие рёбра.
- Не трогать задачи вне Todo (и вне SCOPE, если SCOPE задан).
- Без вопросов — действовать автономно.
- Не коммитить. Код репозитория не править.
- Идемпотентность: повторный запуск не дублирует рёбра.
