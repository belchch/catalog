# Skill: Bugbot → Grok fix loop

Ты — оркестратор цикла «Bugbot-ревью → фикс агентом на Grok» для одного PR. Git/GitHub-операции по публикации комментариев выполняешь **ты сам** (не подагенты). Bugbot-подагент только находит баги, фиксер-подагент только чинит код, коммитит и пушит — оба не трогают PR/комментарии сами.

## Параметры запуска
- **PR_TARGET** — обязателен, задаёт пользователь при вызове: ссылка на PR, `owner/repo#123`, номер PR (если репозиторий очевиден) или имя ветки.
- **MAX_ITER = 10** — лимит полных циклов (Bugbot-ревью + фикс) за один запуск.
- **FIX_MODEL = "cursor-grok-4.5-high-fast"** — модель фиксера (единственный доступный Grok-slug для Task-подагентов).

Если PR_TARGET не передан — спросить у пользователя ссылку/номер PR и не продолжать без него.

## Подготовка (один раз перед циклом)
1. Разрешить PR_TARGET в конкретный PR: `gh pr view <PR_TARGET> --json number,url,headRefName,baseRefName,headRepositoryOwner,headRepository`. Если `gh` не может резолвнуть цель — сообщить об ошибке и остановиться (не угадывать репозиторий).
2. Запомнить: `PR_NUMBER`, `PR_URL`, `HEAD_BRANCH`, `BASE_BRANCH`.
3. Убедиться, что `HEAD_BRANCH` — текущая локальная ветка:
   - Если уже на ней — продолжить.
   - Если на другой ветке — попытаться `git checkout <HEAD_BRANCH>` (после `git fetch origin`, если ветки нет локально).
   - Если checkout блокируется (несохранённые изменения, конфликты) — объяснить блокер и спросить, застэшить ли локальные изменения. Стэшить только после подтверждения, затем повторить checkout.
4. `REPO_PATH` = абсолютный путь корня репозитория. `ITER = 0`. `fixer_agent_id = null`. `prev_findings_signature = null`.

## Цикл (повторять, пока ITER < MAX_ITER)

### Шаг A — Bugbot-ревью (свежий подагент, без resume)
Запустить Task → `subagent_type: "bugbot"`, `description: "Bugbot"`, `run_in_background: false`, промпт по формату из review-bugbot:
```text
Full Repository Path: <REPO_PATH>
Diff: branch changes
Base Branch: <BASE_BRANCH>
```
Обработка результата — как в review-bugbot (при ошибке диффа — один retry с `Diff: natural language`; при ошибке вызова — один retry с исправленным промптом; повторный сбой — остановить весь цикл и сообщить).

Собрать findings: список `{severity, location (file:line), description}`.

### Шаг B — Нет багов → успех
Если findings пуст — выйти из цикла с результатом **«PR чист»**. Перейти к финальному отчёту.

### Шаг C — Опубликовать замечания в PR
Собрать `prev_findings_signature_new` = отсортированный список `location + description` (для проверки прогресса на шаге F).

Опубликовать комментарий в PR:
```bash
gh pr comment <PR_NUMBER> --body "<markdown>"
```
Тело — заголовок `### Bugbot review — cycle <ITER+1>/10` и таблица `Severity | Location | Finding` (сортировка по severity, как в review-bugbot). Если публикация не удалась (права, сеть) — не блокировать цикл, зафиксировать ошибку для финального отчёта и продолжить.

### Шаг D — Фикс агентом на Grok
- Если `fixer_agent_id` пуст (первая итерация с багами) — запустить **новый** Task:
  - `subagent_type: "generalPurpose"`, `model: FIX_MODEL`, `description: "Fix Bugbot findings"`, `run_in_background: false`.
  - Промпт: путь репозитория, `PR_NUMBER`/`HEAD_BRANCH`, полный список findings (severity, location, description), и инструкции:
    - Внимательно проверить каждое замечание Bugbot и исправлять только валидные; если не согласен или не уверен — явно объяснить это в ответе, а не исправлять вслепую.
    - Не менять CI-конфиги/чек-раны только чтобы скрыть проблему, не делать правки за рамками найденных багов.
    - После правок закоммитить (понятное сообщение) и запушить в `HEAD_BRANCH` (`git push`).
    - В конце сообщить, что было исправлено, что пропущено и почему.
  - Сохранить `fixer_agent_id`.
- Если `fixer_agent_id` уже есть (цикл 2+) — **resume** того же агента с промптом: новый список findings + «адресуй каждый пункт; повторно объясни, если не согласен».

### Шаг E — Проверка прогресса
- `head_after = git rev-parse HEAD`. Если фиксер не создал новый коммит (HEAD не изменился) **или** `prev_findings_signature_new == prev_findings_signature` (два цикла подряд одинаковый список замечаний) — остановить цикл досрочно с результатом **«застряло, автопрогресс невозможен»**, вывести оставшиеся findings. Перейти к финальному отчёту.
- Иначе `prev_findings_signature = prev_findings_signature_new`.

### Конец итерации
- `ITER += 1`.
- Если `ITER >= MAX_ITER` — остановить цикл с результатом **«лимит 10 итераций достигнут»**, вывести оставшиеся findings последнего прогона.
- Иначе — вернуться к **Шагу A** (Bugbot увидит новые коммиты фиксера в диффе).

## Финальный отчёт
Сообщить:
- `PR_URL`, итоговый статус: чисто / застряло / лимит итераций;
- сколько полных циклов выполнено (`ITER`);
- если не чисто — таблица оставшихся findings (Severity, Location, Finding);
- ошибки публикации комментариев, если были.

## Жёсткие правила
- Bugbot-подагент запускается **заново каждый цикл** (без resume) — он не помнит предыдущие прогоны.
- Фиксер **резюмируется** (resume) тот же instance между циклами одного запуска — так сохраняется контекст уже сделанных правок.
- Комментарии в PR публикуешь **только ты** (`gh pr comment`), не подагенты.
- Не мержить PR и не менять его base/target самостоятельно.
- Не создавать вложенных подагентов глубже `orchestrator → bugbot/fixer`.
- Если Bugbot или фиксер падают одинаково два раза подряд — остановиться и сообщить, не крутить цикл до конца лимита впустую.
