# Skill: Plane → Todo Loop

Автономно обрабатывает задачи проекта **CATALOG** из Plane (инструменты доступны через MCP-сервер `plane`, см. `~/.cursor/mcp.json`): каждую задачу в статусе **Todo** переводит в **In Progress** и создаёт для неё заполненный файл плана выполнения (на основе анализа кода). Цикл повторяется, пока есть задачи в Todo и не превышен лимит итераций.

Названия инструментов ниже (`list_states`, `list_work_items`, `update_work_item`, `retrieve_work_item`, `list_work_item_comments`) — это имена tool'ов сервера `@makeplane/plane-mcp-server`. В Cursor они видны с префиксом MCP-сервера (например `plane.list_work_items` / `mcp_plane_list_work_items`, точный формат — как показывает автодополнение инструментов). Если по имени инструмент не находится — вызови список доступных MCP-инструментов сервера `plane` и сопоставь по смыслу.

## Параметры запуска
- **PLANS_DIR** — папка для файлов планов.
  - Если пользователь указал папку в запросе — использовать её (например «в docs/plan/night-shift/» → `docs/plan/night-shift/`).
  - Иначе — по умолчанию `docs/plan/auto/`.
  - Создать каталог, если его нет.
- **MAX_ITER** = 30 — лимит итераций (обработанных задач) за один запуск.

## Подготовка (один раз перед циклом)
1. Определить **PLANS_DIR** (см. выше) и **MAX_ITER = 30**.
2. Зафиксировать константы Plane:
   - workspace slug: `belchch`
   - project: `catalog-app`, identifier `CATALOG`, id `84997489-c485-4448-9ebe-0a06c4fa3cbc`
3. Вызвать `list_states(project_id=84997489-c485-4448-9ebe-0a06c4fa3cbc)` и по полю `name` найти:
   - **TODO_STATE_ID** = state с `name == "Todo"` (ожидаемо `a81f8cef-f7d7-471a-b3f1-a6e9a457e5f9`, group `unstarted`)
   - **INPROGRESS_STATE_ID** = state с `name == "In Progress"` (ожидаемо `bc19d2fb-0962-4cb0-96de-15a8478daf4d`, group `started`)
   - Если какого-то статуса нет — сообщить об ошибке и остановиться.
4. Создать PLANS_DIR: `mkdir -p <PLANS_DIR>` (через shell).
5. ITER = 0.

## Цикл (повторять, пока ITER < MAX_ITER)

### ШАГ 1 — Взять задачу в статусе Todo (иначе конец)

Вызвать:
```
list_work_items(
  project_id = "84997489-c485-4448-9ebe-0a06c4fa3cbc",
  pql        = "state = \"<TODO_STATE_ID>\"",
  order_by   = "sequence_id",
  per_page   = 1,
  fields     = "id,name,sequence_id,state"
)
```
- Берётся ровно одна задача — первая по `sequence_id` (самая старая, FIFO).
- **Если `results` пуст** (задач в Todo нет) → выйти из цикла: «Задач в Todo больше нет».
- Иначе — это текущая задача: запомнить `id`, `sequence_id`, `name`, identifier (`CATALOG-<sequence_id>`).

### ШАГ 2 — Перевести в In Progress, собрать ТЗ и определить тип

1. `update_work_item(project_id, work_item_id=<id>, state=<INPROGRESS_STATE_ID>)` — задача переходит в In Progress.
2. Получить полное описание задачи: `retrieve_work_item(project_id, work_item_id=<id>, fields="name,description_html,priority")`. Извлечь текст из `description_html` (счистить теги).
3. Получить комментарии задачи: `list_work_item_comments(project_id, work_item_id=<id>)` (если инструмент называется иначе — найти в списке tool'ов сервера `plane` инструмент чтения комментариев work item). Отсортировать по времени создания.
4. Определить **ТЗ** (актуальную формулировку задачи) и **ПРЕДЫСТОРИЮ**:
   - **Комментарии есть** → ТЗ = текст *последнего* комментария (счистить HTML). ПРЕДЫСТОРИЯ = описание задачи + все комментарии, кроме последнего, в хронологическом порядке.
   - **Комментариев нет** → ТЗ = описание задачи. ПРЕДЫСТОРИИ нет (секция в плане: «_нет — комментариев к задаче не было_»).
5. Определить **тип(ы) шага** по ТЗ (при неоднозначности — по названию и предыстории):
   - `ui` — задача про интерфейс/`frontend/` (новый экран, компонент, поведение UI). Маркер `ui` включает в pipeline фазу дизайна (`catalog-designer`) и UI-ревью (`catalog-ui-reviewer`).
   - `code` — всё остальное (backend, API, скрипты, инфраструктура).
   - **Оба аспекта** (и backend, и интерфейс) → задача логически разбивается на **два отдельных файла плана**: один `code` (backend-часть), один `ui` (интерфейсная часть). В каждом — только его часть работы; планы ссылаются друг на друга в «Контексте», и `code`-план указывается как предусловие для `ui`-плана.
6. Создать каркас файла плана в PLANS_DIR — по одному файлу на каждый тип из п. 5.
   - Имя файла: `CATALOG-<sequence_id>-<type>-<slug>.md`, где `<type>` — `code` или `ui`, а `<slug>` — короткий английский kebab-case транслит формулировки ТЗ (убрать служебные слова, ~3–5 слов). Если транслит затруднён — `CATALOG-<sequence_id>-<type>.md`. Пометка типа в имени файла обязательна.
   - Содержимое-каркас (плейсхолдеры заполняются на шаге 3):
     ```markdown
     # <CATALOG-NN> — <название задачи>

     - **Задача Plane:** [CATALOG-NN](https://app.plane.so/belchch/projects/catalog-app/work-items/<sequence_id>) (id: `<id>`, state: In Progress)
     - **Статус плана:** Draft
     - **Тип шага:** <code | ui>
     - **Цель:** _(заполняется на шаге 3)_

     ## Постановка задачи (актуальное ТЗ)
     _(источник: последний комментарий от <дата> | описание задачи — заполнить текстом ТЗ)_

     ## Предыстория
     > Это уже было: старое описание и предыдущие обсуждения. Приведено для контекста, НЕ является актуальным заданием.

     _(описание задачи и все комментарии, кроме последнего, в хронологическом порядке с датами; либо «нет — комментариев к задаче не было»)_

     ## Контекст
     _(заполняется на шаге 3)_

     ## Затрагиваемые файлы
     _(заполняется на шаге 3)_

     ## План действий
     _(заполняется на шаге 3)_

     ## Критерии приёмки (Definition of Done)
     _(заполняется на шаге 3)_
     ```
   - Записать каркас (Write); секции «Постановка задачи» и «Предыстория» заполнить сразу из данных п. 4.

### ШАГ 3 — Проанализировать код и заполнить план

1. **Анализ кодовой базы.** Из ТЗ (+ название, предыстория) выделить ключевые слова/сущности и найти релевантный код:
   - Grep / Glob / Read по `backend/`, `frontend/` и др.
   - Найти модули, функции, маршруты, типы, файлы, которые затронет задача.
   - Оценить текущую реализацию и место изменения.
2. **Заполнить план** (StrReplace по плейсхолдерам) — при разбиении на `code` + `ui` заполнить оба файла, каждый в рамках своей части:
   - **Цель:** что должно быть сделано (1–3 предложения, на основе ТЗ).
   - **Контекст:** почему/как сейчас устроено, на что опираемся (ссылки на файлы и строки в формате `path/to/file.py:NN`). При разбиении — ссылка на парный план и порядок выполнения (`code` раньше `ui`).
   - **Затрагиваемые файлы:** список конкретных файлов (существующих и новых) с короткой пометкой, что в них меняется.
   - **План действий:** нумерованные шаги реализации (конкретные, исполнимые).
   - **Критерии приёмки:** чек-лист `[ ]` проверимых условий (тесты, lint, typecheck, ручные проверки).
3. Изменить **Статус плана** → `Analyzed` (план заполнен, код проанализирован) — в каждом созданном файле.

### Конец итерации

- ITER += 1.
- Если ITER >= MAX_ITER → выйти из цикла: «Достигнут лимит итераций (30)».
- Иначе — вернуться к **ШАГУ 1** (задача, обработанная на этой итерации, уже в In Progress и не попадёт в выборку Todo снова).

## Итог (финальный отчёт)

После выхода из цикла сообщить:
- причина остановки: «нет задач в Todo» | «достигнут лимит 30 итераций»;
- сколько задач обработано (= ITER);
- список созданных файлов планов (пути);
- сколько задач в Todo осталось (если лимит, а не исчерпание).

## Жёсткие правила

- **Одна задача за итерацию.** Не объединять несколько задач в один план. Разбиение одной задачи на `code` + `ui` — это два файла в рамках *одной* итерации (ITER увеличивается на 1).
- **Последний комментарий главнее описания.** Если у задачи есть комментарии, актуальное задание — последний комментарий; описание и прочие комментарии — только предыстория, их требования сами по себе не исполняются, если не подтверждены последним комментарием.
- **Брать только статус Todo.** Задачи в Backlog / In Progress / Done / Cancelled не трогать.
- **Без вопросов** — действовать автономно по этой инструкции. Не останавливаться на уточнениях внутри цикла.
- **Не реализовывать задачу** — skill только переводит в In Progress и создаёт/заполняет *план*. Код не правится (кроме файла плана).
- **Не коммитить.** Изменения (файлы планов) остаются в working tree; решение о коммите — за человеком.
- **Идемпотентность по статусу:** обработанная задача уходит в In Progress, поэтому повторный запуск skill безопасно продолжит с оставшихся Todo.
- Если на шаге 3 анализ показывает, что задача дублирует уже существующий план в PLANS_DIR — всё равно создать отдельный план и сослаться на дубликат в «Контексте».
