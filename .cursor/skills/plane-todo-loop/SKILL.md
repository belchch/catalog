# Skill: Plane → Todo Loop

Автономно обрабатывает задачи проекта **CATALOG** из Plane: каждую задачу в статусе **Todo** переводит в **In Progress** и создаёт для неё заполненный файл плана выполнения (на основе анализа кода). Цикл повторяется, пока есть задачи в Todo и не превышен лимит итераций. После цикла планы переименовываются с префиксом очереди `NN-` по зависимостям Plane.

Инструменты — MCP-сервер **`user-plane`**: `state` (action `list`), `workitem` (`list`, `retrieve`, `update`), `workitem_comment` (`list`), `workitem_relation` (`list`). Перед вызовом сверь схему через GetMcpTools. Если сервер в `needsAuth` — аутентифицируй через `mcp_auth`, затем повтори.

Зависимости `blocking` / `blocked_by` между задачами Todo **не проставляет** этот скилл — их пишет фаза 1 цепочки [`plane-deps`](../plane-deps/SKILL.md) (или `/plane-deps` вручную) **до** запуска todo-loop. Здесь зависимости только читаются для нумерации `NN-`.

## Параметры запуска
- **PLANS_DIR** — папка для файлов планов.
  - Если пользователь указал папку в запросе — использовать её (например «в docs/plan/night-shift/» → `docs/plan/night-shift/`).
  - Иначе — по умолчанию `docs/plan/auto/`.
  - Создать каталог, если его нет.
- **MAX_ITER** = 30 — лимит итераций (обработанных задач) за один запуск.

## Подготовка (один раз перед циклом)
1. Определить **PLANS_DIR** (см. выше) и **MAX_ITER = 30**.
2. Зафиксировать константы Plane:
   - workspace slug: `belchch`
   - project: `catalog-app`, identifier `CATALOG`, id `84997489-c485-4448-9ebe-0a06c4fa3cbc`
3. Вызвать `state` action `list` с `project_id=84997489-c485-4448-9ebe-0a06c4fa3cbc` и по полю `name` найти:
   - **TODO_STATE_ID** = state с `name == "Todo"` (ожидаемо `a81f8cef-f7d7-471a-b3f1-a6e9a457e5f9`, group `unstarted`)
   - **INPROGRESS_STATE_ID** = state с `name == "In Progress"` (ожидаемо `bc19d2fb-0962-4cb0-96de-15a8478daf4d`, group `started`)
   - Если какого-то статуса нет — сообщить об ошибке и остановиться.
4. Создать PLANS_DIR: `mkdir -p <PLANS_DIR>` (через shell).
5. ITER = 0. **CREATED** = пустой список путей файлов, созданных за этот запуск (пополняется на шаге 2.6).

## Цикл (повторять, пока ITER < MAX_ITER)

### ШАГ 1 — Взять задачу в статусе Todo (иначе конец)

Вызвать:
```
workitem action=list
  project_id = "84997489-c485-4448-9ebe-0a06c4fa3cbc"
  pql        = "state = \"<TODO_STATE_ID>\""
  order_by   = "sequence_id"
  per_page   = 1
  fields     = "id,name,sequence_id,state"
```
- Берётся ровно одна задача — первая по `sequence_id` (самая старая, FIFO).
- **Если `results` пуст** (задач в Todo нет) → выйти из цикла: «Задач в Todo больше нет».
- Иначе — это текущая задача: запомнить `id`, `sequence_id`, `name`, identifier (`CATALOG-<sequence_id>`).

### ШАГ 2 — Перевести в In Progress, собрать ТЗ и определить тип

1. `workitem` action `update` с `project_id`, `workitem_id=<id>`, `state=<INPROGRESS_STATE_ID>` — задача переходит в In Progress.
2. Получить полное описание задачи: `workitem` action `retrieve` с `project_id`, `workitem_id=<id>`, `fields="name,description_html,priority"`. Извлечь текст из `description_html` (счистить теги).
3. Получить комментарии задачи: `workitem_comment` action `list` с `project_id`, `workitem_id=<id>`. Отсортировать по времени создания.
4. Определить **ТЗ** (актуальную формулировку задачи) и **ПРЕДЫСТОРИЮ**:
   - **Комментарии есть** → ТЗ = текст *последнего* комментария (счистить HTML). ПРЕДЫСТОРИЯ = описание задачи + все комментарии, кроме последнего, в хронологическом порядке.
   - **Комментариев нет** → ТЗ = описание задачи. ПРЕДЫСТОРИИ нет (секция в плане: «_нет — комментариев к задаче не было_»).
5. Определить **тип(ы) шага** по ТЗ (при неоднозначности — по названию и предыстории):
   - `ui` — задача про интерфейс/`frontend/` (новый экран, компонент, поведение UI). Маркер `ui` включает в pipeline фазу дизайна (`catalog-designer`) и UI-ревью (`catalog-ui-reviewer`).
   - `code` — всё остальное (backend, API, скрипты, инфраструктура).
   - **Оба аспекта** (и backend, и интерфейс) → задача логически разбивается на **два отдельных файла плана**: один `code` (backend-часть), один `ui` (интерфейсная часть). В каждом — только его часть работы; планы ссылаются друг на друга в «Контексте», и `code`-план указывается как предусловие для `ui`-плана.
6. Создать каркас файла плана в PLANS_DIR — по одному файлу на каждый тип из п. 5.
   - Имя файла (черновое, до префиксов после цикла): `CATALOG-<sequence_id>-<type>-<slug>.md`, где `<type>` — `code` или `ui`, а `<slug>` — короткий английский kebab-case транслит формулировки ТЗ (убрать служебные слова, ~3–5 слов). Если транслит затруднён — `CATALOG-<sequence_id>-<type>.md`. Пометка типа в имени файла обязательна. После цикла файлы переименуются в `NN-CATALOG-…` (см. «После цикла»).
   - Содержимое-каркас (плейсхолдеры заполняются на шаге 3):
     ```markdown
     # <CATALOG-NN> — <название задачи>

     - **Задача Plane:** [CATALOG-NN](https://app.plane.so/belchch/projects/catalog-app/work-items/<sequence_id>) (id: `<id>`, state: In Progress)
     - **Статус плана:** Draft
     - **Тип шага:** <code | ui>
     - **Очередь:** _(заполняется после цикла)_
     - **Цель:** _(заполняется на шаге 3)_

     ## Постановка задачи (актуальное ТЗ)
     _(источник: последний комментарий от <дата> | описание задачи — заполнить текстом ТЗ)_

     ## Предыстория
     > Это уже было: старое описание и предыдущие обсуждения. Приведено для контекста, НЕ является актуальным заданием.

     _(описание задачи и все комментарии, кроме последнего, в хронологическом порядке с датами; либо «нет — комментариев к задаче не было»)_

     ## Контекст
     _(заполняется на шаге 3)_

     ## Затрагиваемые файлы
     _(заполняется на шаге 3)_

     ## План действий
     _(заполняется на шаге 3)_

     ## Критерии приёмки (Definition of Done)
     _(заполняется на шаге 3)_
     ```
   - Записать каркас (Write); секции «Постановка задачи» и «Предыстория» заполнить сразу из данных п. 4. Каждый записанный путь добавить в **CREATED**.

### ШАГ 3 — Проанализировать код и заполнить план

1. **Анализ кодовой базы.** Из ТЗ (+ название, предыстория) выделить ключевые слова/сущности и найти релевантный код:
   - Grep / Glob / Read по `backend/`, `frontend/` и др.
   - Найти модули, функции, маршруты, типы, файлы, которые затронет задача.
   - Оценить текущую реализацию и место изменения.
2. **Заполнить план** (StrReplace по плейсхолдерам) — при разбиении на `code` + `ui` заполнить оба файла, каждый в рамках своей части:
   - **Цель:** что должно быть сделано (1–3 предложения, на основе ТЗ).
   - **Контекст:** почему/как сейчас устроено, на что опираемся (ссылки на файлы и строки в формате `path/to/file.py:NN`). При разбиении — ссылка на парный план и порядок выполнения (`code` раньше `ui`).
   - **Затрагиваемые файлы:** список конкретных файлов (существующих и новых) с короткой пометкой, что в них меняется.
   - **План действий:** нумерованные шаги реализации (конкретные, исполнимые).
   - **Критерии приёмки:** чек-лист `[ ]` проверимых условий (тесты, lint, typecheck, ручные проверки).
3. Изменить **Статус плана** → `Analyzed` (план заполнен, код проанализирован) — в каждом созданном файле.

### Конец итерации

- ITER += 1.
- Если ITER >= MAX_ITER → выйти из цикла: «Достигнут лимит итераций (30)».
- Иначе — вернуться к **ШАГУ 1** (задача, обработанная на этой итерации, уже в In Progress и не попадёт в выборку Todo снова).

## После цикла — префиксы по зависимостям Plane (обязательно)

Выполняется **один раз после выхода из цикла**, до финального отчёта — **всегда**, в том числе при ITER = 0.

Уже пронумерованные файлы (`^[0-9]{2}-CATALOG-`) **не переименовывать и не перенумеровывать**: их имена — ключи `STATE.steps` в файле состояния `catalog-pipeline` и порядок очереди. Снимать префиксы со всей папки запрещено.

### 0. Состав батча

Ключ плана: `(sequence_id, type)` из имени `CATALOG-<n>-<code|ui>-…` или `NN-CATALOG-<n>-<code|ui>-…`. Если имя не парсится — из шапки (`CATALOG-NN` + **Тип шага**).

- **EXISTING** — файлы в PLANS_DIR с именем `NN-CATALOG-*.md` (`NN` = две цифры). Заморожены.
- **CANDIDATES** — объединение: (a) пути из **CREATED** этого запуска без префикса `NN-`; (b) любые другие `CATALOG-*.md` в PLANS_DIR без префикса `NN-` (хвосты прошлого сбоя). `*.design.md` и файлы `_dup-*` сюда не входят.
- **Orphan-дубликат** — кандидат, чей ключ `(sequence_id, type)` уже есть в EXISTING. После сбоя так остаётся непронумерованная копия уже принятого в очередь плана. В BATCH **не включать**, **не нумеровать**. Переименовать в `_dup-<старый basename>` (`git mv` / `mv`). Канон — файл EXISTING. В карту ссылок: старый basename и путь orphan → basename и путь канона EXISTING. Если `_dup-…` занято — суффикс `-2`, `-3`, ….
- **Дубликаты внутри кандидатов.** Несколько файлов с одним ключом и без пары в EXISTING: в BATCH оставить **один** канон — сначала из **CREATED**, при нескольких CREATED / только хвосты — меньший basename. Остальные — orphan-дубликаты (тот же `_dup-` и карта ссылок на канон, который ещё получит `NN-`).
- **BATCH** — то, что осталось после двух дедупов: не больше одного файла на ключ `(sequence_id, type)`.
- Если BATCH пуст — шаг всё равно выполнен: в отчёте «непронумерованных планов нет» и список `_dup-`, если были. Relations для пустого батча не вызывать. EXISTING не трогать.

Стартовый номер: `START = max(NN из EXISTING) + 1`, если EXISTING пуст — `0`. Новые префиксы только `START`, `START+1`, … — вставка «в середину» EXISTING запрещена.

### 1. Снять граф из Plane

Для каждой **уникальной** задачи BATCH (поле `id` в шапке плана) вызвать:

```
workitem_relation action=list
  project_id   = "84997489-c485-4448-9ebe-0a06c4fa3cbc"
  workitem_id  = <id>
```

Ребро **тикетов** — только `dependencies.blocking` / `dependencies.blocked_by`:
- `A blocking B` или `B blocked_by A` → тикет A раньше тикета B.
- `relates to`, `duplicate`, `start_*`, `finish_*` — не использовать.

Соседа-тикета нет ни в BATCH, ни в EXISTING → ребро отбросить (на порядок батча не влияет). Сосед только в EXISTING → в топосорт BATCH ребро не входит (новые файлы и так после всех EXISTING), но в строку **Очередь** соседа записать. Если тикет BATCH **blocking** тикет EXISTING — EXISTING не переименовывать; в отчёте явно: зависимость «новый блокирует уже пронумерованный» в префиксе EXISTING не отражена.

Запомнить по каждому тикету BATCH списки `blocked_by` / `blocking` (соседи из BATCH ∪ EXISTING) — для строки **Очередь**.

### 2. Тикет → рёбра между файлами

Узел сортировки — **файл плана** из BATCH. После §0 в BATCH не больше одного файла на `(sequence_id, type)`; у тикета в BATCH может быть `code` и/или `ui`.

Рёбра файла:

1. **Внутри тикета.** Для каждой задачи: ребро от **каждого** её `code`-файла в BATCH к **каждому** её `ui`-файлу в BATCH (`ui` не стартует, пока нет `code`). Если однотипных файлов несколько (не должны, после §0) — между ними рёбер нет, порядок только tie-break Kahn.
2. **Между тикетами.** Для каждого ребра тикетов `A → B` (A раньше B) из §1, где **оба** тикета имеют файлы в BATCH: рёбра **от каждого файла A к каждому файлу B**. Итог: любой файл B ждёт все файлы A. Вместе с ребром внутри тикета: `A-code → A-ui → B-code → B-ui`, если оба типа есть.
3. Файлы EXISTING в граф BATCH **не добавлять** (их префиксы уже меньше `START`).

Входящее ребро у файла F есть тогда и только тогда, когда оно построено правилами 1–2. Не подменять это «у тикета есть blocked_by».

Алгоритм Kahn по этому графу файлов. Среди готовых (и при дописывании хвоста цикла) ключ сортировки, все три уровня обязательны:
1. меньший `sequence_id`;
2. при равенстве — `code` раньше `ui`;
3. при равенстве типа — меньший basename (лексикографически).

Дальше: снять исходящие рёбра, повторить. Хвост цикла — в отчёте как циклический граф.

Результат: упорядоченный список файлов BATCH `F0, F1, …`.

### 3. Переименовать, шапка, ссылки

Построить **RENAME_MAP** (старое → новое) до первого `mv`. Для каждого `Fi` с индексом `i`:
- `NN = START + i` (две цифры: `00`, `01`, …).
- Новое имя: `NN-CATALOG-<sequence_id>-<type>-<slug>.md`. Stem после `NN-` не менять.
- В карту: basename старый → новый; относительный путь от корня репо старый → новый; то же для соседнего `<stem>.design.md`, если файл есть.

Затем по каждому `Fi`:
1. Переименовать: `git mv`, если файл в индексе git; иначе `mv`. Соседний `<stem>.design.md` — тем же способом, если есть.
2. В шапке (сразу после **Тип шага**) выставить **Очередь:**
   - есть `blocked_by` / `blocking` из п. 1 → `NN · blocked_by CATALOG-X · blocking CATALOG-Y` (соседи из BATCH ∪ EXISTING; лишние куски опустить);
   - рёбер нет и это не парный `ui` → `NN · независимый`;
   - парный `ui` после своего `code` → `NN · предусловие: MM (code того же тикета)` (`MM` — новый префикс code-файла); Plane-рёбра тикета — дописать через `·`.

**Ссылки — отдельный проход по всей PLANS_DIR** (все `*.md`, включая EXISTING, `_dup-*` и `*.design.md`), после того как все `mv` батча и orphan-`_dup-` завершены. Для каждой пары старое → новое из RENAME_MAP **и** карт orphan→канон из §0 заменить все вхождения:
- basename (`CATALOG-79-code-workspaces-api.md`);
- путь от корня репо (`docs/plan/night-shift/CATALOG-79-code-workspaces-api.md`);
- тот же stem у `.design.md`.

Не ограничиваться «парным» code/ui одной задачи. Существующие `NN-…` имена из EXISTING в карте нет — их не подменять. Если после прохода в BATCH осталась ссылка на имя без префикса из RENAME_MAP — это ошибка шага, исправить до отчёта.

Префикс `NN-` у файлов BATCH — продолжение очереди после EXISTING. Номер CATALOG-NN для очереди не использовать.

## Итог (финальный отчёт)

После префиксов сообщить:
- причина остановки: «нет задач в Todo» | «достигнут лимит 30 итераций»;
- сколько задач обработано (= ITER);
- BATCH: список файлов **уже с новыми префиксами** (пути) и `START`;
- EXISTING: сколько файлов не трогали;
- orphan-дубликаты: какие файлы ушли в `_dup-` и на какой канон схлопнуты (EXISTING или канон BATCH);
- граф Plane, учтённый в префиксах BATCH (цепочки `blocked_by` / независимые; цикл — если был);
- если тикет BATCH blocking уже пронумерованный EXISTING — перечислить такие рёбра;
- сколько задач в Todo осталось (если лимит, а не исчерпание).

## Жёсткие правила

- **Одна задача за итерацию.** Не объединять несколько задач в один план. Разбиение одной задачи на `code` + `ui` — это два файла в рамках *одной* итерации (ITER увеличивается на 1).
- **Последний комментарий главнее описания.** Если у задачи есть комментарии, актуальное задание — последний комментарий; описание и прочие комментарии — только предыстория, их требования сами по себе не исполняются, если не подтверждены последним комментарием.
- **Брать только статус Todo.** Задачи в Backlog / In Progress / Done / Cancelled не трогать.
- **Без вопросов** — действовать автономно по этой инструкции. Не останавливаться на уточнениях внутри цикла.
- **Не реализовывать задачу** — skill только переводит в In Progress и создаёт/заполняет *план*. Код не правится (кроме файла плана).
- **Не коммитить.** Изменения (файлы планов) остаются в working tree; решение о коммите — за человеком.
- **Идемпотентность по статусу:** обработанная задача уходит в In Progress, поэтому повторный запуск skill безопасно продолжит с оставшихся Todo.
