# Ревью дифа — Step 02: LLM-провайдер (OpenRouter)

Проверил против плана `.kilo/plans/1783952198152-step-02-llm-provider.md`. `ruff check` чист, 6/6 тестов проходят. По соответствию плану — в целом ок, но есть несколько моментов.

## Критично

### 1. `stream_complete` не стримит по-настоящему (`openrouter.py:209-240`)
```python
resp = await self._client.post(...)        # вычитывает ВЕСЬ ответ
resp.raise_for_status()
async for line in resp.aiter_lines():      # идёт уже по буферу
```
`client.post` буферизует тело полностью до возврата, так что чанки не доходят до потребителя в реальном времени — смысл стриминга теряется. Нужно использовать контекстный менеджер:
```python
async with self._client.stream("POST", url, headers=..., json=body) as resp:
    if resp.status_code == 401: raise ValueError(...)
    if resp.status_code == 429: raise RuntimeError(...)
    resp.raise_for_status()
    async for line in resp.aiter_lines():
        ...
```
Тест `test_stream_complete` проходит только потому, что `MockTransport` отдаёт всё сразу и буферизация незаметна.

## Отклонения от плана

### 2. Логирование реализовано инлайн, а не через `event_hooks` (`openrouter.py:136-176, 201-207`)
План явно постановил: *«Реализуется через httpx `event_hooks` на клиенте — так логируются и сырые HTTP-запросы, и провайдер не размазывается логикой логирования»*. Реализация сделала наоборот — логика раскидана по методам провайдера. Работает, но архитектурно это другое решение, чем договаривались. Либо принять и обновить план, либо переделать на `event_hooks`.

### 3. Тело ответа при не-401/429 HTTP-ошибках не логируется (`openrouter.py:156`)
План: *«Другие HTTP ошибки → лог тела ответа + пробрасывание»*. Сейчас голый `resp.raise_for_status()` поднимает `httpx.HTTPStatusError` без лога тела — при 5xx от OpenRouter будет сложно понять причину.

## Корректность

### 4. `data["choices"][0]` без проверки (`openrouter.py:159`)
При пустом `choices` (контент-фильтр, some edge cases) — `KeyError`/`IndexError` без понятного сообщения. Стоит дать осмысленную ошибку.

### 5. `_parse_tool_calls` молча глотает невалидный JSON (`openrouter.py:67-70`)
```python
except json.JSONDecodeError:
    args = {}
```
Если модель вернёт кривые аргументы — это замаскируется пустым dict. Хотя бы `logger.warning(...)`.

## Мелочи

- **`.env.example` не обновлён** — `OPENROUTER_FALLBACK_MODEL` не задокументирован. Он хардкод, так что не критично, но для консистентности стоит упомянуть.
- **`Authorization` на `/models`** (`openrouter.py:101`) — эндпоинт публичный, ключ не нужен. Не баг, просто лишнее.
- **`Content-Type` в `_HEADERS`** избыточен — `httpx` сам ставит его при `json=body`.
- **`Message.role: str`** — можно `Literal["system","user","assistant","tool"]`, но план говорит «role: str», так что ок.
- **`smoke_llm.py:9`** — длинная строка импортов (~105 символов). Ruff пропустил, но читаемость страдает, лучше разбить.

## Что хорошо
- Чистая DI: клиент приходит в конструктор, lifecycle у caller'а — отлично для тестов и FastAPI lifespan.
- `Protocol` в `base.py` — провайдер можно будет подменить без наследования.
- Тесты на `MockTransport` — быстрые, без сети, покрывают все ветки ошибок.
- Fallback-логика в smoke честно проверяет риск «free-модель не умеет tool-calling».

## Вердикт
К приёмке годится после правки **пункта 1** (стриминг) — это реальная функциональная проблема. Пункты 2–3 требуют осознанного решения: либо привести код к плану, либо обновить план под реализацию. Остальное — полировки.
