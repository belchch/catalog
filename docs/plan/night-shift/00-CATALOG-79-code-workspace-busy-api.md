- **Тип шага:** code
- **Очередь:** 00 · независимый
- **Цель:** Расширить критерий занятости воркспейса: помимо активных `skill_run` учитывать открытые WebSocket-сессии планировщика, и отдать это состояние наружу новым readonly-эндпоинтом `GET /workspaces/busy`, чтобы UI мог показать запрет до выбора папки. Уточнение по блокировке воркспейса при активных ранах (правит п. про 409 в исходной постановке).

**Что не так сейчас**

1. Критерий «занятости» узкий. `has_running_runs()` смотрит только в `skill_run` (`pending`/`running`). Живой чат сессии (`WS /sessions/{session_id}`) долгих операций в `skill_run` не создаёт, поэтому переключение воркспейса посреди генерации ответа формально разрешено. Хендлер перечитывает `manager.current` между итерациями цикла и падает с `workspace not open`, но внутри одной итерации держит старые `db` и `tools` — то есть агент продолжает писать в базу уже закрытого воркспейса.
2. Блокировка существует только как 409 на `POST /workspaces/open`. Пользователь узнаёт о запрете после того, как прошёл дерево, выбрал папку и нажал «Открыть». В UI нет способа узнать про блокировку заранее.

**Что нужно сделать**

Бэкенд:

- Расширить критерий занятости: активные раны (`pending` + `running`, как сейчас, со сбросом зависших) **плюс** счётчик активных WebSocket-сессий в `app_state` (инкремент на accept, декремент в `finally`). `_assert_no_running()` проверяет оба источника.
- Добавить readonly-эндпоинт статуса занятости (например `GET /workspaces/busy` → `{ busy: bool, reason: "run" | "session" | null }`), чтобы UI мог показать запрет до выбора папки. Эндпоинт не должен требовать открытого воркспейса — при `current is None` отдаёт `busy: false`.

Границы блокировки (важно, чтобы не переблокировать):

- Блокируем **только** то, что подменяет активный воркспейс: `POST /workspaces/open` на другую папку и `close()`. Позже по той же логике — удаление из реестра и восстановление из бэкапа.
- **Не** блокируем: `GET /fs/browse`, `POST /workspaces/rescan`, `GET /workspaces`, работу с документами, чат, просмотр трейсов, запуск второго рана. Это работа внутри того же воркспейса, ничего не подменяется. Глушить `browse` бессмысленно: обзор ФС не связан с ранами, а список недавних воркспейсов всё равно остаётся рабочим входом к `open`.
- Повторный `open` той же самой папки блокировать не нужно (переключения нет, только ре-скан) — это текущее поведение, сохранить.

UI (вынесено в парный план, см. «Контекст»):

- В `WorkspacePicker` при `busy: true` — баннер с объяснением и disabled на кнопке открытия, включая клик по недавним.
- 409 от `open` оставить как страховку на гонку и показывать текст из `detail`.

**Приёмка (backend-часть)**

- При активном `WS /sessions/{id}` (идёт генерация) `POST /workspaces/open` на другую папку → 409; после завершения — успех.
- При `skill_run` в `pending` и в `running` → 409 (существующий тест сохранить).
- `GET /fs/browse` и `POST /workspaces/rescan` возвращают 200 при активном ране.
- `GET /workspaces/busy` отдаёт `busy: false` при отсутствии ранов и сессий, в том числе когда воркспейс не открыт.
- Зависшие раны (`pending` > 15 мин, `running` > 60 мин) не запирают переключение навсегда.

**Описание задачи (создана 2026-08-13 17:59 UTC), тип: code**

Контекст: HTTP-слой над менеджером воркспейсов и сканером. Контейнера нет — бэкенд видит ФС пользователя; обзор ограничен разрешённым корнем (`$HOME` по умолчанию).

Скоуп (в основном уже реализован, см. `backend/catalog/api/workspaces.py`):

- Новый роутер `backend/app/api/workspaces.py` (фактически лежит в `backend/catalog/api/workspaces.py`).
- `GET /workspaces` — реестр известных (путь, имя, last_opened); `GET /workspaces/current`.
- `POST /workspaces/open`: валидация → бэкап → ре-скан → активация. Ответы: ok / пустая папка (инициализация) / папка с файлами без `.catalog` (требует явного подтверждения с отчётом что найдено) / ошибка.
- `POST /workspaces/rescan` — ручной скан с отчётом added/updated/renamed/removed/skipped.
- `GET /fs/browse?path=` — листинг директорий строго в пределах разрешённого корня (защита от path traversal).
- Блокировка open/switch при активных `skill_run` в статусе running → 409 с понятным сообщением.

Критерии приёмки из описания: сценарий открыть папку → подтвердить → документы видны; при активном ране `open` возвращает 409; `/fs/browse` не выходит за разрешённый корень; ruff и pytest зелёные.

Последний комментарий сужает задачу до **доработки** уже существующего роутера: критерий занятости + эндпоинт статуса, без переписывания open/rescan/browse.
