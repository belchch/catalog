# CATALOG-90 — Документ удаляется из сессии (гонка гидрации `sessionDocuments`)

- **Задача Plane:** [CATALOG-90](https://app.plane.so/belchch/projects/catalog-app/work-items/90) (id: `49781bcf-8b67-4d64-a7d5-e1995eabc532`, state: In Progress)
- **Статус плана:** Analyzed
- **Тип шага:** code
- **Очередь:** 05 · независимый
- **Цель:** Устранить гонку, из-за которой первый выбранный документ пропадает из «Документы в сессии» при отправке первого сообщения в новом чате: ответ `GET /sessions/{id}/documents` (пустой) не должен перетирать список, уже обновлённый WS-фреймом `session_docs`.

## Постановка задачи (актуальное ТЗ)
_(источник: описание задачи от 2026-08-14 17:49 UTC; комментариев нет)_

**Bug: в новом чате первый выбранный документ пропадает из «Документы в сессии»**

Шаги воспроизведения:

1. Открыть воркспейс, нажать «Новый чат» (сессия ещё не создана).
2. В композере выбрать документ через «+ документ».
3. Ввести текст и нажать «Отправить».

**Фактический результат.** Документ исчезает: чип уходит из композера и не появляется в блоке «Документы в сессии». Список остаётся пустым до конца хода.

**Ожидаемый результат.** После отправки документ переезжает из выбранных в блок «Документы в сессии» и остаётся там.

Дополнительно: воспроизводится только на **первом** сообщении новой сессии; со вторым сообщением (сессия уже существует) всё работает. Проверить, помогает ли F5 после отправки — если документ появляется, привязка в БД прошла и баг чисто на клиенте.

**Анализ причины (гипотеза).** Клик «Отправить» в новом чате запускает две параллельные ветки:

1. `handleSend` (`frontend/src/App.tsx`, ~283) вызывает `ensureSession()` → `POST /sessions` → `setSessionId(...)`, затем `planner.send(text, docIds)`. Соединения ещё нет, поэтому сообщение кладётся в `pendingRef` (`frontend/src/hooks/usePlannerSession.ts`, ~322) и уходит уже в `onOpen`.
2. Смена `sessionId` запускает эффект в `usePlannerSession` (~215), который дергает `GET /sessions/{id}/documents` для только что созданной сессии — там пока пусто, и ответ безусловно пишется в состояние: `setSessionDocuments(docs)` (~259).

Привязка документов происходит позже, уже по WS: backend делает `attach_documents` и отправляет фрейм `session_docs` (`backend/catalog/api/sessions.py`, 695–698). Если ответ на `GET .../documents` приходит **после** этого фрейма, он перетирает актуальный список пустым массивом.

Ключевой момент: для сообщений такая защита есть — `skipHydrateRef` (учитывает непустой `pendingRef`) не даёт HTTP-гидрации затереть стрим. Для `sessionDocuments` аналогичной защиты нет. Вероятность гонки повышает `StrictMode` (`frontend/src/main.tsx`): в dev эффект выполняется дважды, GET уходит два раза, и второй ответ приходит позже. Второй усугубляющий фактор: после `finish` список документов сессии не переспрашивается, поэтому потерянное состояние не восстанавливается само.

**Варианты решения.**

- Не применять ответ `GET /sessions/{id}/documents`, если он устарел: счётчик поколений / флаг «фрейм `session_docs` уже пришёл», либо тот же приём, что у сообщений — пропускать гидрацию при непустом `pendingRef`.
- Дополнительно (страховка): вызывать `refreshSessionDocuments()` по событию `finish`.
- Альтернатива: слать `attach` документов отдельным HTTP-вызовом сразу после создания сессии, до открытия WS, чтобы у списка был один источник истины.

## Контекст
- Гонка подтверждена в коде. Эффект сессии: `frontend/src/hooks/usePlannerSession.ts:215-309`. Флаг пропуска гидрации считается на входе для **сообщений**: `:228-231` (`streamingRef || assistantBufferRef || pendingRef`), и повторно проверяется перед `setMessages` (`:236-247`).
- Документы гидрируются безусловно: `usePlannerSession.ts:259-265` — `getSessionDocuments(sessionId).then((docs) => { if (cancelled) return; setSessionDocuments(docs) })`. Ни `skipHydrateRef`, ни поколения тут не учитываются, поэтому поздний пустой ответ затирает актуальный список.
- WS-источник истины: фрейм `session_docs` обрабатывается в `usePlannerSession.ts:189-191` (`setSessionDocuments(e.documents)`). Бэкенд отправляет его сразу после привязки: `backend/catalog/api/sessions.py:696-698` (`attach_documents` → `_session_docs_frame`, сама сборка фрейма — `sessions.py:163-166`).
- Отложенная отправка: `send` кладёт сообщение в `pendingRef` при незакрытом соединении (`usePlannerSession.ts:311-327`, ветка `:325`), очередь разбирается в `onOpen` (`:284-293`).
- `finish` не трогает документы: `usePlannerSession.ts:180-185` сбрасывает только стрим-состояние. Внешняя точка обновления есть — `refreshSessionDocuments` из `App.tsx:139`, вызывается после завершения рана скилла (`App.tsx:264`), но не после завершения хода чата.
- Клиентский путь первого сообщения: `ensureSession` (`App.tsx:275-282`, `POST /sessions` + `setSessionId`) и `handleSend` (`App.tsx:284-294`).
- StrictMode включён (`frontend/src/main.tsx`), поэтому в dev эффект и запрос дублируются — это делает гонку почти стабильной, а не редкой.
- Тесты фронтенда: в `frontend/` сейчас только `build`/`lint`/`typecheck` (см. `.cursor/rules/catalog-pipeline-checks.mdc`), готового раннера юнит-тестов нет. Тест на гонку из критериев приёмки требует решения: либо добавить раннер (расширение объёма), либо проверять инвариант на уровне бэкенда/ручного сценария. Решение зафиксировать в PR.

## Затрагиваемые файлы

- `frontend/src/App.tsx` — при необходимости точка вызова `refreshSessionDocuments()` после завершения хода чата (рядом с эффектом на `planner.streaming`, `:268-273`).

## План действий
1. Ввести в `usePlannerSession` явный признак «список документов уже пришёл из WS» — например `docsFromStreamRef`, выставляемый в обработчике `session_docs` (`:189-191`), и/или счётчик поколений запроса, инкрементируемый при каждом запуске эффекта (`:215`).
2. В ветке гидрации документов (`:259-265`) применять ответ только если: запрос принадлежит текущему поколению **и** WS-фрейм ещё не приходил **и** очередь `pendingRef` пуста (тот же критерий, что у сообщений на `:239-245`). Иначе ответ отбрасывается.
3. Сбрасывать новый признак/поколение при смене сессии — рядом с существующим сбросом в `:216-231` (`resetLocal`, `prevSessionRef`), чтобы переключение чатов гидрировалось нормально.
4. Добавить страховку: по событию `finish` (`:180-185`) обновлять документы сессии — либо вызовом внутреннего рефреша, либо через эффект в `App.tsx` рядом с `:268-273` (по спаду `planner.streaming`), переиспользуя `refreshSessionDocuments`.
5. Проверить, что ручное удаление документа из сессии (`removeDocument`, `usePlannerSession.ts:343+`) не откатывается новой логикой: локальный оптимистичный фильтр не должен перетираться поздним ответом гидрации.
6. Зафиксировать решение по автотесту гонки (раннер юнит-тестов фронтенда отсутствует): либо добавить его в объём, либо описать в PR проверенный вручную сценарий «ответ `GET .../documents` приходит после `session_docs` → состояние не обнуляется».
7. Ручные проверки: первое сообщение с документом в новом чате; второе сообщение с документами в той же сессии; F5 в середине и после хода; повтор в dev (StrictMode).
8. Прогнать из `frontend/`: `pnpm run build`, `pnpm run lint`, `pnpm run typecheck`.

## Решение по автотесту гонки

Во `frontend/` нет юнит-раннера — только `pnpm run build` / `lint` / `typecheck`. Добавлять раннер в объём шага не стали.

Инвариант на клиенте: `GET /sessions/{id}/documents` применяется, только если поколение запроса ещё актуально и фрейм `session_docs` не приходил. Поздний ответ (гидрация эффекта или finish-рефреш) после `session_docs` отбрасывается — в том числе пустой GET первого хода и finish-GET прошлого хода при повторной отправке.

Ручная проверка: новый чат → документ → первое сообщение; повторная отправка с документами, пока finish-GET ещё в полёте; F5; StrictMode. Список «Документы в сессии» не обнуляется.
