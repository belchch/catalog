## Цель и пользовательский путь

Ключи провайдеров перестают быть одноразовой историей онбординга: в хедере появляется шестерёнка, за ней — модалка «Настройки» с единственным блоком «Провайдеры», где видно состояние каждого известного провайдера и можно ввести или заменить ключ.

1. Пользователь работает в приложении, в правом верхнем углу рядом с селектором модели — иконка шестерёнки.
2. Клик (или Enter с клавиатуры) → поверх приложения открывается модалка «Настройки». Фокус уходит на кнопку закрытия, фон затемнён `--overlay`.
3. В блоке «Провайдеры» — список **всех** известных провайдеров из `GET /setup`, по строке на провайдера. Видно сразу: кто подключён, кто без ключа, у кого ключ приходит из окружения, кто сейчас активный.
4. У провайдера без ключа поле ввода раскрыто сразу: вставил ключ → «Сохранить».
5. У подключённого провайдера поля нет — есть кнопка «Заменить ключ»; она раскрывает пустое поле (старый ключ не показывается, сервер его не отдаёт).
6. После успешного сохранения строка перерисовывается в статус «Подключён», под блоком коротко объявляется «Ключ сохранён», а новый провайдер сам появляется в `ModelSelector` — без F5. Активный провайдер при этом **не** переключается: подключение ключа — не смена рабочего провайдера.
7. У провайдера с `managed_by_env` поле есть, но заблокировано, и под ним объяснено, почему ввод через интерфейс не сработает.
8. Escape или ✕ закрывает панель, фокус возвращается на шестерёнку.

Отдельный сценарий — онбординг (`SetupKeyScreen`): пользователь выбирает z.ai, вводит ключ, жмёт «Сохранить ключ» — и попадает в приложение, где активным провайдером уже стоит z.ai, а не OpenRouter. Визуально экран не меняется; меняется только то, что происходит между нажатием и входом.

## Layout и состояния

### Состояния строки провайдера

Приоритет разбора — `managed_by_env` → `configured` → всё остальное.

| Состояние | Условие | Статус-бейдж | Поле ввода | Действие |
|---|---|---|---|---|
| Через окружение | `managed_by_env` | `badge-warning` «через окружение» | раскрыто, `disabled`, пустое | «Сохранить» `disabled` |
| Подключён | `configured && !managed_by_env` | `badge-success` «подключён» | скрыто | «Заменить ключ» |
| Замена ключа | подключён + нажали «Заменить ключ» | `badge-success` «подключён» | раскрыто, пустое, автофокус | «Сохранить» + «Отмена» |
| Без ключа | `!configured && !managed_by_env` | `badge-neutral` «нет ключа» | раскрыто сразу, пустое | «Сохранить» |
| Неизвестный id | id нет в карте полей ключа | как выше | раскрыто, `disabled` | «Сохранить» `disabled` + пояснение |
| Сохранение | идёт `PUT /setup/keys` по этой строке | без изменений | `disabled` | «Сохранение…», `aria-busy` |

Бейдж «активный» (`badge-info`) рисуется дополнительно к статусу, когда `active === true` — он про выбранный в `ModelSelector` провайдер, а не про наличие ключа, и потому занимает отдельное место сразу после имени.

Пока идёт сохранение по одной строке, кнопки действий **всех** строк `disabled`: параллельные `PUT /setup/keys` не нужны, а последовательность «сохранил → перезапросил статусы» должна быть однозначной.

### Состояния панели

| Состояние | Когда | Что показываем |
|---|---|---|
| Обычное | `setup.providers.length > 0` | список строк |
| Пустое | `providers` пуст (старый бэкенд, поле по умолчанию `[]`) | `p.text-xs.text-ink-faint`: «Список провайдеров недоступен — обновите бэкенд.» Список не рисуем, панель остаётся закрываемой |
| Обновление статусов | после успешного сохранения, пока идут `setup.refresh()` и `settings.refreshProviders()` | кнопки строк `disabled`, в `sr-only`-регионе «Обновляю статусы…» |
| Ошибка сохранения | `PUT /setup/keys` упал | текст `extractApiDetail(e)` под своей строкой, `role="alert"`; введённый текст **не** стирается, чтобы можно было повторить |
| Ошибка обновления | сохранение прошло, `refresh` упал | под списком `role="alert"`: «Ключ сохранён, но статусы не обновились» + кнопка «Обновить» (повтор `refresh`) |

Отдельного loading-состояния у панели нет: `App` рендерит основной UI только при `setup.status === 'ready'`, значит данные уже в руках, и открытие модалки мгновенное. Спиннер при открытии был бы ложным.

### Успех

После успешного `PUT /setup/keys` и перезапроса:

- поле очищается, форма замены схлопывается;
- строка перерисовывается в «Подключён» из свежих данных `GET /setup` — отдельного оптимистичного состояния не заводим, источник правды один;
- в `sr-only`-регионе появляется «Ключ сохранён»;
- видимая обратная связь для зрячих — смена бейджа на «подключён» и исчезновение поля; отдельной зелёной плашки не вводим, чтобы не дублировать статус.

## Взаимодействия

- **Открытие.** Клик по шестерёнке → `setSettingsOpen(true)`. У кнопки `aria-haspopup="dialog"` и `aria-expanded={settingsOpen}`.
- **Закрытие.** ✕, Escape или успешное закрытие из кода → `setSettingsOpen(false)`, фокус возвращается на шестерёнку (`ref` в `App`, `focus()` в `onClose`). Клик по затемнению **не** закрывает — так же, как в `WorkspacePicker` и `SkillSettingsModal`.
- **Escape.** Если раскрыта форма замены ключа — первый Escape схлопывает её (фокус на «Заменить ключ»), второй закрывает панель. Во время сохранения Escape не срабатывает (как `submitting` в `WorkspacePicker:215`).
- **«Заменить ключ».** Раскрывает форму, поле получает фокус и всегда пустое. Одновременно раскрыта не более одной формы замены — открытие второй схлопывает первую вместе с её текстом.
- **«Отмена».** Схлопывает форму, стирает введённое, снимает ошибку строки, возвращает фокус на «Заменить ключ».
- **«Сохранить».** Кнопка активна только при непустом `trim()`. Отправляется `saveProviderKey({ [поле провайдера]: trimmed })` — ровно одно поле, остальные не трогаются. Форма — настоящий `<form onSubmit>`, поэтому Enter в поле сохраняет.
- **Фокус после успеха.** Форма исчезает, поэтому фокус явно переносится на кнопку «Заменить ключ» этой же строки (мапа `ref`-ов по id провайдера). Без этого фокус улетел бы на `body` и пользователь потерял бы место в модалке.
- **Активный провайдер.** Панель его не меняет: ни `POST /settings`, ни `changeProvider` отсюда не вызываются.

**Крайние случаи:**

- Сохранение ключа тому провайдеру, который сейчас активен → строка остаётся «подключён», активность не трогаем, список в `ModelSelector` просто перезапрашивается.
- `refresh` вернул `providers`, где раскрытая строка исчезла (реестр изменился) → форма схлопывается сама, потому что состояние редактирования хранится по id и рисуется только для существующих строк.
- Ключ с пробелами по краям → `trim()` перед отправкой; строка из одних пробелов кнопку не активирует.
- Повторная отправка двойным Enter → блокируется `saving`-состоянием.
- Провайдер одновременно `managed_by_env` и `configured` → приоритет у env: поле заблокировано, статус «через окружение», иначе пользователь получил бы кнопку, нажатие которой ничего не меняет.
- Онбординг: `POST /settings` после сохранения ключа упал → пользователь всё равно входит в приложение (ключ-то сохранён), активным остаётся провайдер по умолчанию, сменить его можно в `ModelSelector`. Ошибку не показываем — экран в этот момент уже уходит, а блокировать вход нельзя.

## Доступность (a11y)

- Кнопка-шестерёнка: `aria-label="Настройки"` и одинаковый `title`, `aria-haspopup="dialog"`, `aria-expanded`. Внутри — `aria-hidden` SVG, доступное имя даёт только `aria-label`.
- Модалка: `role="dialog"`, `aria-modal="true"`, `aria-labelledby` на заголовок (`useId`). Блок провайдеров — `<section aria-labelledby>` на свой `h3`.
- Начальный фокус — кнопка закрытия (паттерн `WorkspacePicker:201-203`). При закрытии фокус возвращается на шестерёнку.
- Порядок Tab: ✕ → строки сверху вниз, внутри строки поле → «Сохранить» → «Отмена»/«Заменить ключ». Фокус-ловушку не вводим — её нет ни в одной существующей модалке проекта, вводить её только здесь значило бы разъехаться с остальным UI.
- Поле ключа: связанный `<label className="sr-only">` вида «API-ключ {name}» — визуальная подпись не нужна, но имя поля должно быть уникальным на весь список.
- Пояснение про env связано с полем через `aria-describedby`, чтобы скринридер прочитал причину недоступности вместе с самим полем.
- Ошибки — `role="alert"` (как `SetupKeyScreen:127`), успех и фоновое обновление — `sr-only` регион `role="status" aria-live="polite"`.
- Состояние «идёт сохранение» передаётся не только текстом кнопки: `aria-busy` на форме и нативный `disabled` на контролах.
- Escape закрывает панель; обработчик вешается на `window` и снимается при размонтировании.
- Контраст: `--ink` и `--ink-faint` на `--surface-muted`, бейджи `success`/`warning`/`neutral`/`info` — существующие пары токенов, уже выверенные в CATALOG-86; focus-ring `ring-2 ring-brand`.

## Контракты данных

- `GET /setup` → `SetupOut.providers: ProviderSetupOut[]`, где `ProviderSetupOut = { id, name, configured, managed_by_env, active }` (бэкенд — CATALOG-94, `backend/catalog/api/schemas.py`). Ключей в ответе нет и не появится: поле ввода не заполняется никогда.
- `PUT /setup/keys` через `saveProviderKey(input: SetupKeysInput)` (`api.ts:515`) — отправляем ровно одно поле. Карта `id → поле` живёт в `SettingsPanel`: `openrouter → openrouter_api_key`, `zai → zai_api_key`; id вне карты рисуется в состоянии «неизвестный id» и ничего не отправляет.
- `POST /settings` через `updateSettings` — из онбординга вызывается **только** с `provider`, без `model`: бэкенд сам подберёт модель (`coerce_model_for_provider`, `models.py:163-170`). Для этого вход `updateSettings` ослабляется до частичного (`{ provider?: string; model?: string }`); существующие вызовы с полным объектом продолжают работать.
- `useSetup` отдаёт наружу весь `SetupOut` (нужны `providers`) и `refresh(): Promise<void>`.
- `useSettings` отдаёт `refreshProviders(): Promise<void>` — перезапрос `listProviders()` без ремонта хука и без изменения выбранных `provider`/`model`.
- Порядок после сохранения: `setup.refresh()` → `settings.refreshProviders()`. Обратный порядок допустим, но статусы в панели важнее и обновляются первыми.
- Ключ не попадает ни в `localStorage` (там только `provider`/`model`, `useSettings.ts:27-32`), ни в логи, ни в `title`/`aria-*`.
