# CATALOG-79 — API воркспейсов: блокировка при активных ранах (UI пикера)

- **Задача Plane:** [CATALOG-79](https://app.plane.so/belchch/projects/catalog-app/work-items/79) (id: `66296bc6-eb90-4e40-a083-769cab0cb81c`, state: In Progress)
- **Статус плана:** Analyzed
- **Тип шага:** ui
- **Очередь:** 01 · предусловие: 00 (code того же тикета)
- **Цель:** В `WorkspacePicker` показывать запрет на переключение воркспейса **до** выбора папки: баннер с причиной («идёт выполнение скилла» / «активна сессия») и disabled на всех кнопках открытия, включая карточки «Недавние». Обзор дерева при этом остаётся рабочим. 409 от `open` сохраняется как страховка на гонку.

## Постановка задачи (актуальное ТЗ)
_(источник: последний комментарий от 2026-08-14 21:24 UTC — UI-часть; backend-часть вынесена в парный план)_

> пользователь говорит: ни какие операции не привели к блокировке ui

Проблема (UI): блокировка существует только как 409 на `POST /workspaces/open`. Пользователь узнаёт о запрете после того, как прошёл дерево, выбрал папку и нажал «Открыть». В UI нет способа узнать про блокировку заранее.

Что нужно сделать (UI):

- В `WorkspacePicker` при `busy: true` — баннер с объяснением («идёт выполнение скилла / активна сессия, переключение воркспейса недоступно») и disabled на кнопке открытия, включая клик по недавним. Дерево и обзор остаются работоспособными: смотреть можно, переключиться — нет.
- 409 от `open` оставить как страховку на гонку и показывать текст из `detail`.

Источник данных — новый readonly-эндпоинт `GET /workspaces/busy` → `{ busy: bool, reason: "run" | "session" | null }`. Эндпоинт не требует открытого воркспейса: при `current is None` отдаёт `busy: false`.

Границы: **не** блокируем обзор ФС (`GET /fs/browse`), ре-скан, работу с документами, чат, запуск второго рана. Повторный `open` той же самой папки блокировать не нужно.

Приёмка (UI-часть):

- В пикере при `busy: true` кнопка открытия недоступна и причина видна до выбора папки.

## Контекст
- Модалка целиком в `frontend/src/components/WorkspacePicker.tsx`. Кнопки, которые должны уходить в disabled при `busy`: «Открыть» у карточки недавних (`:190-210`, обработчик `tryOpen(ws.path, false)` на `:194`), «Открыть эту папку» (`:235-242`), «Открыть» в строке списка (`:271-278`), а также кнопки подтверждения внутри pending-панели (`:293-300`, `:311-318`).
- Навигация по дереву — `goInto` (`:144`), `goUp` (`:152`) и кнопка «Вверх» (`:227-234`): их блокировать нельзя, только `submitting` как сейчас.
- 409 уже обрабатывается: `tryOpen` (`:132-138`) при `ApiError` со `status === 409` вызывает `onBusyConflict(e.detail)` и кладёт `{ kind: 'error', detail }` в `pending`. Эту ветку сохранить как страховку на гонку.
- Данные о воркспейсе живут в `frontend/src/hooks/useWorkspace.ts`: там уже есть флаг `busy` (`:32`, `:76`, `:99`), но это **другой** `busy` — «идёт мой собственный запрос open/rescan». Новый серверный статус занятости нельзя смешивать с ним: нужно отдельное поле (например `blocked` / `busyReason`), иначе disabled начнёт срабатывать на собственных запросах.
- HTTP-клиент — `frontend/src/api.ts` (`openWorkspace`, `listWorkspaces`, `browseFs`, `rescanWorkspace` импортируются в `useWorkspace.ts:3-11`); туда добавляется вызов `GET /workspaces/busy`.
- Пикер монтируется из `frontend/src/App.tsx:823` (`WorkspacePicker`), открывается через `openPicker` (`App.tsx:167`), пропсы включают `recents`, `browse`, `open`, `onOpened`, `onClose`, `onBusyConflict`.
- **Предусловие:** парный backend-план `00-CATALOG-79-code-workspace-busy-api.md` — без `GET /workspaces/busy` этот шаг реализовать нечем. Выполнять строго после него.

## План действий
1. В `frontend/src/api.ts` добавить тип ответа `{ busy: boolean; reason: 'run' | 'session' | null }` и функцию `getWorkspaceBusy()`.
2. В `frontend/src/hooks/useWorkspace.ts` добавить состояние занятости, не пересекающееся с текущим `busy` (`:32`) — например `blocked` + `blockedReason` + `refreshBlocked()`. Ошибку запроса трактовать как «не заблокировано», чтобы недоступность эндпоинта не запирала пикер.
3. Обновлять статус при открытии пикера (`App.tsx:167` `openPicker`) и после завершения рана/стрима — переиспользовать существующие точки: эффект завершения рана (`App.tsx:257-265`) и завершения стрима (`App.tsx:268-273`).
4. В `WorkspacePicker` принять статус пропом и отрисовать баннер с текстом причины — размещение и тон по дизайн-спеке; текст различает `run` и `session`.
5. Проставить `disabled` на кнопки открытия: карточки недавних (`:190-210`), «Открыть эту папку» (`:235-242`), «Открыть» в строке (`:271-278`), кнопки подтверждения pending (`:293-300`, `:311-318`). Кнопку «Вверх» (`:227-234`), клик по имени папки (`goInto`, `:258-270`) и «Закрыть» (`:170-179`) оставить рабочими.
6. Сохранить ветку 409 в `tryOpen` (`:132-138`): при гонке показывать `detail` в pending-панели и обновлять статус занятости.
7. Прогнать из `frontend/`: `pnpm run build`, `pnpm run lint`, `pnpm run typecheck`.
