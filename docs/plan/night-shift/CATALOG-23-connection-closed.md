# CATALOG-23 — Ошибка в чате: «соединение закрыто»

- **Plane:** CATALOG-23 (модуль: Баги) — [Todo → In Progress]
- **Тип шага:** ui
- **Симптом:** Пользователь видит «Соединение закрыто» в чате. Гипотеза автора задачи: возникает, когда истекла сессия.
- **Ограничение из постановки:** «Исправить только если проблема чётко определена. Если не понятно — просто закрыть».

## Механизм вывода сообщения

- `usePlannerSession.ts:108-110`: `onClose` → `setClosed(true)`.
- `Chat.tsx:52`: `{closed && <div>…Соединение закрыто</div>}`.
- `closed` не сбрасывается в `false`, пока не сменится `sessionId` (connect-эффект сбрасывает его, `usePlannerSession.ts:95`).

То есть сообщение показывается при **любом** закрытии WS без предшествующего `finish`. Причины закрытия могут быть разными — задача требует сначала **чётко определить** причину.

## Кандидаты-причины (требуют воспроизведения)

1. **Idle/таймаут соединения.** Сервер держит WS в `while True: await websocket.receive_text()` (`sessions.py:86`) без ping/keepalive. При простое посредник (uvicorn/прокси/браузер) может закрыть соединение → `onclose` без `finish`.
2. **Исключение на сервере.** `sessions.py:143-145`: при ошибке шлёт `{"type":"error", ...}` и затем закрывает сокет. Фронт покажет **и** «Ошибка: …», **и** «Соединение закрыто». Если ошибка неинформативна (например, общее исключение LLM-провайдера), пользователь видит «соединение закрыто» как основной симптом.
3. **Перезапуск бэкенда / потеря сети.** Сокет рвётся → `onclose`.
4. **Сессия не найдена.** `sessions.py:80-83`: при подключении к несуществующей сессии шлётся `error` + `close`. Но это крайний случай (id валиден при создании в том же UI).

## Порядок работы (investigate-first)

**Шаг 0 — воспроизведение и диагноз (обязательно до правок):**
1. Открыть новый чат, дождаться появления «соединение закрыто»:
   - при активной работе (после отправки сообщения) — проверить логи бэкенда на исключения (`sessions.py:143`);
   - после длительного простоя (idle) — проверить, разрывает ли соединение сервер/прокси.
2. В логах uvicorn найти момент закрытия WS и причину (исключение vs чистый disconnect).
3. Сформировать однозначный вердикт: причина №1 (idle), №2 (ошибка) или «не воспроизводится».

**Шаг 1 — решение по вердикту:**

- **Если причина №2 (ошибка на сервере):** сделать сообщение понятным — различать «системная ошибка» и «закрытие». Не показывать «соединение закрыто», когда уже показали `error`. Минимум: в `Chat.tsx`/`usePlannerSession` не ставить `closed=true`, если перед `onclose` пришёл `error` (флаг `hadError`). Плюс: в `sessions.py` уточнить сообщение об ошибке (группировка известных кейсов: провайдер недоступен, модель 403/таймаут).
- **Если причина №1 (idle):** добавить серверный ping (FastAPI `WebSocket` + periodic `send_json({"type":"ping"})`) либо сообщение «сессия неактивна, отправьте сообщение ещё раз / начните новый чат» вместо пугающего «соединение закрыто». Для среза — достаточно корректного текста + кнопки «Начать новый чат».
- **Если не воспроизводится / причина неясна:** согласно постановке — **закрыть задачу** (Cancelled) с комментарием о результатах воспроизведения; не плодить правки наугад.

## Возможные правки (после подтверждения причины)

- **`frontend/src/hooks/usePlannerSession.ts`:** ввести `hadErrorRef`; в `onClose` ставить `closed=true` только если не было `error`. Иначе оставить «Ошибка: …» как единственный сигнал.
- **`frontend/src/components/Chat.tsx`:** текст «Соединение закрыто» → более понятный («Сессия неактивна. Начните новый чат.») + (опц.) кнопка перезапуска сессии.
- **`backend/app/api/sessions.py`:** (если idle) — periodic ping; (если ошибки) — группировка сообщений об ошибках.

## Риски / заметки
- Главная ценность шага — **диагноз**, а не правка. Без воспроизведения фиксить нельзя (риск сломать рабочий стрим).
- Не вводить полноценный reconect-механизм в этом срезе (вне скоупа); ограничиться понятным UX/текстом или ping.
- Если корнем окажется истечение сессии на уровне БД — проверить `repo_session` (нет ли TTL/удаления). На текущей схеме `session` не имеет expiry — значит «истечение» скорее всего = закрытие WS, а не удаление данных.
