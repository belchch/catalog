# CATALOG-129 — Дизайн UI

- **Источник:** `docs/plan/1-shift/08-CATALOG-129-ui-trace-limiter.md`
- **Статус дизайна:** Ready

## Цель и пользовательский путь

Пользователь смотрит трейс хода планировщика (или трейс запуска скилла) и хочет понять, что происходило с вложенными запусками скиллов: как глубоко ушёл вызов, во сколько LLM-вызовов он обошёлся и почему очередной скилл не сработал.

1. В списке шагов он видит узел вложенного запуска (сделан в CATALOG-119): `⤷ skill_summary … запуск ab12cd34`. Теперь в той же строке — **глубина**.
2. Раскрывает узел. Заголовок дополняется **фактической ценой** запуска в LLM-вызовах (`3 LLM-вызова` / `без LLM-вызовов`), внутри — прежний трейс.
3. Если ход упёрся в ограничитель, вместо безликого «скилл вернул ошибку» стоит отдельный узел с заголовком-объяснением: бюджет вызовов / лимит запусков / время хода / скилл не предлагался. Там же — **остаток бюджета хода** (единственное место, где бэкенд его записывает).
4. Если модель попробовала вызвать скилл, которого в этом запуске не было (глубина или цикл в цепочке), она видит приглушённую пометку, а не красную ошибку.

Скоуп — ровно это. Новых экранов, кнопок, фильтров и запросов к API нет; узел ограничителя не делает своих fetch'ей, кроме уже существующего ленивого `getRun` внутри вложенного узла.

### Что уже есть в данных (ничего не выдумываем)

Всё ниже — уже записанные поля из CATALOG-124…127.

| Что показываем | Откуда берём |
|----------------|--------------|
| Глубина | `depth` в payload скилл-тула (`tool_result`), сразу, до загрузки дочернего запуска. Резерв: запись `skill_pin` в трейсе дочернего запуска (`data.depth`). |
| Фактическая цена | Число записей `kind === 'llm'` в трейсе дочернего запуска (`getRun(runId).trace`) — по одной на итерацию, включая шаги pipeline. Известна только после раскрытия узла. |
| Остаток бюджета хода | `budget.llm_calls_left` / `budget.nested_runs_left` в payload отказа `budget exhausted`. |
| Сколько требовалось | `budget.needed_llm_calls` / `budget.needed_nested_runs` там же. |
| Причина ограничителя | `error`: `budget exhausted` / `deadline exceeded`; плюс `ok === false` + `error: unknown tool 'skill_…'` для скилла, которого не было в реестре. |

**Осознанное ограничение:** на успешном запуске остатка бюджета в данных нет — бэкенд пишет остаток только в отказе. Поэтому остаток показываем в узле ограничителя, а на успешном узле — только цену. Никакой арифметики «оценка минус потраченное» во фронте: лимиты хода в API не отдаются, а угаданный остаток хуже отсутствующего.

### Разбор payload — контракт

`result` приходит в двух видах: по WS это **строка** (JSON, обрезанный до 400 символов с хвостом `…[truncated]`), в сохранённом трейсе — **объект**. Отсюда:

```
parseSkillToolResult(result: unknown): SkillToolResultInfo | null
  объект                     → читаем поля напрямую
  строка → JSON.parse ок     → читаем поля напрямую
  строка → JSON.parse упал   → regex по началу строки: "depth":N, "error":"…"
  иначе                      → null
```

- Ключ `depth` в успешном payload стоит **до** длинного `text`, поэтому в обрезанной строке он остаётся — как и `run_id`, который так же добирает `extractChildRunId`. Логику regex-резерва копируем оттуда, а не изобретаем.
- Payload отказов короткий (< 400 символов), так что для ограничителей `JSON.parse` работает; ветка «числа неизвестны» — только страховка, и она обязана деградировать текстом без чисел, а не пустым узлом.

### Четыре причины — детекция и приоритет

```
limiterReason(step): LimiterReason | null
  error === 'deadline exceeded'                              → 'deadline'
  error === 'budget exhausted' && runs_left < needed_runs     → 'nested_runs'
  error === 'budget exhausted'                                → 'llm_budget'
  ok === false && toolName.startsWith('skill_')
        && /unknown tool/ в результате                        → 'unavailable'
  иначе                                                       → null
```

- `nested_runs` проверяем раньше `llm_budget`: лимит запусков за ход не возвращается (в отличие от неизрасходованных LLM-вызовов), это жёсткий потолок хода, и он важнее для объяснения.
- Прочие `ok: false` (`provide text or texts`, исключение внутри скилла) ограничителями **не** считаются и рендерятся как сейчас — обычной строкой `tool_result`. Ограничитель — это остановка по правилу, не поломка.

## Layout и состояния

### Узел вложенного запуска (`TraceRunNode`)

Заголовок остаётся однострочным flex-рядом; имя тула по-прежнему `min-w-0 truncate`, всё новое уходит в правый кластер фиксированного порядка:

```
[ ⤷  skill_summary                    ✓ · глубина 2 · 3 LLM-вызова · запуск ab12cd34 ]
```

| Поле | Когда есть |
|------|-----------|
| `глубина N` | Как только известен `depth` из payload (до раскрытия) либо `skill_pin` после загрузки. Нет данных — блока нет. |
| `N LLM-вызовов` | Только после загрузки дочернего запуска. `0` записей `llm` → `без LLM-вызовов` (это факт про script-скилл, а не отсутствие данных). |
| `запуск xxxxxxxx` | Как сейчас. |

Цена появляется при раскрытии — заголовок дорастает вправо. Это допустимо: правый кластер `shrink-0`, имя тула усекается, строка не переносится. Ставить цену в подпись тела вместо заголовка не стали — план требует её в заголовке, где она сравнима между узлами.

Состояния тела узла (`loading` / `notFound` / `error` + «Повторить» / `inFlight` + «Обновить» / `failed`) не меняются.

### Узел ограничителя (`TraceLimiterNode`)

Отдельный узел `<li>` на месте пары `tool_call` + `tool_result`. Не `details` — весь смысл виден сразу:

```
┌─────────────────────────────────────────────────────────────┐
│ ⚠ Бюджет LLM-вызовов на ход исчерпан                        │
│ Скиллу «Сводка» нужно до 24 вызовов, а на ход осталось 6.    │
│ Запуск не начинался.                                        │
│ Остаток хода: 6 LLM-вызовов · 4 вложенных запуска · глубина 2│
│ ⤷ skill_summary            ✗ · запуск 7c1f0ab2   (свёрнут)   │
└─────────────────────────────────────────────────────────────┘
```

- Первая строка — заголовок причины, вторая — объяснение, третья (`text-ink-muted`) — остаток и глубина, если известны.
- Если в payload есть `run_id`, снизу вкладываем существующий `TraceRunNode` (свёрнутый, `ok={false}`) — чтобы не потерять трейс: при истечении дедлайна **после** отработавшего запуска там лежит реальная работа, а не заглушка.
- Синтетический запуск отказа содержит одну запись `budget` / `deadline`. Сейчас `runTraceToSteps` рендерит её как слово `budget` — правим мапинг на человеческий текст: `Ограничитель: бюджет хода исчерпан · осталось 6 вызовов, 4 запуска`, `Ограничитель: время хода вышло`. Тот же мапинг закрывает запись `deadline`, которую runner пишет **внутри** живого вложенного запуска между итерациями.

### Тон узла: два вида

| Причина | Фон / текст | Глиф | Почему |
|---------|-------------|------|--------|
| `llm_budget`, `nested_runs`, `deadline` | `bg-warning-soft` · `text-warning-ink` · `border-warning-line` | `⚠` | Работа остановлена правилом. Не `danger`: скилл не падал, ход жив, модель получила ответ. |
| `unavailable` | `bg-surface-muted` · `text-ink-muted` · `border-line` | `–` | «Инструмента не предлагали» — справка, а не событие. План прямо просит приглушённую пометку. |

Все три токена warning уже есть в `frontend/tailwind.config.cjs` (`warning.soft/ink/line` → `--warning-*`), новых переменных заводить не нужно.

### Тексты (единственный источник формулировок)

| Причина | Заголовок | Объяснение |
|---------|-----------|------------|
| `llm_budget` | Бюджет LLM-вызовов на ход исчерпан | Скиллу «{имя}» нужно до {needed} {вызов/вызова/вызовов}, а на ход осталось {left}. Запуск не начинался. |
| `llm_budget`, чисел нет | Бюджет LLM-вызовов на ход исчерпан | Скилл «{имя}» не запускался: на ход не осталось LLM-вызовов. |
| `nested_runs` | Лимит вложенных запусков на ход исчерпан | Ход уже израсходовал все вложенные запуски скиллов. Скилл «{имя}» не запускался. |
| `deadline` | Время хода вышло | Ход шёл слишком долго, поэтому новые запуски скиллов остановлены. |
| `unavailable` | Скилл не предлагался модели | Инструмента «{tool}» в этом запуске не было: на такой глубине вложенные скиллы не подключаются либо скилл уже есть в текущей цепочке вызовов. |

- Третья строка (только когда числа есть): `Остаток хода: {llm} {вызов/вызова/вызовов} · {runs} {запуск/запуска/запусков}`; глубина добавляется как ` · глубина {n}`.
- Имя скилла — `skill_name` из payload; нет его — имя тула. Кодов ошибок (`budget exhausted`, `deadline exceeded`, `unknown tool`) в видимом тексте быть не должно ни в одном узле.
- Множественные формы обязательны и вынесены в `pluralRu(n, ['вызов','вызова','вызовов'])`; логика — та же, что в существующем `eventCountLabel` (его вывод менять нельзя).

### Одиночная строка `tool_result`

На вложенных уровнях (`nodeList` при `depth > 0`) запуски в узлы не сворачиваются — это поведение CATALOG-119 и мы его не трогаем. Чтобы глубина всё равно была видна, к такой строке добавляем приглушённый суффикс: `← skill_summary ✓ · глубина 2`. Узлы ограничителя, наоборот, сворачиваем **на всех уровнях**: `unavailable` возникает как раз внутри вложенного запуска, где реестр урезан, и там он нужнее всего. Практически: `foldNestedRuns(items, { foldRuns })` — `foldRuns` берётся из UI-глубины, фолдинг ограничителей всегда включён.

## Взаимодействия

- **Раскрытие узла запуска**: как сейчас — первый `open` вызывает `getRun`, повторные переключения не перезапрашивают. После загрузки в заголовке появляется цена.
- **Узел ограничителя**: сам ничего не грузит и не сворачивается. Вложенный в него узел запуска раскрывается по клику/Enter как обычно.
- **Живой стрим против сохранённого трейса**: узел ограничителя должен выглядеть одинаково в обоих случаях. Единственное отличие — обрезанный payload по WS; поля, которых не хватило, просто не рендерим.
- **Крайние случаи**:
  - `depth` отсутствует (старый трейс, обрезанный payload без совпадения) → блок глубины не выводим, «глубина —» не пишем.
  - Дочерний запуск ещё выполняется → цену не показываем (трейс неполный), «глубина» остаётся.
  - `run_id` в отказе отсутствует → узел ограничителя без вложенного узла запуска.
  - Оба лимита исчерпаны одновременно → показываем `nested_runs`, второй причиной строку не дублируем.
  - `unknown tool` для не-`skill_*` тула → обычная строка ошибки, ограничителем не считаем.

## Стиль и токены

- Только токены и примитивы `docs/ui-style-guide.md`: `bg-warning-soft`, `text-warning-ink`, `bg-surface-muted`, `text-ink-muted`, `text-ink-faint`, `border-line`. Сырые палитры (`amber-*`, `red-*`, …) запрещены.
- Узел ограничителя повторяет геометрию соседей по дереву: `rounded border p-1.5`, `font-mono text-[11px]`, вертикальные зазоры `gap-1.5`. Никаких карточек `rounded-card`/`shadow-card` — это не карточка, а элемент плотного списка.
- Новые части заголовка живут в существующем правом кластере `text-ink-faint`; цена и глубина **не** красятся в акцент — иначе они перетянут внимание с глифа статуса.
- Глифы (`⚠`, `–`, `⤷`, `✓`, `✗`) — текстовые, как во всём дереве; иконочных зависимостей не добавляем.

## Доступность (a11y)

- Глифы — `aria-hidden="true"`, смысл дублируется словом: `sr-only` «ограничитель» для трёх жёстких причин и «пометка» для `unavailable`. Заголовок причины — обычный видимый текст, скринридер читает его как есть.
- Узел ограничителя не `role="alert"` и не `aria-live`: он приезжает в потоке шагов вместе с остальными и не должен перебивать чтение. Разметка — `<li>` с обычными `<p>`.
- Новые поля заголовка запуска — видимый текст внутри существующего `<summary>`, отдельных `aria-label` не добавляем; `sr-only`-слово статуса (`ок`/`ошибка`/`выполняется`) остаётся последним в summary.
- Интерактив прежний: `<summary>` фокусируется с клавиатуры, кольцо `ring-2 ring-brand` не трогаем. Новых табстопов узел ограничителя не вносит (кроме вложенного `<summary>`, если запуск есть).
- Контраст: `text-warning-ink` на `bg-warning-soft` и `text-ink-muted` на `bg-surface-muted` — штатные пары style guide, самодельных полупрозрачностей не вводим.

## Контракты данных

Всё уже существует, новых эндпоинтов и WS-кадров не появляется.

- `tool_result` (WS `frontend/src/ws.ts` и запись трейса): payload скилл-тула — `{ok, status, run_id, skill_id, skill_name, config_hash, depth, verify_failures, text}`; отказ бюджета — `{ok: false, error: "budget exhausted", budget: {llm_calls_left, nested_runs_left, needed_llm_calls, needed_nested_runs}, …, depth, run_id}`; отказ дедлайна — то же без `budget` и с `error: "deadline exceeded"` (`backend/catalog/skills/skill_tools.py`).
- `GET /runs/{id}` → `trace`: записи `skill_pin` (`depth`), `llm` (по одной на итерацию), `budget`, `deadline` (`backend/catalog/skills/apply.py`, `backend/catalog/agent/runner.py`).
- По WS `result` всегда строка и обрезана до 400 символов (`_snip_result` в `backend/catalog/api/deps.py`); в сохранённом трейсе — полный объект. Разбор обязан переваривать оба вида.
- Лимиты хода (`skill_budget_llm_calls`, `skill_budget_nested_runs`, `max_skill_depth`) наружу не отдаются — фронт на них не опирается и «сколько всего было» не показывает.

## Критерии визуальной приёмки

- [ ] В заголовке узла вложенного запуска видно `глубина N` — до раскрытия, из payload `tool_result`.
- [ ] После раскрытия в заголовке появляется фактическая цена: `3 LLM-вызова` при трёх записях `llm`, `1 LLM-вызов` при одной, `без LLM-вызовов` при нуле.
- [ ] Цена не показывается, пока дочерний запуск не загружен или ещё выполняется; заголовок при этом не ломается и не переносится.
- [ ] Отказ по бюджету LLM даёт узел с заголовком «Бюджет LLM-вызовов на ход исчерпан», числом нужных вызовов и остатком хода.
- [ ] Отказ по лимиту запусков даёт заголовок «Лимит вложенных запусков на ход исчерпан»; при одновременном исчерпании обоих лимитов показана именно эта причина.
- [ ] Истечение дедлайна даёт заголовок «Время хода вышло».
- [ ] Попытка вызвать скилл, которого не было в реестре, даёт приглушённую пометку «Скилл не предлагался модели» с упоминанием глубины/цепочки — в `surface-muted`/`ink-muted`, без `danger`.
- [ ] Ни в одном узле нет строк `budget exhausted`, `deadline exceeded`, `unknown tool` и слова `budget` как заголовка шага.
- [ ] Узел ограничителя не показывает парную строку `→ skill_…({…})` над собой (пара `tool_call` + `tool_result` свёрнута) и появляется в том числе внутри вложенного запуска.
- [ ] Когда в отказе есть `run_id`, внутри узла ограничителя доступен свёрнутый узел запуска; после дедлайна на отработавшем запуске его трейс раскрывается.
- [ ] Строка `tool_result` на вложенном уровне показывает суффикс `· глубина N`, когда `depth` есть.
- [ ] Дерево CATALOG-119 без регрессии: успешные вложенные запуски по-прежнему сворачиваются в узлы на верхнем уровне, ленивый `getRun` срабатывает один раз, состояния «Загружаю запуск…», «Запуск не найден», «Повторить», «Обновить» на месте.
- [ ] Обрезанный по WS payload не ломает узлы: глубина видна, отсутствующие числа просто не выводятся, пустых плейсхолдеров нет.
- [ ] В диффе `frontend/src` только токены style guide — ни сырых палитр Tailwind, ни новых кастомных цветов, ни иконочных зависимостей.
