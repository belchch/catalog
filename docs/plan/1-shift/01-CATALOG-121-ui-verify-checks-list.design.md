# CATALOG-121 — Дизайн UI

- **Источник:** `docs/plan/1-shift/01-CATALOG-121-ui-verify-checks-list.md`
- **Статус дизайна:** Ready

## Цель и пользовательский путь

Сегодня verify в трейсе — это чёрный ящик: строка `Проверка (итерация 1)` зелёная или красная, и при провале — склейка причин через `; `. Что именно прогонялось и что прошло — не видно.

После среза verify-шаг отвечает на три вопроса сразу: **сколько проверок прошло из скольких**, **какие именно упали и почему**, **какие не запускались**.

Сценарий (живой прогон, `RunView`):

1. Идёт прогон, в ленте появляется строка `› Проверка (итерация 1)`.
2. Под ней — свёртка со сводкой: `✓ 3 из 4 · пропущено 1`. Прогон прошёл — свёртка закрыта, лента не раздувается.
3. Проверки упали — свёртка **раскрыта сразу** (причины не должны требовать клика, как и сегодня), внутри список: зелёные пройденные, красные упавшие с причиной, приглушённые пропущенные с пометкой «пропущена».
4. Ретрай — следующая итерация даёт свой verify-шаг со своим списком; сравнить попытки можно, прокрутив ленту.

Сценарий (сохранённый запуск): открытие запуска из истории (`runTraceToSteps`) даёт ровно тот же список — данные лежат в трейсе.

Сценарий (вложенный запуск, `TraceRunNode`): в раскрытом узле строка «✓ проверки пройдены» превращается в свёртку `✓ проверки: 3 из 4` с тем же списком.

Старый трейс без `checks` — рендер сегодняшний, без свёртки и без «N из M».

## Дерево компонентов и файлы

Новых файлов нет; новых зависимостей нет.

**`frontend/src/ws.ts`** — тип исхода проверки (единственное место объявления, его импортируют остальные):

```ts
export interface VerifyCheckOutcome {
  check: string
  params: Record<string, unknown>
  passed: boolean
  reason: string | null
  source: string
  skipped: boolean
}
```

и поле в WS-кадре: `{ type: 'verify'; iteration: number; passed: boolean; failures: string[]; checks?: VerifyCheckOutcome[]; step_id?: string }`.

`source` — строка, а не union: значения приходят с бэкенда (`builtin` / `custom`), UI сравнивает только с `'custom'` и не должен ломаться на новом значении.

**`frontend/src/lib/traceSegments.ts`** — две чистые функции (тестируются в `TraceSteps.test.ts`):

- `toCheckOutcomes(raw: unknown): VerifyCheckOutcome[] | undefined` — защитный разбор. Не массив, пустой массив, массив без валидных объектов → `undefined`. Валидная запись: объект с непустой строкой `check`. Нормализация полей: `params` — объект или `{}`; `passed` — `raw.passed === true`; `reason` — строка или `null`; `source` — строка или `'builtin'`; `skipped` — `raw.skipped === true`. Записи-мусор внутри массива пропускаются, порядок остальных сохраняется (порядок = порядок `verify_checks` в конфиге скилла).
- `formatCheckParams(params: Record<string, unknown>): string` — компактная подпись параметров: пары `key=value` (значение через `String`, объекты/массивы — через `formatToolArgs`) через `, `. Пусто → `''`. Длиннее 80 символов (`pattern`, `schema`) — обрезка с `…`; полная строка уходит в `title`.

`runTraceToSteps`, ветка `kind === 'verify'`: `checks: toCheckOutcomes(data.checks)`.

**`frontend/src/hooks/useRunStream.ts`** — `RunStep` получает `checks?: VerifyCheckOutcome[]`; в `case 'verify'` заполняется тем же `toCheckOutcomes(e.checks)` (один путь нормализации для стрима и трейса — иначе тесты живого и сохранённого рендера расходятся).

**`frontend/src/components/TraceSteps.tsx`**:

- `VerifyChecksSummary` — новый локальный компонент (не экспортируется), props: `{ checks: VerifyCheckOutcome[]; passed: boolean; label?: string }`. Рисует `<details>` со сводкой и списком строк. Один компонент на оба места: шаг ленты и узел вложенного запуска — иначе два рендера разъедутся.
- `TraceItem`, ветка `s.kind === 'verify'`: есть `s.checks?.length` → `<VerifyChecksSummary checks={s.checks} passed={s.passed === true} />`; иначе прежний блок `failures.join('; ')` при `passed === false`.
- `lastVerifyChecks(run: RunOut): VerifyCheckOutcome[] | undefined` — локальный хелпер рядом с `verifyFailuresOf`: идёт по `run.trace`, берёт **последнюю** запись `kind === 'verify'`, у которой `toCheckOutcomes(data.checks)` не `undefined`. Именно последнюю: при ретраях записей несколько, а сводка узла должна показывать итоговую попытку — промежуточные видны в списке шагов ниже.
- `TraceRunNode`, блок «проверки» (сейчас две `<p>` на строках 394–399): есть `lastVerifyChecks(run)` → `<VerifyChecksSummary checks={…} passed={failures.length === 0} label="проверки: " />`; иначе прежние две строки. Danger-блок «запуск завершился с ошибкой» выше по разметке не трогаем — он про статус запуска, а не про проверки.

**Тесты**

- `frontend/src/components/TraceSteps.test.ts` — `toCheckOutcomes` (валидный список; `undefined` на `undefined`/`[]`/строке/массиве мусора; нормализация дефолтов), `formatCheckParams` (пусто, пара ключей, обрезка), `runTraceToSteps` (verify c `checks` и verify без `checks` → `checks: undefined`).
- `frontend/src/components/TraceRunNode.test.tsx` — рендер: сводка `✓ 3 из 4`, раскрытый список при провале с причиной, строка `пропущена`, узел со сводкой `проверки: N из M`, и трейс без `checks` → старый текст «✓ проверки пройдены» / список failures.

## Layout и состояния

Всё живёт в существующей типографике ленты: `font-mono text-[11px]`. Новых карточек и рамок нет — список это вложенный уровень внутри строки шага.

Шаг ленты (`TraceItem`, verify с `checks`):

```
› Проверка (итерация 1)
   ✓ 3 из 4 · пропущено 1
     ✓ non_empty
     ✓ has_section · heading=Тезисы
     ✗ min_length · min=500 — 320 символов, нужно 500
     – custom:9f3a… · AI · пропущена — не запускалась: детерминированные проверки упали
```

Разметка:

- `<details>` — `className="mt-0.5 block pl-3"` (тот же отступ `pl-3`, что у сегодняшнего блока failures и у `<details>` «код»/«результат»).
- `<summary>` — `cursor-pointer` + тон: `text-success-ink` при `passed`, `text-danger-ink` иначе. Текст: `{glyph} {label ?? ''}{N} из {M}` и, если пропущенных `k > 0`, суффикс ` · пропущено {k}`. Глиф `✓` / `✗` — `aria-hidden`.
- `<ul className="mt-0.5 flex flex-col gap-0.5 pl-3">` — список строк, `key = ${check}-${index}` (одна и та же проверка может повторяться с разными params).
- Строка — `<li className="flex items-baseline gap-1">`: глиф `shrink-0` + `<span className="min-w-0 break-words">` с содержимым. Причина не обрезается (это главное, что читает пользователь), длинные строки переносятся.

Счётчики: `M = checks.length`, `N = checks.filter(c => c.passed).length`, `k = checks.filter(c => c.skipped).length`. Пропущенная приходит с `passed: false` и в `N` не попадает — «3 из 4» честно означает «прошли три».

Тона строк:

| Исход | Глиф | Класс строки | Содержимое |
|---|---|---|---|
| `passed` | `✓` | `text-success-ink` | `{check}` + ` · {params}` |
| `!passed && !skipped` | `✗` | `text-danger-ink` | `{check}` + ` · {params}` + ` — {reason}` |
| `skipped` | `–` | `text-ink-faint` | `{check}` + ` · {params}` + ` · пропущена` + ` — {reason}` |

Дополнительно: при `source === 'custom'` после имени проверки — ` · AI` в `text-ink-faint` (LLM-судья против детерминированной проверки — разная цена доверия). Отдельный `badge-accent` не заводим: в моно-ленте бейдж ломает ритм строки.

Идентификатор проверки печатается как есть (`non_empty`, `has_section`) — лента техническая, человекочитаемые лейблы из `/verify-checks` сюда не тянем: это лишний сетевой запрос на каждый трейс. Исключение — длинный `custom:<uuid>`: показываем `custom:{id.slice(0, 8)}…` с полным id в `title` (как `запуск {runId.slice(0, 8)}` рядом).

Состояния блока:

| Состояние | Что показываем |
|---|---|
| `checks` есть, `passed === true` | свёртка закрыта, сводка `✓ N из M` в success-тоне |
| `checks` есть, `passed === false` | свёртка **открыта**, сводка `✗ N из M` в danger-тоне, внутри причины |
| `checks` отсутствует / пустой массив (старый трейс, старый бэкенд) | рендер как сегодня: при `passed === false` — `failures.join('; ')` в `text-danger-ink`; при `passed === true` — ничего |
| `checks` есть, но `failures` пуст, а среди `checks` есть упавшие | доверяем `passed` шага для тона и глифа; список рисуем как пришёл (рассинхрон бэкенда не должен ронять рендер) |
| Узел вложенного запуска, `verify`-записей нет | блока проверок нет — как сегодня |

Первое раскрытие/сворачивание пользователем ничего не догружает: данные уже в `RunStep`.

## Взаимодействия

- **Раскрытие/сворачивание** — нативный `<details>`, состояние по умолчанию задаётся атрибутом `open={!passed}`. Значение стабильно на всё время жизни шага (`passed` у завершённой verify-записи не меняется), поэтому React не перетирает ручной тогл пользователя. Хранить open в state не нужно — лишний ререндер ленты.
- **Живой стрим** — каждая verify-запись приходит один раз и добавляется как новый шаг; уже отрисованные свёртки не перерисовываются и не схлопываются при появлении следующих шагов.
- **Ретраи** — на каждую итерацию своя строка `Проверка (итерация N)` со своей свёрткой; агрегата «по всем итерациям» не делаем.
- **Узел вложенного запуска** — сводка появляется после загрузки `GET /runs/{id}` вместе с остальным содержимым узла; при повторном сворачивании узла ничего не перезапрашивается (поведение узла из CATALOG-119 не меняется).
- **Крайние случаи.**
  - Длинная причина (regex, дамп текста) — перенос по словам, горизонтальной прокрутки в ленте не появляется.
  - Длинные `params` (`pattern`, `schema`) — обрезка на 80 символах с `…`, полная строка в `title`.
  - Один и тот же `check` с разными `params` (`has_section` × 3) — три отдельные строки, ключ по индексу.
  - `checks` пришли, а `reason` у упавшей пустой — рисуем строку без хвоста `— …`; красный глиф остаётся.
  - Все проверки пропущены (`0 из 3 · пропущено 3`) — валидное состояние, свёртка открыта, строки приглушённые.
  - Глубина > 1 — на список это не влияет: он живёт внутри строки шага, а не внутри узла запуска.

## Стиль и токены

- Только семантические утилиты из `docs/ui-style-guide.md`: `text-success-ink`, `text-danger-ink`, `text-ink-faint`, `text-ink-muted`. Сырые палитры (`green-*`, `red-*`, `slate-*`) запрещены.
- Заливок (`bg-success-soft` / `bg-danger-soft`) в списке нет: цветные плашки на каждую проверку превратят ленту в светофор. Заливка остаётся только у существующих блоков ошибок (`ScriptStep.error`, danger-блок узла).
- Типографика неизменна: `font-mono text-[11px]`, вложенность через `pl-3`, зазоры `gap-0.5` внутри списка (плотнее, чем `gap-1.5` между шагами — это подуровень одного шага).
- Глифы текстовые (`✓ ✗ –`), как во всей ленте; в `icons.tsx` ничего не добавляем.
- Новых классов в `index.css` / `@layer components` не заводим.

## Доступность (a11y)

- Свёртка — нативные `<details>/<summary>`: клавиатура и скринридер работают без ARIA-костылей (тот же паттерн, что у группы шага и узла запуска).
- Список — `<ul>/<li>`: скринридер объявляет количество проверок.
- Глифы строк и сводки — `aria-hidden="true"`; словесный статус дублируется `<span className="sr-only">` внутри строки: «пройдена» / «не пройдена» / «пропущена». Смысл не передаётся одним цветом ни в одной строке.
- Причина провала — обычный текст в той же строке, читается сразу после статуса.
- `role="alert"` для списка **не** ставим: verify-провал не срочное уведомление, а часть ленты; alert на каждую итерацию ретрая — спам для скринридера.
- Порядок фокуса естественный: `summary` шага → `summary` списка проверок → следующий шаг.

## Контракты данных

- WS-кадр `verify` (`backend/catalog/api/deps.py` → `VerifyResult.as_payload()`): `{ type, iteration, passed, failures, checks, step_id }`, где `checks: [{ check, params, passed, reason, source, skipped }]`.
- `TraceEntry(kind="verify")` (`backend/catalog/skills/apply.py`, три места) — тот же `as_payload()`, поэтому живой стрим и сохранённый трейс структурно совпадают.
- Семантика полей (парный план `00-CATALOG-121-code-verify-check-outcomes.md`): `source` — `builtin` | `custom`; `skipped=true` — проверка не выполнялась (unknown check, custom в синхронном `run_verify`, custom-judge при упавших детерминированных), при этом `passed=false`; `reason` — текст причины или `null`.
- `passed` / `failures` остаются на месте и остаются источником истины для тона и для fallback-рендера. UI **не** пересобирает `failures` из `checks`.
- Запуски, записанные до этого среза, приходят без `checks` — отсюда обязательный fallback-путь.

## Критерии визуальной приёмки

- [ ] У verify-шага с `checks` под строкой шага есть свёртка со сводкой `{✓|✗} N из M` (и ` · пропущено k`, если пропущенные есть).
- [ ] Пройденные проверки видны отдельными строками в `text-success-ink` — не только упавшие.
- [ ] Упавшая проверка — `✗`, `text-danger-ink`, идентификатор + причина в одной строке.
- [ ] Пропущенная — приглушённая строка (`text-ink-faint`) со словом «пропущена».
- [ ] Свёртка открыта по умолчанию при `passed === false` и закрыта при `passed === true`.
- [ ] Сохранённый запуск (через `runTraceToSteps`) даёт тот же список, что живой стрим.
- [ ] В узле вложенного запуска строка «✓ проверки пройдены» заменена на свёртку `{✓|✗} проверки: N из M` с тем же списком.
- [ ] Трейс без `checks` рендерится по-старому: пройденный verify — без списка, упавший — строкой `failures.join('; ')`.
- [ ] `params` показаны компактно (`key=value`), длинные значения обрезаны с `…` и раскрыты в `title`; `custom:<uuid>` укорочен до 8 символов с `title`.
- [ ] Проверка с `source === 'custom'` помечена ` · AI`.
- [ ] Типографика и отступы совпадают с лентой: `font-mono text-[11px]`, вложенность `pl-3`, без новых карточек и заливок.
- [ ] Глифы `aria-hidden`, у каждой строки есть `sr-only`-статус; список — `<ul>/<li>`.
- [ ] В диффе нет сырых палитр Tailwind, новых классов в `index.css`, новых иконок и новых зависимостей.
