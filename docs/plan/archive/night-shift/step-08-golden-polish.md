## Порядок задач

### 1. Золотой прогон (end-to-end, вручную + скрипт)
Реальный `.docx` (положить в `samples/`, не в workspace). Полный путь:
1. Загрузить `samples/<golden>.docx` → документ в списке.
2. В чате спланировать: «выдели ключевые тезисы, оформи markdown с секцией `Тезисы`».
3. «Создать скилл» → агент вызывает `read_document`, выдаёт markdown; шаги стримятся; `verify` (`non_empty` + `markdown_well_formed` + `has_section «Тезисы»`) проходит → результат показан.
4. «Коммит» → скилл в списке.
5. Загрузить второй docx → выбрать скилл → «Применить» → новый результат; в trace видны вызовы инструментов.

Автоматизация: `backend/scripts/golden_run.py` — оркестрирует весь путь через REST/WS-клиент (или прямо через сервисный слой), ассерты:
- документ загрузился (kind=docx);
- скилл создан (status=draft), `allowed_tools ⊆ ["read_document","list_documents"]`, `verify_checks` содержит требуемые;
- после коммита status=committed;
- второй прогон: `SkillRun.status == "ok"`, `output_doc_id` задан, результат содержит `## Тезисы`, в trace есть `tool_call read_document`.

### 2. Полировка failure modes (из верхнего плана)
- **Вечный луп:** проверить `max_iterations` cap → `FinishEvent(capped=True)` доходит до UI; trace сохранён.
- **verify не сходится:** `max_retries` → `status=failed`, результат + ошибки показаны, trace сохранён.
- **Неверные tool-аргументы:** валидация JSON-Schema → ошибка обратно в модель; проверить, что цикл не падает.
- **Переполнение контекста:** минимальная стратегия truncate tool-results (обрезать длинный `read_document`-текст до лимита с пометкой) — реализовать, если проявится.
- **Ошибки провайдера/сети (401/429/таймаут):** корректный статус в UI; retry с backoff на уровне провайдера (если ещё не сделано) или хотя бы понятное сообщение.
- **WS-обрыв:** UI показывает «соединение закрыто», не висит.
