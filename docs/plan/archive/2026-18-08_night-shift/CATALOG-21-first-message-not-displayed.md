# CATALOG-21 — Первый запрос улетает, но не отображается в чате

- **Plane:** CATALOG-21 (модуль: Баги) — [Todo → In Progress]
- **Тип шага:** code
- **Симптом:** Открыли новый чат → ввели сообщение → нажали «Отправить» → в чате ничего не изменилось. Начиная со второго сообщения — чат работает нормально.

## Корневая причина (воспроизводимо)

Гонка инициализации сессии и буфера отправки в `usePlannerSession`. Цепочка:

1. `App.tsx:32` `handleSend` → `await ensureSession()` → `createSession()` резолвится → `setSessionId(id)` (App.tsx:28), затем сразу `planner.send(text)` (App.tsx:36).
2. На момент вызова `planner` в замыкании — это результат хука при `sessionId === null`. `readyRef.current` ещё `false` → `send` (`usePlannerSession.ts:121-133`) кладёт текст в `pendingRef.current` и добавляет user-сообщение в `messages` через `setMessages`.
3. Реакт перерисовывается с новым `sessionId` → срабатывает connect-`useEffect` (`usePlannerSession.ts:91-119`), зависящий от `[sessionId, handleEvent]`. В самом начале эффект делает:
   - `setMessages([])` (строка 93) — **стирает user-сообщение из чата**;
   - `pendingRef.current = []` (строка 98) — **выбрасывает поставленный в буфер текст первого запроса**.
4. К моменту `onOpen` (когда сокет откроется и должен сбросить буфер, строки 102-106) `pendingRef` уже пуст. Первый запрос **не уходит на сервер и не показывается**.
5. Второе сообщение: `sessionId` уже выставлен, `ensureSession` возвращает его сразу, WS уже открыт → `send` шлёт напрямую. Работает.

Итог: первый запрос теряется полностью (ни отправки, ни отображения); пользователь видит «отправил, но ничего не произошло».

## Решение

Сделать отправку первого сообщения устойчивой к асинхронной инициализации сессии. Два равноценных варианта; принять **вариант A** (минимальный, в одном хуке):

### Вариант A (рекомендуемый) — не чистить буфер/сообщения при первом подключении
В `usePlannerSession.ts` connect-эффект:
- Не обнулять `pendingRef.current` при старте эффекта. Сбрасывать буфер **только в `onOpen` после фактической отправки** (что уже сделано в строках 103-107). Иными словами: удалить строку `pendingRef.current = []` из тела эффекта (98) — буфер должен дожить до `onOpen`.
- Не звать `setMessages([])` безусловно. Чистить историю только когда `sessionId` реально сменился (сравнить с предыдущим значением через `ref`), а не при каждом перевешивании замыкания `handleEvent`.
- Усилить `send`: если WS ещё не открыт, всегда ставить в `pendingRef` (уже так) — но убедиться, что `onOpen` корректно флешит всё накопленное.

### Вариант B (более явный) — дожидаться открытого сокета перед первым send
В `App.tsx` `handleSend` не звать `planner.send` сразу после `ensureSession`, а отдать это хуку: передавать первый текст как аргумент/сигнал в `usePlannerSession`, чтобы хук сам отправил его после `onOpen`. Это убирает гонку полностью, но требует изменения API хука.

> Вариант A достаточно локален и не ломает контракт хука — принимаем его.

## Порядок задач
1. **Фронт `usePlannerSession.ts`:**
   - Хранить предыдущий `sessionId` в `ref` (`prevSessionRef`). Чистить `messages`/`streaming`/`closed`/`error`/`assistantBufferRef` **только если `sessionId !== prevSessionRef.current`**.
   - Убрать безусловное `pendingRef.current = []` из тела эффекта; оставить сброс в `onOpen` после флеша.
2. **Проверить `App.tsx` `handleSend`:** после фикса A `planner.send(text)` сразу после `ensureSession` корректен — текст попадёт в `pendingRef` и уйдёт по `onOpen`. Изменений в `App.tsx` не требуется.
3. **Тест/ручная проверка:** см. критерий приёмки.

## Критерий приёмки
- [ ] Новый чат: первое же отправленное сообщение **отображается** в чате (user-пузырь) **и доходит до сервера** (приходит ответ планировщика / tool-кадры / finish).
- [ ] Второе и последующие сообщения работают как раньше.
- [ ] Переключение/создание новой сессии по-прежнему чистит историю корректно (предыдущий чат не «слипается» с новым).
- [ ] `pnpm run typecheck` и `pnpm run lint` зелёные; `pnpm run build` без ошибок.
- [ ] Регресс: при уже открытой сессии повторная отправка не дублирует сообщения.

## Риски / заметки
- Главное — не сломать очистку истории при смене сессии: чистить нужно строго по смене `sessionId`, а не по перевешиванию замыкания `handleEvent`.
- `handleEvent` обёрнут в `useCallback([])` (стабилен), поэтому эффект не пересоздаётся лишний раз — но фикс должен это учитывать.
- После фикса буфер `pendingRef` может содержать сообщение до открытия сокета дольше обычного; убедиться, что `onOpen` флешит **весь** массив, а не один элемент.
