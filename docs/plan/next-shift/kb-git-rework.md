- **Связанные ADR:** переопределяет ADR-0012 (п.2/4/6), уточняет ADR-0005; закрывает долг ADR-0018 (git-коммит скилла); затрагивает ADR-0006/0016/0017/0019; реализует шаг 2 роадмапа ADR-0010. Полная сверка — раздел «Сверка с ADR».

## Цель

Заменить загрузку одиночных документов через UI на подключение пользовательского **git-репозитория базы знаний** и индексирование его содержимого на месте. Репозиторий — источник истины по файлам (документы и скиллы). Любая транзакция работы с доками и коммит скилла из UI завершаются реальным git-коммитом в этот репо. Модель работает в трёх сценариях развёртывания одинаково: on-prem (корп-среда), SaaS, локально на машине пользователя.

## Зафиксированные решения (итог обсуждения)

1. **Разделение двух гитов.** Репо *проекта* (исходный код Catalog, где «версия = коммит» про разработку) и репо *базы знаний* (пользовательский, подключаемый) — разные вещи. Задача про второй. Ниже везде «репо» = пользовательский репо базы знаний.
2. **Подключение: локальный путь + опциональный remote.** Приложение делает `git init`/`open` по указанному пользователем локальному пути. `push` на remote — отдельная, отключаемая по умолчанию функция (бэкап). Работает офлайн.
3. **Один репо, подпапки.** Внутри репо три зоны, как в текущей ФС: `documents/` (входные документы), `results/` (result_md прогонов), `skills/` (конфиги скиллов). Одно подключение в UI, атомарное версионирование всех трёх зон.
4. **Индексирование на месте, не копирование.** Файлы лежат в подключённом репо; приложение сканирует их и строит индекс в SQLite. **SQLite — пересобираемый индекс над git** (инвариант ADR-0005/0012), в git не кладём ни `catalog.db`, ни отдельный манифест.
5. **Коммит — явной кнопкой в UI.** Изменения (добавление/удаление документов, редактирование/коммит скилла, результаты прогонов) накапливаются в рабочем дереве; пользователь коммитит кнопкой (развитие текущего `commit_skill`, но с реальной записью в git). Каждый коммит опционально пушится, если remote настроен.
6. **UI загрузки заменяется.** Кнопка «+ Загрузить документ» (одиночный файл) убирается; вместо неё — экран подключения репо, список проиндексированных документов, панель незакоммиченных изменений и кнопка Commit.

## Расхождения с текущим кодом и ADR (что переопределяем)

- **ADR-0012 п.6** («folder-picker = admin/env-настройка, не end-user UI») — **переопределяем**: подключение репо становится end-user действием в UI. Нужно дополнить ADR-0012 или новый ADR.
- **ADR-0012 п.2** (два app-owned репо `documents/` и `skills/`) — **переопределяем на один репо с подпапками** `documents/`, `results/`, `skills/`. Сейчас `main.py:58-59` init-ит два отдельных репо (`workspace/documents`, `workspace/skills`), а `results/` вообще без git; станет один `ensure_repo(repo_root)` + ensure трёх подпапок.
- **ADR-0012 п.4** (внешние репо — только read-source, никогда не мутируются/пушатся) — уточняем: подключённый **пользовательский рабочий** репо приложение мутирует и коммитит (он не «авторитетный прод-репо заказчика»). Опциональный push — это open-step ADR-0012 «configured remote для бэкапа».
- **Расположение репо больше не захардкожено** в `workspace_dir`. Сейчас `document.path` относителен `workspace/`, а `documents/` — подпапка workspace. Станет: путь относителен корня подключённого репо; сам репо конфигурируется.
- **`commit_skill` (`api/skills.py:967-974`)** сейчас только флипает статус в SQLite — станет реальной материализацией конфига скилла в `skills/` + git-коммитом.
- **`delete_document` (`repo_document.py`)** делает `unlink` файла и удаляет строку — сохраняется (файл в рабочем дереве репо, удаление стейджится к коммиту), но семантика «удаление = staged deletion до коммита».
- **`reconcile_orphans`** остаётся валиден (нет файла в рабочем дереве → строка индекса удаляется), но переосмысляется как часть пере-сканирования репо.

## Целевая модель (кратко)

```
<repo_root>/                 # подключаемый git-репо базы знаний (init/open через UI)
  documents/                 # входные документы (kind: md/docx/pdf/csv/xlsx)
  results/                   # result_md прогонов скиллов (kind: result_md)
  skills/                    # материализованные конфиги скиллов (по одному файлу/папке на скилл)
  .git/                      # версии = коммиты; опциональный remote для бэкапа

catalog.db (в data-root, НЕ в репо)   # пересобираемый индекс над репо
```

- `document.path` = путь относительно `repo_root` (`documents/...` для входных, `results/...` для result_md — уже так в `build_doc_path(..., subdir)`).
- Индекс строится сканом `documents/` и `results/` при подключении и при «Rescan».
- Транзакции (add/delete doc, edit/commit skill, save result) меняют рабочее дерево и стейджатся; **Commit** фиксирует в git (+ optional push).
- SQLite всегда выводим из репо: `rebuild_index()` = скан рабочего дерева.

## Декомпозиция на подшаги

### Шаг 1 (code) — Слой git-транзакций поверх dulwich

Расширить `app/storage/git.py`: помимо `ensure_repo` добавить операции стейджа/статуса/коммита/пуша на dulwich.

- `open_repo(root)` / `init_repo(root)` — открыть или инициализировать; идемпотентно (уже частично есть).
- `stage_paths(repo, paths)` / `stage_removal(repo, paths)` — добавить/удалить в git-index (dulwich `repo.stage`, `porcelain.add`, `porcelain.remove`).
- `status(repo)` — `porcelain.status`: список staged/unstaged/untracked, для панели «незакоммиченные изменения».
- `commit(repo, message, author)` — фиксированная app-identity (dulwich не требует host-config, критично для on-prem): напр. `Catalog <catalog@localhost>`; сообщение генерится или задаётся пользователем.
- `push(repo, remote, credentials)` — опционально; ошибки push не роняют коммит (коммит уже локально сделан), возвращаем предупреждение.
- Гард пути: любые операции строго внутри `repo_root` (защита от path traversal, симлинков наружу).

Тесты: init во временной папке, stage+commit создаёт коммит, status до/после, удаление файла → staged deletion, commit пустого дерева — no-op с понятным ответом.

### Шаг 2 (code) — Конфиг подключения репо и состояние приложения

- Расширить `config.py`/`paths.py`: `APP_KB_REPO` (env) — путь к репо базы знаний. По умолчанию для локального запуска — `<data-root>/kb` (совместимо с текущим поведением), но переопределяется через UI.
- Хранить подключение персистентно: таблица/строка настроек (например `app_setting(key,value)`), чтобы выбор пользователя переживал рестарт. Remote-URL и признак «push включён» — там же; credentials — отдельно и вне git (см. риски).
- `main.py`: вместо `ensure_repo(workspace/documents)` + `ensure_repo(workspace/skills)` — `ensure_repo(repo_root)` и `ensure` подпапок `documents/`, `results/`, `skills/`. `app.state.repo` / `app.state.repo_root` в дополнение к (или вместо) `app.state.workspace`.
- Обновить резолв путей документов: `document.path` относителен `repo_root`; `read_document`/`extract` собирают `os.path.join(repo_root, path)`.

Тесты: старт с пустым `APP_KB_REPO` (дефолт), с заданным путём; ре-резолв в `get_settings()` (уже есть паттерн с monkeypatch).

### Шаг 3 (code) — Индексирование репо (scan) вместо upload

- Новый модуль `app/documents/scan.py`: `scan_repo(db, repo_root)`:
  - Обойти `documents/` (входные, kind по `_EXT_TO_KIND`) и `results/` (result_md); отфильтровать по расширениям. `skills/` сканируется отдельно (шаг 5), не как документы.
  - Дедуп по `path` (первичный ключ соответствия «файл ↔ строка индекса»).
  - Новый файл → `create_document` (path относителен репо, id генерится). Изменённый (по `mtime`/`size`) → обновить метаданные строки, **сохранив id** (не рвём FK `session_document`/`skill_run`). Исчезнувший → пометить/удалить (переиспользуем логику `reconcile_orphans`).
  - Вернуть сводку `{added, updated, removed, skipped}` для UI.
- Схема `document`: добавить `mtime`, `size` (и опц. `content_hash` на будущее) через `ADDITIVE_MIGRATIONS`.
- `ingest_file` перепрофилировать: писать байты сразу в `documents/` подключённого репо (для сценария «добавить документ из UI перетаскиванием» — если оставляем такой путь) и потом стейджить; либо полностью заменить сканом, если добавление файлов идёт только через файловую систему/репо. **Решение по добавлению файлов из UI — см. открытый вопрос O1.**

Тесты: скан пустого репо; добавление файла на диск → появляется в индексе; изменение файла → обновление той же строки (id стабилен); удаление файла → строка убрана; неподдерживаемый формат → skipped.

### Шаг 4 (code) — API: connect / status / commit / rescan

- `POST /kb/connect` — тело: `path` (+ опц. `remote`, `push_enabled`). Init/open репо, ensure подпапок, первичный `scan_repo`, вернуть сводку.
- `GET /kb/status` — текущее подключение + `git status` (незакоммиченные изменения) + счётчики индекса.
- `POST /kb/rescan` — пере-скан рабочего дерева (замена/обёртка над `POST /documents/reconcile`).
- `POST /kb/commit` — тело: `message`. Стейдж всех изменений (documents + skills) → `commit` → опц. `push`. Вернуть sha + push-статус/варнинг.
- `GET /documents` — теперь читает индекс, наполненный сканом (реконсайл заменить на rescan-путь).
- Депрекейтнуть/убрать `POST /documents` (одиночная загрузка) — по решению O1.

Тесты (pytest + FastAPI TestClient): connect на временный путь, status показывает pending после add, commit создаёт коммит и очищает pending, rescan подхватывает внешние изменения файлов.

### Шаг 5 (code) — Скиллы в git: материализация + реальный commit_skill

- При «commit skill» писать конфиг скилла (`config_json` → например `skills/<slug>-<id>.json` или папка со `skill.json`) в рабочее дерево репо, стейджить и коммитить (может входить в общий `POST /kb/commit` либо отдельный `POST /skills/{id}/commit`, который делает commit точечно).
- `commit_skill_endpoint` (`api/skills.py:967`) — заменить «флип статуса» на: материализовать файл → stage → commit → статус `committed`.
- Долг из ADR-0012 (миграция скиллов из SQLite в ФС+git) закрывается здесь. SQLite-строка скилла остаётся кэшем/индексом; источник истины — файл в `skills/`.
- Результаты прогонов (`apply.py:355-363`, `runs.py:145-149` — уже пишут в `results/`) остаются в `results/` подключённого репо, но теперь стейджатся; попадают в ближайший commit.

Тесты: commit skill создаёт файл в `skills/` и коммит; повторный commit после правки — новый коммит; rebuild индекса из `skills/` восстанавливает список скиллов.

## Открытые вопросы (решить до реализации)

- **O1. Добавление файлов из UI.** Раз загрузка одиночных файлов убирается: добавлять документы (а) только через файловую систему/репо + Rescan, или (б) оставить drag-and-drop, который кладёт файл в `documents/` репо и стейджит? Влияет на судьбу `ingest_file`/`POST /documents`.
- **O2. Гранулярность коммита скиллов.** «Commit skill» — точечный коммит только скилла, или скиллы попадают в общий `POST /kb/commit` вместе с документами? (сейчас в решениях: явный commit в UI — но для скиллов исторически отдельная кнопка.)
- **O3. Хранение credentials для push.** Где и как (keyring/env/зашифрованная настройка), учитывая on-prem и SaaS. В git не коммитить.
- **O4. Миграция существующих данных.** Что делать с уже загруженными в текущий `workspace/documents/` файлами и строками `document` при первом переходе на подключаемый репо (одноразовый импорт в новый репо?).
- **O5. Индексирование `results/`.** result_md уже пишутся в `results/` и создаются приложением (строка `document` есть сразу). Нужно ли скану отдельно обходить `results/`, или доверять, что эти строки всегда создаёт `apply.py`? (важно для восстановления индекса из чистого репо и для правок result-файлов вне приложения.)
- **O6. `persist=false` и «транзакция = коммит» (ADR-0006/0017).** При выводе «на экран» файл результата не создаётся — текст в `skill_run.result_text`, документ появляется только после `POST /runs/{id}/save`. Значит не всякий прогон даёт коммитируемый артефакт. Уточнить формулировку «любая транзакция завершается коммитом»: коммитим только персистентные результаты (после save), а не каждый прогон.
- **O7. Скан и FK сессий (ADR-0016).** Явно зафиксировать: обновление файла сохраняет `document.id`; удаление строки за «исчезнувший» файл каскадит по `session_document`/`skill_run` так же, как текущий `delete_document` (nullify refs), и не роняет открытые сессии. Нужен тест на «файл пропал → сессия, куда он был привязан, не падает».
- **O8. Git-состояние скилла при edit (ADR-0018).** `edit` возвращает `committed`-скилл в `draft`. Решить: файл в `skills/` удаляется до ре-коммита, помечается устаревшим или остаётся как есть до следующего commit. Влияет на консистентность `skills/` с таблицей `skill.status`.
- **O9. Форма правки ADR-0012.** Переписать 0012 на месте (Supersedes-пометки внутри) или завести новый ADR-0022, superseding-ий его п.2/4/6. Обычно для сдвига такого масштаба чище новый ADR + пометка на старом.

## Критерии приёмки (эпик)

- [ ] Приложение подключается к локальному git-репо по пути из UI (init или open); при подключении строит индекс из `documents/`.
- [ ] Индекс — только в SQLite и полностью пересобираем из репо; в git не коммитятся `catalog.db`/манифест.
- [ ] Добавление/удаление документа и правка/коммит скилла отражаются как незакоммиченные изменения; кнопка Commit создаёт git-коммит; при включённом remote — push (сбой push не теряет коммит).
- [ ] `commit_skill` материализует конфиг в `skills/` и реально коммитит (не только флип статуса).
- [ ] Rescan подхватывает изменения файлов, сделанные вне приложения; id документов стабильны при обновлении (FK `session_document`/`skill_run` целы).
- [ ] UI загрузки одиночного файла заменён на подключение репо + список + панель изменений + Commit.
- [ ] Пути изолированы внутри `repo_root` (нет traversal/симлинков наружу).
- [ ] ADR-0012/0005 обновлены; README/.env.example описывают `APP_KB_REPO` и push.
- [ ] `pytest` и `ruff check .` зелёные; регрессия существующих тестов документов/скиллов.
- [ ] Модель работает одинаково для on-prem / SaaS / локального запуска (нет зависимости от системного `git`).
