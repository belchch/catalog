## Цель и пользовательский путь

Сценарий: пользователь отправил сообщение планировщику, идёт ответ («●●● планировщик думает…»), сокет рвётся (сервер перезапустился / сеть моргнула / прокси убил соединение).

Как должно выглядеть сейчас:

1. Пользователь пишет сообщение → под перепиской появляется индикатор «●●● планировщик думает…», композер заблокирован, справа кнопка «Стоп».
2. Сокет рвётся. Индикатор «думает» **сразу исчезает** (не висит вечно), композер разблокируется, вместо «Стоп» возвращается «Отправить».
3. На месте индикатора появляется баннер «Соединение потеряно — ответ прерван» с кнопкой «Переподключить». Отправка новых сообщений заблокирована, черновик в поле ввода сохраняется.
4. Пользователь жмёт «Переподключить» → баннер переходит в состояние «Переподключаю…», кнопка блокируется и показывает busy.
5. Соединение открылось → баннер исчезает, история сообщений **перезагружается из БД** (то, что успел сохранить бэкенд, включая законченный ответ, если ход на сервере всё-таки доехал), фокус возвращается в поле ввода, отправка снова доступна.
6. Если сокет упал повторно — снова состояние из шага 3 (кнопка «Переподключить» снова активна), без залипания на «Переподключаю…».

Идентичный путь при обрыве **вне хода** (нет streaming): баннер без пометки о прерванном ответе.

### Контракт `ConnectionBanner`

```
interface ConnectionBannerProps {
  reconnecting: boolean   // идёт попытка переподключения
  interrupted: boolean    // обрыв произошёл во время ответа планировщика
  onReconnect: () => void
}
```

Компонент рендерится только когда `Chat` решил его показать (`closed || reconnecting`); внутренней логики видимости у него нет.

## Layout и состояния

Баннер живёт **в потоке ленты сообщений**, последним блоком внутри `catalog-chat__content`: после последнего сообщения, на месте, где был индикатор «думает», и **до** строки `error`. Ширина — по контенту ленты (`max-w` не задаём, блок тянется на ширину колонки), отступ `my-3`.

Матрица состояний ленты:

| Состояние | Индикатор «думает» | Баннер | Композер |
|---|---|---|---|
| `streaming`, сокет жив | показан | нет | заблокирован, кнопка «Стоп» |
| Обрыв во время хода (`closed && interrupted`) | **скрыт** | «Соединение потеряно — ответ прерван» + кнопка | поле активно, отправка заблокирована |
| Обрыв вне хода (`closed && !interrupted`) | скрыт | «Соединение потеряно» + кнопка | поле активно, отправка заблокирована |
| `reconnecting` | скрыт | «Переподключаю…», кнопка disabled + `aria-busy` | отправка заблокирована |
| Переподключились | скрыт | нет (баннер размонтирован) | обычный режим |
| `error` от сервера | скрыт | не показывается (ошибка перекрывает: `hadErrorRef` уже гасит `closed`) | обычный режим |

Правило видимости индикатора в `Chat`: `streaming && !closed && !reconnecting`. Даже если хук по какой-то причине не сбросил флаг, «думает» и баннер не могут отображаться одновременно.

Тексты (ru, без вариативных склонений):

- Заголовок при `interrupted`: `Соединение потеряно — ответ прерван`; подпись второй строкой: `Часть ответа могла не сохраниться. Переподключитесь и повторите запрос.`
- Заголовок без `interrupted`: `Соединение потеряно`; подпись: `Отправка сообщений недоступна.`
- При `reconnecting`: заголовок `Переподключаю…`, подписи нет.
- Кнопка: `Переподключить` / при `reconnecting` — `Переподключаю…` (disabled).

## Взаимодействия

- **Клик «Переподключить»** → `onReconnect()`; баннер немедленно переходит в `reconnecting` (кнопка disabled, `aria-busy="true"`), повторные клики невозможны.
- **Успешный реконнект** → баннер исчезает; если переподключение было инициировано кликом, фокус программно возвращается в `textarea` композера (иначе фокус «повисает» на исчезнувшей кнопке). Автофокус не срабатывает, если пользователь ушёл в другое поле.
- **Повторный обрыв** → баннер снова в состоянии «потеряно», кнопка снова активна.
- **Отправка при `closed || reconnecting`**: кнопка «Отправить» — `disabled`, `title`/`aria-description` = `Нет соединения — переподключитесь`; Enter в поле ввода ничего не отправляет; чипы быстрых ответов `disabled`. Поле ввода остаётся активным — черновик не теряется. Логика согласована с уже существующим поведением «Повторить» в `MessageCommands` (блокируется при `closed`).
- **Удаление вложений и переключение инструментов** при `closed` не блокируем: это HTTP, а не сокет.
- **Автоскролл**: эффект прокрутки вниз срабатывает не только на изменение `messages`, но и на появление баннера — иначе баннер уезжает за нижнюю границу при длинной переписке.
- **Гидрация после реконнекта**: сообщения из API заменяют локальный список одним `setMessages` — без промежуточного пустого состояния и мигания.

Крайние случаи:

- Обрыв, когда сообщение ещё лежало в `pendingRef` (сокет не успел открыться): индикатор «думает» гаснет, показывается баннер; неотправленное сообщение остаётся в ленте как пользовательское — новых «фантомных» спиннеров нет.
- Смена сессии при открытом баннере: `resetLocal` гасит и `closed`, и `interrupted` — баннер не переезжает в другую сессию.
- Намеренное закрытие сокета (unmount / смена сессии) баннер не показывает — как и сейчас (`intentionalClose`).

## Стиль и токены

- Баннер — карточка-алерт в стиле существующего блока `buildError` (`Chat.tsx:463-467`), но в warning-палитре:
  `my-3 flex items-start justify-between gap-3 rounded-md border border-warning-line bg-warning-soft px-3 py-2 text-xs text-warning-ink`.
- Текстовый блок: заголовок `font-medium`, подпись — отдельным `<p className="mt-0.5 text-warning-ink/80">`… — для подписи допустим `text-[11px]`, как в других вторичных подписях (`Chat.tsx:330`, `449`).
- Кнопка — существующий класс `btn-secondary shrink-0` (нейтральная серая на warning-фоне, как и остальные вторичные действия чата). Новых кнопочных классов не заводим.
- Никаких анимаций и спиннер-иконок: состояние «Переподключаю…» передаётся текстом + `aria-busy`, как уже сделано в чате.
- Токены берём только из `index.css` (`--warning-*`, `--ink-*`); хардкод hex-цветов запрещён.
- Ширина/выравнивание наследуются от `catalog-chat__content` — баннер визуально в одной колонке с сообщениями.

## Доступность (a11y)

- Обёртка баннера: `role="status"`, `aria-live="polite"`, `aria-busy={reconnecting}` (сохраняем текущую семантику; `alert`/assertive не используем — обрыв не критическая ошибка формы).
- Заголовок и подпись — текстовые узлы внутри `role="status"`, читаются скринридером целиком при появлении.
- Кнопка: `type="button"`, доступное имя совпадает с видимым текстом, `disabled` + `aria-busy` при `reconnecting`, фокус-кольцо из `.btn-secondary` (`focus-visible:ring-2 ring-brand`).
- После успешного переподключения фокус переносится в `textarea` композера — фокус не теряется на body.
- Заблокированная кнопка «Отправить» объясняет причину через `title` + `aria-description` (паттерн уже применён к кнопке инструментов, `Chat.tsx:416-418`).
- Контраст: `--warning-ink (#8a5a12)` на `--warning-soft (#fbeecd)` — AA для мелкого текста; палитра уже используется в бейджах.
- Клавиатура: до кнопки «Переподключить» доходим Tab из ленты сообщений (лента — `tabIndex=0` регион), Enter/Space активируют.

## Контракты данных

Новых API/WS-контрактов нет. Изменяется только публичный контракт хука `UsePlannerSessionResult`:

- добавляется `interrupted: boolean` — «обрыв случился, пока шёл ответ»; выставляется в `onClose`, если `streamingRef.current === true`; сбрасывается в `send`, `reconnect`, `onOpen` и `resetLocal`;
- смысл `closed` / `reconnecting` / `streaming` / `cancelling` не меняется, меняются только моменты сброса (`onClose` гасит `streaming` и `cancelling`) — см. план, пункты 1–3.

`ChatProps` получает соответствующий `interrupted: boolean`. Прогонный экран (`RunView` / `useRunStream`) в этот срез не входит — его строку «Соединение закрыто» не трогаем.

## Критерии визуальной приёмки

- [ ] При `closed=true` индикатор «●●● планировщик думает…» не отрисован ни при каком значении `streaming`.
- [ ] При `closed && interrupted` виден баннер с текстом `Соединение потеряно — ответ прерван` и подписью про несохранённую часть ответа.
- [ ] При `closed && !interrupted` виден баннер `Соединение потеряно` без пометки о прерванном ответе.
- [ ] В обоих случаях в баннере есть активная кнопка `Переподключить`, клик по ней вызывает `onReconnect`.
- [ ] При `reconnecting=true` баннер показывает `Переподключаю…`, кнопка `disabled` и `aria-busy="true"`.
- [ ] Баннер — один блок с `role="status"` и `aria-live="polite"`, отрисован после последнего сообщения и до строки ошибки.
- [ ] Оформление баннера использует только warning-токены (`border-warning-line`, `bg-warning-soft`, `text-warning-ink`) и класс `btn-secondary` для кнопки; hex-цветов в разметке нет.
- [ ] При `closed || reconnecting` кнопка «Отправить» заблокирована и объясняет причину (`title` = `Нет соединения — переподключитесь`), Enter в поле ввода не вызывает `onSend`, чипы подсказок заблокированы.
- [ ] Текст черновика в поле ввода при обрыве сохраняется (поле не disabled и не очищается).
- [ ] После исчезновения баннера по клику «Переподключить» фокус оказывается в `textarea` композера.
- [ ] После реконнекта в ленте видны сообщения, пришедшие из API (гидрация не блокируется залипшим `streamingRef`), без промежуточного пустого экрана.
