## Контекст
Вечный спиннер на фронте:

- `frontend/src/hooks/usePlannerSession.ts:374-379` — `onClose` ставит `closed`, но не сбрасывает `streaming` / `cancelling` / `streamingRef`.
- `frontend/src/hooks/usePlannerSession.ts:409-418` — `send()` ставит `streaming=true` до открытия сокета; если сокет не откроется — спиннер навсегда.
- `frontend/src/hooks/usePlannerSession.ts:297-314` — гидрация сообщений пропускается при `streamingRef=true` / pending / буфере ассистента.
- `frontend/src/hooks/usePlannerSession.ts:421-424` — Stop шлёт `cancel()` в, возможно, уже закрытый сокет.
- Баннер обрыва уже частично есть (`closed` / `reconnect`); его нужно связать со сбросом streaming.

Предусловие: `docs/plan/2-shift/00-CATALOG-130-code-planner-finish-keepalive.md` (idle-cancel кадр, keepalive). Без него Stop в idle по-прежнему молчит на бэкенде, но UI больше не зависает на обрыве.

## Затрагиваемые файлы
- `frontend/src/hooks/usePlannerSession.ts` — `onClose` сбрасывает флаги; гидрация после обрыва; `send` не держит streaming, если сокет так и не открылся.
- Компонент чата/баннера (тот, что уже рисует `closed` / `reconnecting`) — явный «соединение потеряно» + переподключение, без вечного «думает».
- Тесты хука/компонента — `onClose` во время streaming; реконнект гидрирует сообщения.

## План действий
1. В `onClose` (неintentional): `streamingRef=false`, `setStreaming(false)`, `setCancelling(false)`.
2. Не блокировать гидрацию сообщений из БД только из-за `streamingRef` после обрыва — после `onClose` флаги уже сброшены; на реконнекте грузить историю.
3. Если `send` ушёл в `pendingRef` и сокет не открылся / закрылся — не оставлять `streaming=true`.
4. Баннер «соединение потеряно» + существующая кнопка `reconnect`; спиннер «думает» не держать на `closed`.
5. Тест: close посреди хода → нет streaming, виден баннер; после reconnect сообщения из API на экране.
