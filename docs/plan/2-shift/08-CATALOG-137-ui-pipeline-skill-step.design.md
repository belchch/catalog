# CATALOG-137 — Дизайн UI

- **Источник:** docs/plan/2-shift/08-CATALOG-137-ui-pipeline-skill-step.md
- **Статус дизайна:** Ready

## Цель и пользовательский путь

Третий тип шага pipeline (`skill`, ADR-0022) должен читаться в UI так же спокойно, как `script` и `llm`: планировщик поставил шаг → пользователь видит его в списке шагов, понимает, какой скилл вызывается и какой снапшот прибит; после прогона — раскрывает вложенный запуск в трейсе.

Сценарий:

1. **Черновик.** В чате планировщик вызывает `save_skill_steps` со шагом `{type:"skill", skill_id}`. В панели STEPS появляется строка с бейджем `SKILL`. Раньше такой шаг попадал в ветку `script` и врал: «код не задан».
2. **Разбор шага.** Пользователь раскрывает «подробнее» и видит: какой скилл вызывается (имя + kind), к чему прибит снапшот (короткий `config_hash`), либо честное «имя и пин появятся при сборке», пока сборки не было.
3. **Готовность.** Карточка черновика («Артефакты скилла») и подсказки в PROMPT/SCRIPT не требуют промпта и кода, если ни один шаг их не ждёт. Счётчик шагов считает skill-шаги наравне с остальными.
4. **Трейс.** Прогон pipeline со skill-шагом: в дереве трейса шаг раскрывается в узел вложенного запуска — имя скилла, глубина, цена, статус, а внутри — трейс вложенного прогона. Механика та же, что у вложенного скилла из сессии (CATALOG-119/129), пользователю не нужно учить второй способ читать дерево.

## Layout и состояния

### STEPS — строка шага

Строка не меняется по структуре (одна строка 11px, `flex flex-wrap items-center gap-2`):

```
[3]  extract_terms   SKILL   ПРЕДЫДУЩИЙ
     подробнее
```

Порядок и семантика элементов те же, что у `script` / `llm`: индекс → id шага (mono; `text-warning-ink`, если id пуст) → бейдж типа → бейдж входа (`документы` / `предыдущий`).

### STEPS — «подробнее» для skill-шага

| Состояние шага | Что показываем |
|----------------|----------------|
| Снапшот собран (`skill_name` есть) | Строка 11px `text-ink-muted`: `Сводка · agent` (kind опускаем, если его нет в снапшоте). Ниже строка 11px `text-ink-muted`: `пин 1a2b3c4d` — первые 8 символов `config_hash`, полный хеш в `title` |
| Черновик: есть `skill_id`, нет `skill_name`/`config_hash` | Строка 11px mono `text-ink-muted`: `id: <skill_id>` (обрезка длинного id по ширине, `break-words`). Ниже 10px `text-ink-faint`: `имя и пин появятся при сборке` — тем же тоном, что «код возьмётся из артефакта Script при сборке» |
| `skill_id` пуст | Одна строка 11px `text-warning-ink`: `скилл не выбран` (парная к «код не задан» / «промпт не задан») |

Чего у skill-шага **не** должно быть: строк «код не задан», «промпт не задан», `pre` с кодом/промптом, строки `модель / провайдер / reasoning` и строки `allowed_tools` — они относятся только к `script` / `llm`.

Расчёт «первого пустого» шага (`firstEmptyScript` / `firstEmptyLlm`) фильтруется по типу, поэтому skill-шаги не сдвигают подсказки у соседей — это надо сохранить.

### Карточка черновика (`ArtifactSummaryCard`)

Состав строк не меняется: без артефакта `steps` — три строки и «из 3»; с артефактом — четыре строки.

Новое — понятие «требуется по шагам» для pipeline-черновика:

- `нужен промпт` = есть хотя бы один шаг `type=llm` без своего `system_prompt`;
- `нужен код` = есть хотя бы один шаг `type=script` без своего `code`.

| Строка | Состояние | Вид |
|--------|-----------|-----|
| Промпт / Скрипт | требуется и заполнено | `✓` + «готово» (как сейчас) |
| Промпт / Скрипт | требуется и пусто | `—` без правой пометки (как сейчас) |
| Промпт / Скрипт | не требуется | `—` + правая пометка `не требуется` (`artifact-summary__ready`, приглушённый тон) |
| Шаги | ≥1 шаг любого типа, JSON валиден | `✓` + «N шагов»; skill-шаги считаются наравне |

Знаменатель готовности («Готово N из M разделов») считает только требуемые строки: pipeline из одних skill-шагов даёт «Готово 2 из 2» (Настройки + Шаги), а не вечное «2 из 4». Черновик без артефакта `steps` работает как раньше.

### Подсказки в ArtifactsPanel (kind = pipeline)

| Секция | Условие | Текст (10px `text-ink-faint`, на месте текущей подсказки) |
|--------|---------|------------------------------------------------------------|
| Prompt | есть llm-шаг без своего промпта | `pipeline: подставится в первый llm-шаг без своего промпта` (как сейчас) |
| Prompt | llm-шаги есть, но у всех свой промпт | `pipeline: у всех llm-шагов свой промпт` |
| Prompt | llm-шагов нет | `pipeline: llm-шагов нет — промпт не нужен` |
| Script | есть script-шаг без своего кода | `pipeline: подставится в первый script-шаг без своего кода` (как сейчас) |
| Script | script-шаги есть, но у всех свой код | `pipeline: у всех script-шагов свой код` |
| Script | script-шагов нет | `pipeline: script-шагов нет — код не нужен` |

Секция Script включена намеренно: это та же строка кода и тот же дефект — подсказка обещает подстановку в шаг, которого в pipeline из skill-шагов просто нет. Правка симметричная и однострочная.

### Трейс — узел вложенного запуска

Разметка узла не меняется: тот же `TraceRunNode` внутри группы шага.

```
шаг 2 · call_summary                              ✓  3 события
  ⤷ Сводка                          ✓ · глубина 1 · 2 LLM-вызова · запуск 7c1f0ab2
      вход / результат / проверки / трейс вложенного прогона
```

Состояния узла — существующие, ничего нового не рисуем: свёрнут (запроса нет) → «Загружаю запуск…» (`role="status"`) → загружен / «Запуск не найден» / ошибка с кнопкой «Повторить» / «Запуск ещё выполняется» с кнопкой «Обновить».

Провал вложенного verify останавливает пайплайн (ADR-0022 п.4): в узле это уже покрыто существующей веткой — красная плашка с причинами и блок «проверки». Отдельного визуала для этого случая не добавляем.

Исчерпание бюджета / дедлайн на skill-шаге приходят как записи трейса `budget` / `deadline` и рендерятся существующей строкой-ограничителем внутри группы шага — это тоже не меняем.

## Взаимодействия

- **Раскрытие деталей шага** — нативный `<details>/<summary>` «подробнее», как у script/llm. Ничего не грузит, состояние не запоминается.
- **Раскрытие вложенного запуска** — клик/Enter по `summary` узла; запрос `getRun` уходит только при первом открытии (ленивая загрузка), повторное сворачивание не перезапрашивает. Поведение уже реализовано в `TraceRunNode` — переиспользуем без правок.
- **Глубина раскрытия.** Узлы вложенных запусков сворачиваются на глубине дерева 0 и 1; глубже (`depth >= 2`) tool_result остаётся строкой с суффиксом `· глубина N`. Это даёт нужный сценарий «чат → pipeline-скилл → его skill-шаг» и не превращает дерево в неограниченную рекурсию запросов.
- **Регрессия 119/129.** Правило фолдинга для session-тулов (`skill_*`) не трогаем: на глубине ≥ 1 они по-прежнему не сворачиваются, ограничители сворачиваются как раньше.
- **Крайние случаи:**
  - `skill_id` пустой или снапшот отсутствует → шаг рисуется, но с предупреждающей строкой; UI не падает и не подставляет «script».
  - Неизвестный `type` в артефакте по-прежнему нормализуется в `script` (fail-visible, как было) — новым является только то, что `skill` больше не попадает в эту ветку.
  - `config_hash` короче 8 символов → показываем как есть, без многоточия.
  - Живой поток прогона не присылает событие на skill-шаг (бэкенд CATALOG-136 пишет только запись трейса), поэтому во время прогона в `RunView` узла нет — он появляется там, где рендерится сохранённый трейс (pipeline, открытый как вложенный запуск). Расширять скоуп до дозагрузки трейса в `RunView` в этом шаге не нужно.

## Стиль и токены

- Бейдж `SKILL` — `badge-success`. `badge-info` занят `SCRIPT`, `badge-accent` — `LLM`, `badge-neutral` — бейджем входа в той же строке; `success` в гайде значит «ok / committed», а шаг несёт снапшот committed-скилла, так что смысл совпадает и три типа различимы с одного взгляда.
- Размеры и тона — как у соседних строк: 11px для содержательных строк (`text-ink-muted`, `text-warning-ink` для проблем), 10px `text-ink-faint` для подсказок «появится при сборке».
- Идентификаторы (`skill_id`, `config_hash`) — `font-mono`, как id шага.
- Только семантические утилиты из `docs/ui-style-guide.md`; сырые палитры Tailwind (`slate-*`, `red-*`, …) запрещены. Новых CSS-классов не заводим: пометка «не требуется» использует существующий `artifact-summary__ready`.

## Доступность (a11y)

- Тип шага передаётся текстом бейджа (`SKILL`), а не только цветом; статус «скилл не выбран» — текст, не только тон.
- Короткий `config_hash` — `<span title={полный хеш}>`, как уже сделано для длинных имён проверок (`formatCheckName`); визуальный текст остаётся осмысленным без наведения (`пин 1a2b3c4d`).
- Раскрытие — нативные `details`/`summary`: клавиатура и скринридер работают без ARIA-костылей; фокус-кольцо `ring-2 ring-brand` из глобальных стилей не переопределяем.
- Состояния загрузки и ошибки узла уже озвучены (`role="status"` + `aria-live="polite"`, `role="alert"`, `aria-busy`) — сохранить.
- Контраст: `success`-бейдж и `ink-muted` берём из токенов, кастомных цветов не вводим.

## Контракты данных (если нужны)

**Артефакт `steps`** (сериализация `pipeline_step_to_dict`, CATALOG-135):

```json
{ "id": "call_summary", "type": "skill", "input": "previous",
  "skill_id": "sk_7f3…", "skill_name": "Сводка",
  "config_hash": "1a2b3c4d…", "config": { "kind": "agent", "...": "..." } }
```

- В черновике есть только `skill_id`; `skill_name` / `config_hash` / `config` появляются при сборке.
- `skill_kind` в `PipelineStepDraft` читается из `config.kind`; отсутствует — пустая строка.
- Все новые поля опциональны: старый артефакт без них должен нормализоваться без ошибок.

**Запись трейса skill-шага** (`apply.py`, CATALOG-136):

```json
{ "kind": "tool_result", "iteration": 2,
  "data": { "name": "Сводка", "ok": true, "step_id": "call_summary",
            "run_id": "7c1f0ab2…", "skill_id": "sk_7f3…", "skill_name": "Сводка",
            "config_hash": "1a2b3c4d…", "depth": 1, "failures": [],
            "result": { "ok": true, "status": "ok", "run_id": "7c1f0ab2…", "depth": 1, "...": "..." } } }
```

- Ключевое отличие от session-тула: `name` — это имя скилла, без префикса `skill_`. Поэтому распознавать вложенный запуск надо по payload: есть `run_id` (≥8 символов) и признак скилл-шага (`config_hash` либо `skill_id`) → это узел вложенного запуска. Ветку `skill_*` оставляем как есть.
- `depth` для заголовка берётся из payload (`skillDepth`), цена (`N LLM-вызовов`) — из загруженного трейса вложенного прогона, как сейчас.
- `getRun(run_id)` для такого запуска работает: `persist=False` означает лишь отсутствие результирующего документа, строка прогона есть.

## Критерии визуальной приёмки

- [ ] Шаг `type: "skill"` в STEPS показан бейджем `SKILL` (`badge-success`), отличимым от `SCRIPT` и `LLM`, вместе с id шага и бейджем входа.
- [ ] На skill-шаге нет строк «код не задан», «промпт не задан», блока модель/провайдер/reasoning и `allowed_tools`.
- [ ] «Подробнее» skill-шага показывает имя скилла и kind (когда снапшот есть) и короткий `config_hash` (8 символов) с полным хешем в `title`.
- [ ] Черновой skill-шаг без снапшота показывает `id: <skill_id>` и подсказку «имя и пин появятся при сборке»; шаг без `skill_id` — предупреждение «скилл не выбран».
- [ ] Счётчик «N шагов» в карточке черновика считает skill-шаги; строка «Шаги» отмечается готовой.
- [ ] Строки «Промпт» / «Скрипт» помечаются «не требуется» и исключаются из «Готово N из M», когда ни один шаг их не ждёт; pipeline из одних skill-шагов даёт «Готово 2 из 2 разделов».
- [ ] Подсказки под PROMPT и SCRIPT для pipeline соответствуют составу шагов (три варианта из таблицы) и не обещают подстановку в несуществующий шаг.
- [ ] В трейсе skill-шаг раскрывается узлом вложенного запуска с именем скилла, глубиной, ценой и статусом; внутри виден трейс вложенного прогона.
- [ ] Узел вложенного запуска грузится только при первом раскрытии и проходит состояния «Загружаю запуск…» / «Запуск не найден» / ошибка с «Повторить» / «Запуск ещё выполняется» с «Обновить».
- [ ] Дерево CATALOG-119/129 не изменилось: session-тулы `skill_*` на глубине ≥ 1 остаются несвёрнутой строкой с `· глубина N`, ограничители по-прежнему сворачиваются в свою плашку.
- [ ] Использованы только токены `docs/ui-style-guide.md`; новых CSS-классов и зависимостей нет.
