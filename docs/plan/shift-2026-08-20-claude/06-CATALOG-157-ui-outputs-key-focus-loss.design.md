# CATALOG-157 — Дизайн UI

- **Источник:** docs/plan/shift-2026-08-20-claude/06-CATALOG-157-ui-outputs-key-focus-loss.md
- **Статус дизайна:** Ready

## Цель и пользовательский путь

Шаг чинит поведение, а не внешний вид: визуальная разметка карточки **Outputs** остаётся
байт-в-байт прежней, меняется только модель идентичности строк и управление фокусом.

Пользовательский путь (редактор артефактов черновика скилла → карточка **Outputs**, а также
модалка настроек скилла, где `OutputsList` переиспользуется):

1. Пользователь жмёт «Добавить выход» → появляется пустая строка, каретка сразу в её поле «ключ».
2. Печатает многосимвольный ключ (`table`) — фокус и каретка остаются в поле на протяжении всего
   ввода, значение набирается целиком.
3. Переставляет строки кнопками ↑/↓ — визуально «едет» строка, а фокус едет вместе с ней, поэтому
   повторное нажатие ↑ двигает **ту же** строку дальше.
4. Удаляет строку кнопкой ✕ — фокус остаётся в колонке действий на той же позиции списка (или на
   «Добавить выход», если удалять больше нечего), клавиатурный сценарий не обрывается.
5. По клику «перейти к outputs» из подсказки панели фокус по-прежнему попадает в поле «ключ»
   первой строки (`firstKeyRef`).

Ключевой инвариант всего шага: **ни ввод текста, ни переключение чекбокса не должны приводить к
перемонтированию строки**. Строка списка — стабильный DOM-узел, привязанный к позиции, а не к
содержимому полей.

```
OutputsList (div.flex.flex-col.gap-2)
├── строка выхода × N  (div.rounded.border.border-line.bg-surface-muted.p-2)   ← key={index}
│   └── div.flex.items-start.gap-2
│       ├── div.min-w-0.flex-1
│       │   ├── шапка (div.mb-1.flex.items-center.gap-2)
│       │   │   ├── badge «основной» (только index === 0)

│       │   ├── label «описание» → input#outputs-desc-{index}.field
│       │   ├── label «несколько документов» → input#outputs-multiple-{index} (checkbox)
│       │   ├── p#outputs-multiple-hint-{index} «число документов определяется при прогоне»
│       │   └── ошибки строки: p#outputs-key-error-{index} / p#outputs-desc-error-{index} / p#outputs-multiple-error-{index}
│       └── колонка действий (div.flex.shrink-0.flex-col.gap-0.5)
│           ├── button ↑  aria-label="Поднять выход {label}"
│           ├── button ↓  aria-label="Опустить выход {label}"
│           └── button ✕  aria-label="Удалить выход {label}"
└── button «Добавить выход» (.btn-secondary.self-start), disabled при value.length >= MAX_SKILL_OUTPUTS
```

`label = row.key.trim() || String(index + 1)` — формула accessible name кнопок сохраняется.

## Layout и состояния

Layout не меняется: вертикальный стек строк с `gap-2`, внутри строки — контент слева
(`min-w-0 flex-1`) и колонка из трёх ghost-кнопок справа (`shrink-0`), под списком — кнопка
«Добавить выход» слева (`self-start`).

Состояния (все существующие, ничего не добавляется и не удаляется):

| Состояние | Что видно |
| --- | --- |
| Пустой список | нет строк, видна только кнопка «Добавить выход» |
| Первая строка | badge `основной` в шапке строки 0 (и только там — после ↑/↓/✕ badge всегда у верхней строки) |
| Ошибка поля | `aria-invalid` на input + красный текст `text-[11px] text-danger-ink` под полями |
| `disabled` | все input/checkbox/кнопки задизейблены, стили `disabled:*` из `.field`/`.btn-*` |
| Первая строка / последняя строка | ↑ задизейблена при `index === 0`, ↓ — при `index === value.length - 1` |
| Достигнут лимит | «Добавить выход» задизейблена, `title="максимум 8 выходов"` (`MAX_SKILL_OUTPUTS`) |

Единственное изменение разметки — атрибут `key` строки: вместо составного ключа со значением поля
используется индекс позиции (`key={index}`). Идентичность строки = её позиция в списке.

> В текущем файле это строка вида `<div key={`${index}-${row.key}`} className={ROW_CLS}>` — искать
> по содержимому, номер строки мог сместиться после соседних шагов прогона.

## Взаимодействия

### Ввод текста (главный сценарий бага)

- Ввод символа в «ключ» вызывает `updateRow(index, { key })` → новый массив → перерисовка.
- React-key строки при этом **не меняется**, DOM-узел `input#outputs-key-{index}` переиспользуется,
  фокус и позиция каретки сохраняются. Аналогично для «описание» и чекбокса.
- Никакого программного возврата фокуса при вводе быть не должно (это маскировка, а не фикс):
  фокус обязан сохраняться сам за счёт стабильного key.

### Модель фокуса при мутациях списка

Компонент хранит «намерение сфокусироваться» (`pendingFocus`), которое ставится в обработчике
мутации и отрабатывает в эффекте после коммита DOM.

- Хранилище ссылок: по одной записи на строку с элементами `key` (input), `up`, `down`, `remove`
  (кнопки); плюс ссылка на кнопку «Добавить выход». Существующий `keyRefs` может быть сохранён как
  есть или поглощён единой структурой — важно лишь, что `firstKeyRef` по-прежнему получает input
  «ключ» строки с `index === 0` (и `null`, когда список опустел).
- Эффект фокусировки должен срабатывать на **любой** мутации списка, а не только на изменении
  длины: зависимость эффекта — сам массив `value` (перестановка ↑/↓ длину не меняет). Если
  намерения нет — эффект ничего не делает.
- Устаревшие записи ссылок подрезаются под текущую длину списка, чтобы после удалений не остаться с
  «хвостом».

Таблица правил:

| Действие | Куда уходит фокус после перерисовки |
| --- | --- |
| «Добавить выход» | поле «ключ» новой (последней) строки — поведение сохраняется |
| ↑ на строке `i` | кнопка ↑ строки, оказавшейся на позиции `i - 1` (фокус едет за строкой); если ↑ там задизейблена (`i - 1 === 0`) — кнопка ↓ той же строки |
| ↓ на строке `i` | кнопка ↓ строки, оказавшейся на позиции `i + 1`; если ↓ там задизейблена (последняя позиция) — кнопка ↑ той же строки |
| ✕ на строке `i`, список не опустел | кнопка ✕ строки на позиции `min(i, value.length - 1)` — фокус остаётся на той же позиции списка |
| ✕ последней оставшейся строки | кнопка «Добавить выход» |

Обоснование: при `key={index}` DOM-узлы привязаны к позициям, поэтому без явного управления фокус
после ↑/↓ остался бы на кнопке «чужой» строки, а после удаления последней строки — потерялся бы на
`<body>`. Оба случая прямо названы в разделе «Что ломается при индексном key» плана.

### Корректность данных при перестановке и удалении

- Все input остаются полностью управляемыми: `value={value[index].key}` / `value[index].description`
  / `checked={value[index].multiple === true}`. После ↑/↓/✕ содержимое полей обязано соответствовать
  своей строке — «съезжания» значений быть не должно.
- Мутации по-прежнему пересобирают массив целиком (`map`/`slice`+`splice`/`filter`/spread) и уходят
  наверх через `onChange`; внутреннего state со значениями строк компонент не заводит.
- `id`/`aria-describedby`/`aria-label` пересчитываются от индекса и `row.key` при каждом рендере,
  поэтому после перестановки они автоматически соответствуют новому порядку.

## Стиль и токены

- Стек по ADR 0011: React 19 + Vite + TS + Tailwind v3. Новых зависимостей — ноль (в частности,
  `@testing-library/user-event` **не добавляется**; в тестах используется явный `.focus()` +
  `fireEvent.change`/`fireEvent.input`).
- Никаких новых CSS-классов в `frontend/src/index.css` и никаких новых утилит: используются уже
  существующие компонентные классы `.field`, `.btn-ghost`, `.btn-secondary`, `.badge-neutral` и
  токены `border-line`, `bg-surface-muted`, `text-ink-faint`, `text-danger-ink`, `accent-brand`.
- Размеры шрифтов строки остаются `text-[11px]` (лейблы/ошибки) и `text-[10px]` (подсказка).
- Цвет/рамка/отступы строки (`ROW_CLS`) и стили задизейбленных кнопок (`MOVE_DISABLED`) не меняются.

## Доступность (a11y)

- Фокус никогда не должен «проваливаться» в `<body>` после действия пользователя: каждое из
  действий добавления/перестановки/удаления заканчивается предсказуемым видимым фокусом по таблице
  выше. Фокусировать задизейбленный элемент запрещено — для этого в таблице заданы фолбэки.
- Программная фокусировка выполняется без прокрутки-рывка там, где это уместно; фокусируется всегда
  реальный интерактивный элемент (input или button), а не контейнер строки.
- Связки label→input сохраняются (input вложен в `<label>`, у каждого — уникальный `id` от индекса).
- `aria-invalid` + `aria-describedby` на полях с ошибкой и на чекбоксе (подсказка + ошибка) остаются
  без изменений; идентификаторы остаются уникальными в пределах списка.
- Accessible name кнопок ↑/↓/✕ (`Поднять/Опустить/Удалить выход {label}`) остаётся прежним; то, что
  он меняется по мере ввода ключа, — существующее и допустимое поведение, менять его в этом шаге не
  нужно.
- Клавиатурный сценарий «Tab до ↑, несколько раз Enter/Space» должен двигать одну и ту же строку.

- `OutputDraft` (`frontend/src/api.ts`) остаётся `{ key: string; description: string; multiple?: boolean }`.
  **Служебный id в модель не добавляется** — драфт сериализуется в артефакт (`serializeOutputs`), и
  посторонние поля туда попасть не должны.
- Публичный контракт компонента не меняется:
  `OutputsListProps = { value: OutputDraft[]; onChange: (next: OutputDraft[]) => void; disabled?: boolean; rowErrors?: (OutputRowError | null)[]; firstKeyRef?: Ref<HTMLInputElement> }`.
  Оба потребителя (`ArtifactsPanel`, `SkillSettingsModal`) продолжают работать без правок.
- Лимит строк — `MAX_SKILL_OUTPUTS` из `api.ts` (никаких локальных числовых литералов).
