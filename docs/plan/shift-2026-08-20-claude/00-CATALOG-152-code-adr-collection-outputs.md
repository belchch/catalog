- **Задача Plane:** [CATALOG-152](https://app.plane.so/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc/issues/960dfb94-ae4b-4a84-bddb-84af91072d83) (id: `960dfb94-ae4b-4a84-bddb-84af91072d83`, state: In Progress)

- **Тип шага:** code
- **Очередь:** 00 · независимый (рёбер в Plane нет) · по тексту ТЗ — первый шаг CATALOG-150, блокирует 01/02
- **Цель:** Принять ADR-0025: объявленный выход скилла получает флаг `multiple: true`, его значение — `list[str]`, и каждый элемент персистится отдельным `Document(kind="result_md")`. Только документ, кода не трогаем.

## Постановка задачи (актуальное ТЗ)
_(источник: описание задачи — комментариев не было)_

Тип: code (только документ). Порядок: первый шаг CATALOG-150, блокирует остальные.

**Контекст.** ADR-0024 зафиксировал фиксированный набор именованных выходов с разными ролями и явно отклонил «persist `list[str]` как N документов». Аргумент был верный для того решения: у голого списка нет роли, а позиция в нём ничего не значит. Но следствием стало то, что разбиение документа на главы выразить нечем вообще (CATALOG-150).

Разница, которую надо провести: **роль выхода** и **кратность выхода** — разные измерения. Роли обязаны быть заморожены (ADR-0002: повторяемость скилла), кратность — не обязана.

**Что зафиксировать в ADR:**

1. **Флаг `multiple` в декларации.** `SkillOutput` получает `multiple: bool = False`. Объявление остаётся частью замороженного конфига и входит в `config_hash`. Отсутствие ключа = `false`, старые конфиги читаются без миграции.
2. **Значение коллекционного выхода — `list[str]`**, каждый элемент становится отдельным `Document(kind="result_md")`. Значение обычного выхода — по-прежнему `str`. Несовпадение типа с декларацией — ошибка прогона, fail-closed.
3. **Primary может быть коллекцией — рекомендуемый вариант, но решается здесь.** Если `outputs[0].multiple`, то `result_text` = склейка элементов через `_value_as_text` (сегодняшняя семантика), а persist даёт N документов. То есть у коллекции два представления: «одно значение» (verify, шаг pipeline, skill-as-tool) и «N документов» (persist). Альтернатива — запретить `multiple` на `outputs[0]`; она проще, но делает невалидным чистый `split_by_chapters` без индекса. Взвесить и выбрать явно.
4. **Граница между шагами не меняется.** ADR-0018 и ADR-0024 остаются в силе: между шагами `pipeline` значение — `str | list[str]` и это **одно значение**. Коллекция раскрывается в документы только на финале top-level прогона. Промежуточные шаги документами не становятся.
5. **Два разных лимита.** `MAX_SKILL_OUTPUTS = 8` остаётся лимитом на **объявленные ключи**. Вводится второй лимит — на **число документов за прогон** (предложение: 50). Превышение — прогон `failed` с внятной причиной, а не молчаливое усечение: тихо потерять главы хуже, чем отказать.
6. **Пустая коллекция — ошибка.** Объявили выход и вернули `[]` — то же самое, что пустое значение в ADR-0024. Один элемент — легитимно (документ из одной главы). Пустая строка внутри списка — ошибка.
7. **Заголовки документов коллекции.** `{скилл} — {описание} {i}` читается плохо, когда документов два десятка. Зафиксировать: заголовок берётся из первого markdown-заголовка элемента, если он есть, иначе — из позиции. Столкновения имён разводит `allocate_rel_path`, как сейчас.
8. **Как рождается коллекция по `kind`.** `script` — sandbox возвращает `dict[str, str | list[str]]`. `agent` — `emit_output` вызывается по разу на элемент, для `multiple`-ключа вызовы **накапливаются**, а не перезаписывают (сегодня `sink[key] = text`, `emit_output.py:88-90`). `pipeline` — финальный шаг по своему типу.
9. **Verify по-прежнему на primary-тексте.** ADR-0007 не трогаем. Проверка каждого элемента коллекции — в CATALOG-148 к «verify с адресацией на артефакт».
10. **Вложенный apply не меняется.** ADR-0019 и ADR-0022 в силе: `persist=False`, документов не создаётся.

**Почему ADR, а не сразу код.** ADR-0025 частично пересматривает решение ADR-0024 (там вариант «`list[str]` → N документов» отклонён явным текстом). Пересмотр принятого ADR обязан быть записан отдельным документом с обоснованием — иначе в `docs/adr/` останется противоречие, и следующий шаг (CATALOG-153) будет опираться на неписаную договорённость.

**Пункт 3 — единственное открытое решение.** Оно влияет на CATALOG-153 напрямую: разрешение `multiple` на `outputs[0]` определяет, нужен ли в рантайме отдельный путь для «primary-коллекция» (склейка в `result_text` + N документов в persist). Рекомендация плана — **разрешить**, потому что запрет делает невыразимым чистый `split_by_chapters` без индекса, а склейка primary в один текст у нас уже есть в `_value_as_text` и работает.
