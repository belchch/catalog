# CATALOG-157 — ui: панель Outputs — поле «ключ» теряет фокус после каждого символа

- **Задача Plane:** [CATALOG-157](https://app.plane.so/belchch/projects/84997489-c485-4448-9ebe-0a06c4fa3cbc/issues/1ec9b33a-ce73-42ed-b409-81e2339812af) (id: `1ec9b33a-ce73-42ed-b409-81e2339812af`, state: In Progress)
- **Статус плана:** Analyzed
- **Тип шага:** ui
- **Очередь:** 06 · независимый
- **Цель:** Убрать значение поля из React-key строки `OutputsList`, чтобы ввод символа не перемонтировал строку и `input` не терял фокус; закрыть регрессионным тестом на `document.activeElement`.

## Постановка задачи (актуальное ТЗ)
_(источник: описание задачи — комментариев не было)_

**Симптом.** В редакторе артефактов черновика скилла, в карточке **Outputs**, поле «ключ» теряет фокус после ввода каждого символа. Набрать многосимвольный ключ (например `table`) невозможно — после первой буквы нужно заново кликать в поле. Поле «описание» работает нормально.

**Причина.** `frontend/src/components/OutputsList.tsx:76` — React-key строки списка включает значение самого поля:

```
<div key={`${index}-${row.key}`} className={ROW_CLS}>
```

Ввод символа меняет `row.key` → меняется React-key → React размонтирует и монтирует строку заново → `input` теряет фокус. Найдено при ревью ветки `pipeline/shift-2026-08-20` (CATALOG-146).

**Воспроизведение.**
1. Открыть «Черновик скилла» → «Редактор артефактов» → карточка **Outputs**.
2. Нажать «Добавить выход».
3. Поставить курсор в поле «ключ» и набрать `table`.

**Ожидается:** в поле `table`. **Фактически:** в поле `t`, фокус потерян, остальные символы никуда не попали.

**Фикс.** Сделать React-key стабильным относительно ввода: `key={index}` (как в `StepsList.tsx`, где порядок тоже меняется кнопками ↑↓) либо завести на строку стабильный id, не зависящий от содержимого полей.

**Definition of Done.**
- В поле «ключ» можно набрать многосимвольное значение без потери фокуса.
- Кнопки ↑ / ↓ / ✕ и «Добавить выход» продолжают работать корректно (значения не «съезжают» между строками при перестановке и удалении).
- Добавлен регрессионный тест в `frontend/src/components/ArtifactsPanel.test.tsx` (или отдельный `OutputsList.test.tsx`), который проверяет именно **сохранение фокуса**: `fireEvent.change` этого не ловит — нужно проверять `document.activeElement` после ввода символа.

**Заметка.** Существующие тесты баг не видят, потому что `fireEvent.change` не зависит от фокуса. Проверено вручную: после одного символа `document.activeElement` перестаёт быть этим input.

## Контекст

**Баг подтверждён в коде.** [frontend/src/components/OutputsList.tsx:76](frontend/src/components/OutputsList.tsx:76) — ровно та строка, что в ТЗ: `<div key={`${index}-${row.key}`} className={ROW_CLS}>`. Поле «описание» не страдает, потому что в key входит только `row.key`.

**Почему `key={index}` здесь безопасен.** Список короткий (максимум 8 — [api.ts:685](frontend/src/api.ts:685)), рендерится целиком из `value`, и все мутации идут через `onChange` с пересборкой массива: `updateRow` — [:43](frontend/src/components/OutputsList.tsx:43), `move` — [:47](frontend/src/components/OutputsList.tsx:47), `remove` — [:56](frontend/src/components/OutputsList.tsx:56), `add` — [:60](frontend/src/components/OutputsList.tsx:60). Прецедент в том же проекте — [frontend/src/components/StepsList.tsx](frontend/src/components/StepsList.tsx), где порядок тоже меняется кнопками ↑↓.

**Что ломается при индексном key и на что смотреть.** Управляемые `input` берут значение из `value[index]`, поэтому «съезжания» быть не должно. Но при `remove`/`move` DOM-узел переиспользуется под другую строку — надо убедиться, что:
- фокус после удаления/перестановки не оказывается в чужой строке неожиданно для человека;
- `keyRefs` — [:34](frontend/src/components/OutputsList.tsx:34) и отложенная фокусировка после `add` — [:36-41](frontend/src/components/OutputsList.tsx:36) продолжают работать (эффект завязан на `value.length`);
- `firstKeyRef` — [:87](frontend/src/components/OutputsList.tsx:87) по-прежнему указывает на первую строку.

**Альтернатива — стабильный id строки.** Надёжнее при перестановках, но требует менять форму `OutputDraft` ([api.ts:687](frontend/src/api.ts:687)) либо держать параллельный массив id в компоненте. `OutputDraft` сериализуется в артефакт (`serializeOutputs` — [api.ts:730](frontend/src/api.ts:730)), поэтому служебный id туда попасть не должен. План выбирает **`key={index}`** как минимальное изменение; вариант с id — запасной, если при реализации всплывёт проблема с перестановкой.

**Соседи по файлу.** `OutputsList` в этом же прогоне правят CATALOG-154 (план `02-…`, переключатель «несколько документов») и переиспользует CATALOG-155 (план `04-…`, блок «Выход» в форме сохранения). Если этот шаг едет позже них, строка с key могла сместиться — искать по содержимому, а не по номеру.

**Про тест.** `fireEvent.change` баг не ловит — это записано в самом ТЗ. Нужен ввод, который проходит через фокус: `userEvent.type` (если `@testing-library/user-event` уже в зависимостях) либо ручная последовательность `focus` + `fireEvent.change` с проверкой `document.activeElement` после каждого символа. Проверять надо именно `document.activeElement === input` после ввода **второго** символа — после первого баг уже проявляется.
