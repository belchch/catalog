# ADR 0018: Pipeline-скилы (kind=pipeline) — python + LLM в одном скиле

- **Date:** 2026-08-15
- **Status:** Accepted
- **Extends:** ADR-0002, ADR-0014
- **Related:** ADR-0008 (системный скилл = тул), CATALOG-84

## Context

`kind` сегодня бинарный и зашит в рантайм: `apply` ветвится на
`kind="script"` (sandbox, без LLM) и `kind="agent"` (function-calling loop).
Агент не может выполнить python — базовый реестр инструментов содержит только
`list_documents` и `read_document`. Скрипт не может обратиться к модели —
sandbox синхронный, с таймаутом 5 с, без сети.

Класс задач «разбить → обработать каждый кусок → собрать» (конспект по
разделам длинного регламента, проверка пачки документов по чеклисту,
извлечение сущностей из реестра на сотни строк) недостижим ни одним из
существующих типов. `compute_tags` уже документирует «genuinely mixed skill»
с обоими тегами `python` и `ai`, но рантайма под это нет.

## Decision

Третий тип скила — `kind="pipeline"`:

- Скил = **последовательность шагов**. Шаг — либо `script` (существующий
  `run_script` / sandbox), либо `llm` (существующий `_run_agent_core`).
- **Контракт значения между шагами:** строка либо список строк. Заложен сразу,
  чтобы шаг `map` (fan-out по списку) добавлялся без миграции конфигов.
- **Модель, провайдер и reasoning** объявляются на llm-шаге в схеме конфига.
  UI-переопределение отложено: в первой версии значения задаются в конфиге
  или правятся диалогом в чате-планировщике.
- **Verify** только на финальном результате, без retry (перезапуск пайплайна
  дорог; retry agent-лупа из ADR-0007 для pipeline не применяется).
- **Промежуточные значения** шагов не становятся документами (ADR-0006
  сохраняет только финал); живут в трейсе.
- **Оркестрация детерминирована конфигом** — в отличие от agent-скила, где
  порядок действий выбирает модель в рантайме. Недетерминизм остаётся только
  внутри отдельных llm-шагов.
- **Sandbox не меняется.** LLM внутрь песочницы не попадает; ADR-0014
  остаётся в силе целиком.

Первая поставка — линейная цепочка `script → llm → script` плюс создание
такого скила из чата (артефакт сессии `steps`, тул `save_skill_steps`).
Шаг `map` / fan-out — отдельный этап (см. связанные задачи Plane).

## Consequences

**Плюсы:**
- Закрывается класс задач, недоступный ни `agent`, ни `script`.
- Оркестрация возвращается в замороженный конфиг (ADR-0002 усиливается).
- Исполнители переиспользуются без дублирования sandbox и agent-loop.
- Контракт «строка | список строк» позволяет добавить map без ломки схемы.

**Минусы / риски:**
- Стоимость выше: системный промпт повторяется на каждом llm-шаге.
- Схема шагов и трейс усложняются; UI должен рисовать шаги как структуру.
- Промпт планировщика получает третий вариант выбора `kind` — риск снижения
  качества автоопределения типа; смягчается опорой на эталоны/шаблоны.

## Alternatives considered

- **`run_script` как тул с кодом от модели (code interpreter)** —
  отклонено для воспроизводимого скилла: оркестрацию и код выбирает
  модель в рантайме. Вызов *замороженного* script-скилла как тула —
  отдельное решение (ADR-0019), не путать.
- **Функция `llm(prompt)` внутри sandbox** — отклонено: требует переписать
  исполнитель на subprocess с RPC, уничтожает детерминизм скрипта (ADR-0014)
  и делает стоимость запуска неограниченной (цикл вызовов модели из кода).
- **Только линейная цепочка без контракта списка** — отклонено: введение map
  позже потребовало бы миграции схемы; цена заложить «строка | список» сейчас
  минимальна.

## Relation to ADR-0002 / ADR-0014 / ADR-0008

ADR-0002 остаётся в силе для `kind="agent"` и усиливается для pipeline:
порядок шагов тоже заморожен. ADR-0014 остаётся в силе для script-шагов.
ADR-0008 (системный скилл = тул, вызываемый моделью) — контекст направления,
в котором пользовательские скилы позже могут расширять tool calling; витрина
системных скилов и расширение tooling — вне объёма этого ADR.
