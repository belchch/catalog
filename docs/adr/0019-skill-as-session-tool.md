# ADR 0019: Пользовательский скилл как вызываемый тул сессии

- **Date:** 2026-08-16
- **Status:** Accepted
- **Extends:** ADR-0002, ADR-0008, ADR-0014, ADR-0015
- **Clarifies:** ADR-0018 (альтернатива `run_script` как тул)

## Context

Базовый реестр инструментов агента содержит только `list_documents` и
`read_document`. Пользовательские скиллы — замороженные операции — не
доступны планировщику как callable tools.

ADR-0018 отклонил «`run_script` как тул», потому что в той формулировке
`code` генерирует модель на каждом вызове (code interpreter). Это другая
задача: здесь код уже заморожен в `config_json` скилла.

Открытые вопросы первого среза: вход текстом или документами; как пинить
версию; какие `kind` допускать; куда класть вложенный результат.

## Decision

1. К сессии прикрепляются скиллы (`session_skill`), по аналогии с
   `session_document`. Прикрепление = разрешение модели вызвать скилл.
   REST: `/sessions/{id}/tools` (не `/sessions/{id}/skills` — путь занят
   билдом).
2. Каждый прикреплённый `kind="script"` скилл регистрируется как tool в
   WS-сессии. Имя — slug `skill_<name>`, `^[a-z0-9_]+$`, без коллизий с
   document/artifact tools. `agent` и `pipeline` — позже.
3. Вызов создаёт отдельный `skill_run` с `parent_run_id` и прогоняет
   `verify_checks` вызванного скилла. Первый срез: глубина 1, без
   рекурсии (вложенный скилл не получает чужие skill-тулы).
4. **Вход — текст** (`text` или `texts`), не документ. `_apply_core`
   принимает `input_texts` без загрузки `input_doc_ids`.
5. **Пин версии** — id скилла + SHA-256 префикс `config_json` (через
   `SkillConfig.to_json()`) на момент вызова; пишется в трейс и в ответ
   тула.
6. **Вложенный результат — в модель**, не как документ: `persist=False`,
   `result_text` возвращается в tool result. Материализация в
   `result_md` (ADR-0006) остаётся у top-level apply.
7. Для вызова из планировщика (нет родительского `skill_run`)
   `parent_run_id` = `"session"`. `session_id` на строке run и так есть.

## Consequences

**Плюсы:** композиция без code interpreter; verify как постусловие;
дерево запусков через `parent_run_id`; воспроизводимость через пин
конфига.

**Минусы / риски:** рост стоимости при расширении на agent/pipeline;
нужен поиск в UI при большом числе скиллов; sentinel `"session"` — не
UUID run.

## Alternatives considered

- **Читать скилл как инструкцию в чате** — отклонено: модель может
  отклониться от сценария; нет отдельного run и verify.
- **Все committed скиллы workspace всегда в реестре** — отклонено:
  нет явного разрешения пользователя; перегрузка контекста.
- **Вход документами** — отложено: вложенный вызов часто работает с
  промежуточным текстом, не с `document` row.
- **Пин по `skill.updated_at` / номеру версии** — отклонено: у скилла
  нет версионной таблицы; хэш `config_json` фиксирует содержимое.
- **Code interpreter (`run_script` с code от модели)** — остаётся
  отклонённым для воспроизводимых скиллов (ADR-0018); не путать с
  вызовом замороженного script-скилла.
- **Persist вложенного результата как Document** — отклонено в первом
  срезе: засоряет workspace промежуточными артефактами; модель получает
  текст напрямую.

## Relation to ADR-0018 / ADR-0006

Формулировка «`run_script` как тул отклонено» относится к генерации
кода моделью в рантайме. Вызов замороженного `kind=script` скилла как
тула — этот ADR; ADR-0018 остаётся в силе для sandbox и pipeline.

ADR-0006 сохраняет силу для top-level apply. Вложенный skill-as-tool
вызов — исключение: результат живёт в `skill_run.result_text` и в
ответе тула, не в `Document`.
