# ADR 0016: Workspace-as-folder

- **Date:** 2026-08-14
- **Status:** Accepted
- **Revises / partially supersedes:** ADR-0012 (отказ от dulwich git-репо и единого `catalog.db` в data-root как модели воркспейса; folder-picker становится end-user)
- **Clarifies:** ADR-0005 (ФС = открытая папка пользователя; SQLite — workspace `index.db` + глобальная БД), ADR-0008 (FTS5 живёт в workspace `index.db`)

> В Plane задача CATALOG-76 называла это «ADR-0013». Номер сдвинут на **0016**, потому что `0013-multi-provider-and-zai.md` уже занят (Accepted).

## Context

ADR-0012 зафиксировал data-root вне исходников (`APP_DATA_DIR`), единый `catalog.db` и два app-owned git-репозитория на dulwich (`documents/`, `skills/`). Folder-picker оставался admin/env, не end-user UI.

Продукт переходит на модель «воркспейс = папка пользователя»: документы лежат там, куда их положил пользователь; бизнес-состояние — в `.catalog/index.db` внутри этой папки; глобально остаются только настройки и реестр воркспейсов. Доставка становится нативной (Docker перестаёт быть основным способом запуска). Старый `catalog.db` и dulwich-репо внутри user-folder больше не целевая модель.

## Decision

1. **Воркспейс = произвольная папка пользователя.** Маркер воркспейса — каталог `.catalog/`. Бизнес-БД: `.catalog/index.db`. Контент документов — обычные файлы в дереве папки (источник истины — ФС).

2. **Две базы SQLite.**
   - **Workspace** (`.catalog/index.db`): таблицы `document`, `session`, `session_document`, `message`, `session_artifact`, `skill`, `skill_run` — тот же состав, что сейчас в `backend/app/storage/schema.py` для единой БД.
   - **Глобальная** (вне воркспейса, в app data / OS-каталоге настроек): настройки приложения и **реестр воркспейсов** (пути открытых/известных папок). Без бизнес-таблиц сессий/документов/скиллов.

3. **Открытие и переключение.** Пользователь выбирает папку (end-user folder-picker). Переключение на другой воркспейс **блокируется**, пока есть активные `skill_run` со статусом `running`.

4. **Три уровня проверки при открытии** (по порядку; следующий — только если предыдущий прошёл):
   1. Маркер `.catalog/` + `PRAGMA user_version` (совместимость схемы).
   2. `PRAGMA quick_check` по `index.db`.
   3. Ре-скан файлов папки и сверка/обновление индекса `document`.

5. **Папка с файлами без `.catalog`.** Не молчаливая инициализация. Требуется **явное подтверждение** пользователя («инициализировать как воркспейс Catalog?»), после которого создаются `.catalog/` и `index.db`.

6. **Имена файлов.** Без slug-переименования при индексации. `document.path` = путь к файлу там, где его положил пользователь (относительно корня воркспейса).

7. **Бэкапы `index.db`.** Ротация копий в `.catalog/backups/` (перед опасными операциями / по политике приложения). Сами документы в бэкап БД не входят — они на ФС.

8. **Отказ от dulwich git-репо в пользовательской папке.** Пункты ADR-0012 про два app-owned репо (`documents/`, `skills/`), dulwich как модель версий документа и «версия = коммит» **не применяются** к user-folder воркспейсу. Внутренние app-owned git-репо больше не модель воркспейса. Версионирование через git в папке пользователя — вне этой модели (может вернуться отдельным ADR, если понадобится).

9. **FTS5.** Задел: полнотекстовый индекс живёт в workspace `index.db`. Поведение и контракт — по ADR-0008 (системный скилл/инструмент `search_documents`, не UI-поле поиска). Реализация FTS — отдельный шаг после среза.

10. **Чистый разрыв со старым `catalog.db`.** Миграции данных из прежнего data-root / `catalog.db` **нет**. Пользователь открывает папку заново; индекс строится с нуля (или после явной инициализации).

## Consequences

**Плюсы:**
- Папка пользователя = понятный источник истины; документы не спрятаны в docker-томе / data-root.
- Нативная доставка совпадает с моделью данных (открыл папку — работаешь).
- SQLite остаётся пересобираемым индексом над ФС (инвариант ADR-0005), но scope индекса — одна папка.
- Несколько воркспейсов без смешивания бизнес-данных.

**Минусы / риски:**
- Нет переноса сессий/скиллов/истории из старого `catalog.db`.
- Нет git-версий и diff «из коробки» в user-folder (пересмотр ADR-0012).
- Пользователь может повредить `.catalog/` вручную — отсюда уровни проверки и бэкапы.
- Переключение воркспейса во время ранов запрещено — UX должен это объяснять.

## Alternatives considered

- **Оставить data-root + dulwich (ADR-0012 as-is)** — отклонено: противоречит «папка = воркспейс» и нативной доставке; folder-picker оставался бы admin-only.
- **Мигрировать старый `catalog.db` в `.catalog/index.db`** — отклонено: хрупкий one-shot, разные layout путей; выбран чистый разрыв.
- **Молча создавать `.catalog` при открытии любой папки** — отклонено: риск неожиданной записи в чужие каталоги; нужно явное подтверждение.
- **Одна глобальная БД + пути к документам вне папки** — отклонено: ломает переносимость «скопировал папку — унёс воркспейс».

## Relation to ADR-0005 / ADR-0008 / ADR-0012

- **ADR-0005** остаётся в силе по разделению ФС (контент) / SQLite (системные данные). Уточняется место: контент — в выбранной папке; workspace-системные данные — в `.catalog/index.db`; глобальные настройки/реестр — отдельно.
- **ADR-0008** без смены решения (FTS = системный скилл); физически FTS5 размещается в workspace `index.db`.
- **ADR-0012** частично superseded этим ADR в части модели воркспейса (единый `catalog.db`, dulwich-репо в data-root как user workspace, folder-picker = только admin). Абсолютный app data dir для *глобальных* настроек/реестра может сохраниться; это не замена user-folder воркспейса.
