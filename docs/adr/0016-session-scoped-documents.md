# ADR 0016: Документы видны агенту только через сессию

- **Date:** 2026-07-24
- **Status:** Accepted
- **Revises:** ADR-0003 (уточняет область видимости tool layer)

## Context

ADR-0003 зафиксировал tool layer (`list_documents`, `read_document`) как
общий слой для любого скилла, но не сказал ничего про **область видимости**:
инструменты работали над всей таблицей `document`. На практике это дало два
дефекта:

1. Планировщик в чате «видел» всю библиотеку и подтягивал в рассуждения
   посторонние документы, о которых пользователь в этой сессии не говорил.
2. Не было понятия «документы этой задачи» — ни в UI, ни в промпте; контекст
   сессии определялся только текстом переписки.

## Decision

**Единица видимости — сессия.** Агент (планировщик и прогон скилла) видит не
библиотеку, а множество документов, привязанных к его сессии.

1. **Таблица `session_document(session_id, document_id, attached_at)`**
   (`backend/app/storage/schema.py`) — many-to-many привязка. Библиотека
   (`document`) остаётся глобальной; сессия задаёт срез.

2. **Инструменты параметризуются сессией.**
   `build_document_tools(db, workspace, session_id=None)`
   (`backend/app/documents/tools.py:15`):
   - с `session_id` — `list_documents` отдаёт только привязанные документы,
     а `read_document` для непривязанного возвращает
     `{"error": "document_not_available_in_session"}`
     (`backend/app/documents/tools.py:38`);
   - без `session_id` — глобальный реестр (`app.state.tools`): используется
     как база для валидации имён при сборке скилла и для прогонов без сессии.

   Ошибка возвращается **в модель как результат инструмента**, а не как
   исключение: агент должен уметь понять отказ и продолжить, а не упасть.

3. **Точки привязки (attach):**
   - кадр пользователя в WS планировщика `{"type":"user", "doc_ids":[…]}`
     (`backend/app/api/sessions.py:666`);
   - `POST /skills/{id}/apply` с `session_id` — входы прогона привязываются
     до старта (`backend/app/api/runs.py:87`), иначе scoped-инструменты
     отвергли бы явно выбранный пользователем вход;
   - **результат прогона привязывается автоматически** — и при
     `persist=true` (`backend/app/skills/apply.py:377`), и при отложенном
     `POST /runs/{id}/save` (`backend/app/api/runs.py:163`), так что вывод
     скилла сразу становится доступным входом следующего шага в той же сессии.

4. **Отвязка (detach)** — `DELETE /sessions/{id}/documents/{doc_id}`;
   `GET /sessions/{id}/documents` отдаёт текущий срез, WS дублирует его
   кадром `session_docs`.

5. **Промпт планировщика** дополняется списком привязанных документов
   (`_planner_system_prompt`, `backend/app/api/sessions.py:153`) — модель
   знает свой срез до первого вызова инструмента.

## Consequences

**Плюсы:** контекст агента управляем и предсказуем; «документы задачи» —
явная сущность в API и UI; цепочка «результат → вход следующего скилла»
работает без ручной привязки.

**Минусы / риски:** прогон без `session_id` по-прежнему видит всю библиотеку
(осознанное исключение для запусков вне чата); срез — плоское множество без
ролей (вход/референс/результат неразличимы); будущий FTS (ADR-0008) обязан
уважать scope, иначе поиск станет дырой в изоляции.

## Alternatives considered

- **Фильтровать только промптом** («используй документы X, Y») — отклонено:
  инструмент остаётся дырой, модель может прочитать что угодно.
- **Копировать документ в сессию** — отклонено: дублирование контента ломает
  «ФС — источник истины» (ADR-0005) и рвёт связи результата с оригиналом.
- **RBAC/ACL поверх документов** — отклонено: мультипользователь — non-goal
  (ADR-0010); сессия даёт нужную изоляцию бесплатно.
