# ADR 0020: LLM-судья как отдельный тип пользовательской проверки

- **Date:** 2026-08-16
- **Status:** Accepted
- **Extends:** ADR-0007
- **Related:** ADR-0019

## Context

Реестр детерминированных проверок (ADR-0007) не оценивает семантику.
Пользователь хочет сохранять критерии вроде «резюме содержит опыт Python ≥ 3 лет»
и выбирать их в `verify_checks` рядом со стандартными.

ADR-0007 отклонил «верификацию только LLM» как единственный механизм; LLM-судья
был отложен как отдельный слой.

## Decision

1. Пользовательские проверки хранятся в workspace-таблице `custom_check`
   (`id`, `name`, `prompt`, `hidden`, timestamps).
2. В `verify_checks` допускается `{ check: "custom:<id>" }` или
   `{ check: "custom", params: { id } }` — второй тип, не часть
   детерминированного реестра.
3. Порядок: сначала все детерминированные; LLM-судья только если они
   прошли. Судья получает результат и критерий, без system_prompt
   исполнителя.
4. UI: попап выбора «Стандартные» / «Мои проверки» + «Новая проверка»
   (название, промпт, прогон на примере). Удаление не делаем —
   только `hidden=1`, чтобы не ломать ссылки в скиллах.

## Consequences

**Плюсы:** семантика без ломки ADR-0007; стоимость контролируется порядком.

**Минусы:** LLM-судья дороже и недетерминирован; нужна модель/провайдер
на момент verify.

## Alternatives considered

- **Подмешать в детерминированный реестр** — отклонено: ломает контракт.
- **Script-скилл как validator** — отложено; промпт покрывает основной кейс.
- **Жёсткое удаление проверок** — отклонено: fail-closed `run_verify`
  ломает существующие скиллы.
