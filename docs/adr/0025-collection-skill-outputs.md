# ADR 0025: Коллекционный выход скилла — `multiple: true` и N документов

- **Date:** 2026-08-20
- **Status:** Accepted
- **Extends:** ADR-0024
- **Does not change:** ADR-0018, ADR-0019, ADR-0022
- **Related:** CATALOG-150, CATALOG-152, CATALOG-153, CATALOG-154

## Context

ADR-0024 дало скиллу именованные выходы: `primary` + `companions`, каждый —
ровно один `Document(kind="result_md")`. Этого хватает, когда число ролей
известно на этапе объявления конфига (текст + таблица перекодировки), но не
хватает, когда роль одна, а элементов — заранее неизвестное число: скилл
`split_by_chapters` (CATALOG-150) режет документ на главы, и число глав
зависит от содержимого конкретного входного файла, а не от конфига скилла.

ADR-0024 явно отклонил вариант «persist `list[str]` как N документов»
(раздел Alternatives considered) — но отклонение было о другом кейсе: голом
`list[str]` без декларации, где позиция в списке не несёт роли и легко
перепутать «глава 1» с «псевдонимизированный текст». Этот ADR **частично
пересматривает** тот вывод, вводя третье измерение декларации.

Разница между этим решением и отклонённым в ADR-0024 — что именно объявлено:

| | ADR-0024 «отклонено» | ADR-0025 |
|---|---|---|
| Роль | не объявлена (голый список) | объявлена (`key`, `description`) |
| Множественность | не объявлена | объявлена (`multiple: bool`) |
| Число элементов | неизвестно и не различимо от роли | неизвестно, но это единственное неизвестное |

Иными словами: **роль выхода** и **кратность выхода** — разные измерения.
Роли обязаны быть заморожены вместе со скиллом (ADR-0002: воспроизводимость),
кратность — не обязана: она известна только на прогоне, как число глав в
конкретном документе. Поднятие `MAX_SKILL_OUTPUTS` (сейчас 8) эту проблему не
решает — число глав не ограничено сверху заранее и не совпадает с числом
объявленных ключей.

## Decision

1. **Флаг `multiple` в декларации.** `SkillOutput` получает поле
   `multiple: bool = False`. Объявление — часть замороженного конфига
   (ADR-0002) и участвует в `config_hash` (`backend/catalog/skills/apply.py`
   `_config_hash`, через сериализацию `SkillConfig.to_json`). Отсутствие
   ключа в `config_json` дефолтит в `false` — старые конфиги читаются без
   миграции, как уже сделано для `input_arity` и `kind` (ADR-0024, п.1).

2. **Значение коллекционного выхода — `list[str]`.** Каждый элемент списка
   персистится отдельным `Document(kind="result_md")`. Значение
   `multiple: false`-выхода — по-прежнему `str`, как в ADR-0024. Несовпадение
   типа значения с декларацией (`multiple: true`, но пришла строка; или
   `multiple: false`, но пришёл список) — ошибка прогона, fail-closed, как
   остальные проверки формы в `_match_named_outputs`.

3. **Primary может быть коллекцией.** Разрешено объявить
   `outputs[0].multiple = true`. Тогда:
   - `result_text` (значение для verify, значение шага pipeline, ответ
     skill-as-tool) — склейка элементов через `_value_as_text`, то есть
     сегодняшнее поведение `"\n\n---\n\n".join(value)` (`apply.py:102`);
   - `persist_run_outputs` разворачивает тот же список в N документов, а не
     в один.
   У коллекции, объявленной на `outputs[0]`, тем самым два представления
   одного значения: «одно значение» (verify / шаг pipeline / skill-as-tool)
   и «N документов» (persist). Это не новая механика поверх ADR-0018 — оба
   представления уже существуют по отдельности (`_value_as_text` и
   `_value_as_documents`), решение лишь разрешает их одновременное
   применение к одному объявленному ключу.

   Альтернатива — запретить `multiple` на `outputs[0]` — рассмотрена и
   отклонена: см. подраздел «Primary-коллекция» ниже.

4. **Граница между шагами pipeline не меняется.** ADR-0018 и ADR-0024
   остаются в силе: значение между шагами `pipeline` — `str | list[str]`, и
   это **одно значение** (заготовка под будущий `map`). Коллекция
   раскрывается в документы только на финале top-level прогона — либо у
   скилла без шагов, либо на последнем шаге `pipeline`. Промежуточные шаги
   документами не становятся, как и сегодня.

5. **Два разных лимита.** `MAX_SKILL_OUTPUTS = 8` (`config.py:19`) остаётся
   лимитом на **число объявленных ключей** — не меняется этим ADR. Вводится
   отдельный `MAX_COLLECTION_DOCUMENTS = 50` — лимит на **число документов,
   рождаемых элементами коллекций за один прогон** (сумма по всем
   `multiple`-ключам). Превышение — прогон завершается `failed` с явной
   причиной («too many collection documents: N (max 50)»), а не молчаливым
   усечением: тихая потеря глав хуже отказа.

6. **Пустая коллекция — ошибка.** Объявленный `multiple`-выход, вернувший
   `[]`, — та же ошибка, что пустое значение обычного выхода в ADR-0024
   (`_match_named_outputs`, ветка `empty`). Один элемент — легитимно
   (документ из одной главы, если делить было не на что). Пустая строка
   внутри непустого списка — ошибка (элемент коллекции подчиняется тому же
   правилу «непустой текст», что и обычный выход).

7. **Заголовки документов коллекции.** Правило `{skill.name} — {description}
   {i}` (по аналогии с `_primary_result_title`) не масштабируется на два
   десятка документов. Заголовок элемента коллекции — первый markdown-
   заголовок (строка вида `# ...`) внутри текста элемента, если он есть;
   иначе — `{skill.name} — {description} {позиция}` (1-based). Столкновения
   итоговых имён файлов разводит `allocate_rel_path`
   (`backend/catalog/documents/ingest.py:136`) так же, как для остальных
   результатов — отдельного механизма для коллекций не вводится.

8. **Как рождается коллекция по `kind`.**
   - `script` — sandbox возвращает `dict[str, str | list[str]]`: значение по
     ключу с `multiple: true` — список строк, по остальным ключам — строка,
     как в ADR-0024.
   - `agent` — `emit_output(key, text)` вызывается по разу на **каждый
     элемент** коллекции. Для `multiple`-ключа вызовы **накапливаются** в
     список, а не перезаписывают друг друга — меняется
     `register_emit_output` (`emit_output.py:88-90`, сегодня `sink[key] =
     text`): для ключей из `multiple`-выходов накопитель — список, `append`
     на каждый вызов; для остальных ключей поведение не меняется
     (перезапись, как сегодня). Модель заканчивает коллекцию явным сигналом
     о завершении хода (существующий retry-цикл ADR-0007), а не отдельным
     тулом — новый тул под «конец коллекции» не вводится.
   - `pipeline` — финальный шаг производит набор по своему типу, как в
     ADR-0024 (п.5): `script` → `dict`, `llm`/`agent` → `emit_output`.

9. **Verify по-прежнему на primary-тексте.** ADR-0007 не трогаем: проверка
   видит `result_text` — для `multiple`-primary это склейка через
   `_value_as_text`, то есть один текст, как и для обычного primary.
   Проверка каждого элемента коллекции по отдельности — предмет CATALOG-148
   («verify с адресацией на артефакт»), не этого ADR.

10. **Вложенный apply не меняется.** ADR-0019 и ADR-0022 остаются в силе:
    `persist=False` — ни companions, ни элементы коллекции не становятся
    документами при вложенном вызове скилла. Значение шага — `result_text`
    (primary, для `multiple`-primary — склейка).

### Primary-коллекция: разрешить или запретить `multiple` на `outputs[0]`

Рассмотрены два варианта:

- **Разрешить** (выбрано). `outputs[0].multiple = true` даёт `result_text` =
  склейка + N документов из persist. Цена: у одного объявленного ключа два
  представления значения одновременно, и код обязан их синхронизировать
  (persist берёт список поэлементно, verify/шаг pipeline — склейку того же
  списка). Не противоречит ADR-0007 (verify видит один текст, как и раньше)
  и ADR-0018 (шаг pipeline видит `list[str]`, что уже входит в контракт
  `PipelineValue = str | list[str]`, `apply.py:91`).
- **Запретить.** Проще в реализации (persist коллекций — только для
  companions, primary всегда `str`), но делает невыразимым чистый
  `split_by_chapters` без индекса: скиллу с одним выходом («главы») пришлось
  бы либо держать одноимённый фиктивный companion, либо всегда требовать
  второй, «настоящий» primary-ключ рядом с коллекцией — искусственное
  усложнение декларации ради обхода запрета.

Выбор: **разрешить** `multiple` на `outputs[0]`. Цена явно принята: primary
с `multiple: true` живёт в двух представлениях одновременно, и оба уже
существуют как отдельные функции (`_value_as_text`, `_value_as_documents`) —
решение обязывает применять обе к одному значению, а не вводит новую
механику.

## Alternatives considered

- **Поднять `MAX_SKILL_OUTPUTS` выше 8** — отклонено: число глав неизвестно
  до прогона и не привязано к числу объявленных ключей конфига; поднятие
  константы не даёт скиллу способа сказать «сколько выйдет — не знаю
  заранее», а лишь двигает потолок, который всё равно будет либо занижен,
  либо избыточен.
- **`list[str]` → N документов без декларации** — тот же вариант, что
  отклонён в ADR-0024, и остаётся отклонённым в общем виде: без объявленной
  роли и множественности рантайм не отличит «список из двух ролей» от
  «список из двух глав». ADR-0025 не пересматривает это в общем виде —
  пересматривает только частный случай, где роль и кратность объявлены
  явно (`SkillOutput.multiple`).
- **Рантайм-тул `emit_document(title, text)`** — отклонено: тул с
  произвольным заголовком и неограниченным числом вызовов даёт модели
  свободу решать, что персистится и как называется, — это нарушает ADR-0002
  (замороженная декларация решает, что скилл производит, а не рантайм-
  выбор модели). У `script` в sandbox инструментов нет вовсе (ADR-0014),
  так что этот вариант для `script`-скиллов физически недоступен и создал
  бы асимметрию между `kind`.
- **Динамические ключи `chapter_1..chapter_N`** — отклонено: схема тула
  `emit_output` строится из декларации (`emit_output_spec`, `enum` полем
  `key`), а N неизвестно до прогона — значит, схему нельзя построить
  заранее, и декларация конфига перестала бы быть замороженной
  (ADR-0002).

## Consequences

**Плюсы:**
- `split_by_chapters` и подобные скиллы с непредсказуемым числом
  однородных артефактов выразимы через одну декларацию
  (`{key, description, multiple: true}`), без плодения ключей и без
  нарушения замороженности конфига.
- Различие «роль» / «кратность» явное и проверяемое: тип значения по ключу
  фиксирован декларацией и проверяется fail-closed, как остальные формы
  ошибок ADR-0024.
- Primary-коллекция переиспользует существующий код склейки
  (`_value_as_text`) — новой семантики для verify/pipeline не вводится.

**Минусы / риски:**
- Число документов за прогон непредсказуемо до запуска: у скилла с
  `multiple`-выходом одно нажатие «Сохранить» может создать от одного до
  `MAX_COLLECTION_DOCUMENTS` (50) документов разом. Пользователь видит
  результат только после прогона, не может оценить объём заранее.
- Взаимные wiki-links между десятками элементов одной коллекции дали бы
  шумный хвост в каждом файле, если связывать их попарно. Решение: элементы
  коллекции связываются только с primary-документом (или между primary и
  companions, как сегодня через `sibling_stems`), не друг с другом —
  `sibling_stems` для персиста коллекции строится из «все прочие top-level
  результаты прогона» (primary + companions), исключая остальные элементы
  той же коллекции. Это прямой вход для реализации `persist_run_outputs` в
  CATALOG-153.
- Выборочное сохранение (CATALOG-148, «сохранить не всё») становится
  острее: пользователю нужно выбирать не между несколькими ролями (текст /
  таблица), а внутри десятков элементов одной роли — UI для этого решает
  CATALOG-154, не этот ADR.
- Второй лимит (`MAX_COLLECTION_DOCUMENTS`) — ещё одна fail-closed граница,
  которую нужно тестировать отдельно от `MAX_SKILL_OUTPUTS`; их легко
  перепутать при чтении кода, так как оба ограничивают «число выходов», но
  на разных уровнях (ключи декларации vs документы прогона).
