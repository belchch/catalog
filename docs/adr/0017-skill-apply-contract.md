# ADR 0017: Контракт применения скилла — arity, runtime-уточнение, режим вывода

- **Date:** 2026-07-24
- **Status:** Accepted
- **Revises:** ADR-0002 (частично), ADR-0006 (частично), ADR-0010 (снимает «срез на одном входе»)

## Context

ADR-0002 описал «применить скилл» как «запустить агент-луп с этим конфигом
над документом»: один вход, никаких параметров запуска, результат всегда
становится `Document` (ADR-0006). Практика дала три требования, которые в эту
формулировку не помещаются:

1. Скиллы сравнения/сведения принципиально работают на **нескольких входах**
   (ADR-0010 закладывал схему «на вырост», но контракт остался одновходовым).
2. Пользователю нужно **уточнить задание в момент применения** («сравни по
   разделу X»), не размораживая и не переписывая скилл.
3. Результат прогона не всегда стоит класть в библиотеку — часто нужен
   **предпросмотр на экране**, а сохранение — по решению пользователя.

## Decision

Применение скилла имеет собственный контракт из трёх параметров; конфиг
скилла при этом остаётся замороженным.

### 1. `input_arity` — сколько входов ожидает скилл

- Поле `SkillConfig.input_arity: int | None` (`backend/app/skills/config.py`).
  `None` — список произвольной длины (≥ 1); число — ровно столько документов.
- API сужает допустимые значения до **`1`, `2` или `null`**
  (`SkillConfigureRequest`, `SkillMetaPatchRequest`, `SkillTrack` в
  `backend/app/api/schemas.py`) — под слоты в UI; ядро при этом хранит
  произвольное целое, поэтому расширение не потребует миграции.
- Проверка **на двух уровнях**: `POST /skills/{id}/apply` → 422
  (`backend/app/api/runs.py:70`) и `_apply_core` → `ValueError`
  (`backend/app/skills/apply.py:126`). Второй уровень — не дублирование, а
  инвариант ядра: apply вызывается и мимо HTTP-слоя.
- Передача входов исполнителю различается по типу скилла:
  - `agent` — тексты **всех** документов вкладываются в стартовое сообщение
    целиком (плюс `read_document` как fallback);
  - `script` — `document` (склейка через `\n\n---\n\n`) и `documents`
    (`list[str]` по документам).

### 2. `prompt` — runtime-уточнение (только для `kind="agent"`)

`ApplyRequest.prompt` → колонка `skill_run.user_prompt` → добавляется в
стартовое сообщение агента блоком «Уточнение к заданию». Для
`kind="script"` игнорируется: детерминированный скрипт не имеет входа для
свободного текста, и притворяться иначе нельзя. Уточнение **не меняет
конфиг** — оно живёт в строке прогона, поэтому воспроизводимость прогона
восстанавливается из `skill_run`, а скилл остаётся тем же.

### 3. `persist` — режим вывода: «в документ» vs «на экран»

- `persist=true` (дефолт, совместимо с поведением до CATALOG-18): успех →
  `Document(kind="result_md")` + файл в `workspace/results/`.
- `persist=false`: документ не создаётся; сырой текст пишется в
  `skill_run.result_text` и возвращается в UI. Материализация позже —
  `POST /runs/{id}/save` (`backend/app/api/runs.py:122`), идемпотентно
  защищённая: 409 если результат уже сохранён или прогон не завершился `ok`.
- `result_text` пишется **всегда**, независимо от режима, — иначе «сохранить
  позже» было бы невозможно после перезагрузки страницы.

## Consequences

**Плюсы:** один скилл переиспользуется на 1/2/N входах; уточнение задачи не
требует разморозки скилла и не плодит почти одинаковые скиллы; библиотека не
засоряется черновыми прогонами.

**Минусы / риски:** ADR-0006 («результат — полноправный Document») теперь
верен условно — при `persist=false` артефакт существует только как строка
прогона в SQLite, то есть до сохранения он **не** выводим из ФС (натяжение с
инвариантом ADR-0005); runtime-prompt делает два прогона одного скилла
неодинаковыми — при разборе результата всегда надо смотреть `user_prompt`;
ограничение UI на arity ∈ {1, 2, null} придётся расширять руками.

## Alternatives considered

- **Произвольная arity в API (3, 4, …)** — отклонено на текущем UI: слоты
  выбора документов заданы явно; ядро уже готово, ограничение снимается в
  схемах.
- **Уточнение через правку конфига перед прогоном** — отклонено: ломает
  «скилл = замороженный конфиг» (ADR-0002) и делает историю прогонов
  неинтерпретируемой.
- **Всегда сохранять результат** (поведение до CATALOG-18) — отклонено:
  экспериментальные прогоны замусоривают библиотеку и граф ссылок.
- **Хранить preview-результат только в памяти клиента** — отклонено:
  теряется при перезагрузке, нечего материализовать через `/runs/{id}/save`.
