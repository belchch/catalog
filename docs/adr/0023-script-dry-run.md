# ADR 0023: Dry-run script-скилла до заморозки — прогон в той же песочнице

- **Date:** 2026-08-18
- **Status:** Accepted
- **Extends:** ADR-0014, ADR-0015
- **Revises:** ADR-0004 (частично)
- **Related:** CATALOG-138…141

## Context

Script-скилл (`kind="script"`, ADR-0014) не исполняется ни разу до момента
заморозки конфига.

`save_skill_script` вызывает `validate_script` — это только статика: `ast.parse`,
запрет `import`/`from-import`, dunder-атрибутов и опасных builtins. Рантайм-отказы
статика не видит: `KeyError` на разборе markdown-таблицы из docx, `IndexError` на
неожиданной структуре, пустой вывод, результат не того типа, выход за 5-секундный
таймаут.

Первый реальный запуск случается в `apply` после сборки. По ADR-0004 это
намеренно: первый apply на исходном документе — replay-тест. Но для script-скилла
replay-тест выродился в отладку после заморозки: пользователь получает скилл,
который падает, и правит его циклом «разморозить → поправить → заморозить».
Для agent-скилла того же класса проблем нет — там модель в рантайме видит tool
result и выправляет ход сама.

Обратная связь модели при этом обрезана. `run_script` заворачивает любое
исключение в `ScriptRuntimeError(f"script raised: {exc}")`; traceback
выбрасывается. Номера строки нет, поэтому планировщик правит код наугад — часто
меняя не то место.

Отдельная среда отладки при этом не нужна: песочница уже существует
(`script_runner.py` — restricted namespace, whitelist builtins, предзагруженные
`json`/`re`/`math`/`statistics`/`collections`, таймаут через `SIGALRM`). Нужен
доступ к ней до сборки.

## Decision

Прогон черновика скрипта становится частью этапа планирования — тулом
`try_skill_script` в planner-реестре (`build_artifact_tools`, ADR-0015).

1. **Не новый исполнитель.** Dry-run не воспроизводит окружение, а вызывает то
   же, что вызывает `apply`. Из `apply.py` выносится общий хелпер подготовки
   входа и запуска: `extract_text` по документам, склейка одного документа
   verbatim / нескольких через `\n\n---\n\n`, `documents=[...]`,
   `run_script_async` с теми же лимитами. И apply, и dry-run идут через него.
   Копия логики запрещена: разошедшиеся среды делают отладку ложной.

2. **Аргументы — по умолчанию черновик и документы сессии.** `code`
   (опционально; по умолчанию артефакт `script`), `doc_ids` (по умолчанию
   прикреплённые к сессии документы), `step_index` для script-шага pipeline
   (ADR-0018) — там та же болезнь.

3. **Диагностика вместо `str(exc)`.** `ScriptRuntimeError` несёт номер строки и
   строку исходника, собранные из `traceback.extract_tb` по кадрам с filename
   `<script-skill>`. Кадры backend отфильтровываются: внутренние пути наружу не
   отдаются. Тул возвращает `stage` (`validate` / `run` / `verify`), `error` с
   номером строки, `input_preview` (что скрипт видит на входе — извлечённый
   текст, а не исходный файл), `output_preview` + длина + тип (`str` |
   `list[str]`), `duration_ms` и результат прогона `verify_checks` из draft-`meta`.
   `input_preview` и `output_preview` усечены.

4. **Заморозка требует зелёного прогона.** Для `kind="script"` и для
   script-шагов pipeline сборка отдаёт 422, если для `sha256(code)` нет успешного
   dry-run. Результат прогона хранится рядом с артефактом `script` и привязан к
   хешу кода: правка кода обнуляет зелёный статус. Без гейта тул остаётся
   советом, который планировщик пропускает, — а именно это и надо исключить.

5. **Dry-run ничего не сохраняет.** Ни `Document(kind="result_md")`, ни
   `skill_run`, ни trace. Это проверка черновика, не запуск скилла: ADR-0006
   (результаты — документы) к ней не применяется, статистика прогонов не
   загрязняется.

6. **Лимит прогонов на ход.** Счётчик dry-run в бюджете хода (в духе ADR-0021):
   исчерпание возвращает `ok: false` в tool result, не исключение. Таймаут — тот
   же 5с. Как и apply, dry-run исполняется в потоке event-loop (SIGALRM требует
   main thread) и блокирует его на время прогона — известный компромисс ADR-0014
   до перехода на subprocess-исполнитель.

7. **Ручной путь.** HTTP-эндпоинт dry-run для артефакта `script` и кнопка в
   панели черновика: пользователь отлаживает скрипт сам, не через диалог с
   моделью. Порядок вызовов закрепляется в promptе планировщика и в
   `SCRIPT_CODE_CONTRACT_EN`: `save_skill_script` → `try_skill_script` → правка
   до `ok`.

## Consequences

**Плюсы:**
- Рантайм-отказы script-скилла ловятся до заморозки, а не после.
- Модель получает номер строки и фактический вход — правка становится адресной.
- Гейт по хешу кода делает «непроверенный script-скилл» невозможным
  by construction, а не вопросом дисциплины промпта.
- Среда отладки и среда исполнения совпадают по построению — расхождение
  возможно только через сознательное дублирование хелпера.
- Пользователь получает автономный способ отладки скрипта помимо диалога.

**Минусы / риски:**
- Заморозка script-скилла теперь зависит от наличия входных документов: dry-run
  без прикреплённых документов гоняется на пустом входе и зелёный статус в этом
  случае слабее.
- Планирование дольше и дороже: каждый цикл правки — дополнительный tool call.
- Dry-run блокирует event-loop до 5с на прогон; при активной отладке это заметно
  соседним сессиям.
- Хеш кода как ключ зелёного статуса чувствителен к косметике: переформатирование
  без смысловых правок требует повторного прогона.

## Alternatives considered

- **Исполнять прямо внутри `save_skill_script`** — отклонено: save становится
  медленным и с побочным эффектом, и нельзя прогнать вариант кода, не записав его
  в черновик. Гейт по хешу даёт ту же гарантию «не забудет», не смешивая
  сохранение с исполнением.
- **Отдельная среда отладки (subprocess, venv, второй интерпретатор)** —
  отклонено как постановка задачи: песочница уже есть, а вторая реализация
  окружения расходится с рантаймом и делает отладку недостоверной. Переход на
  subprocess-исполнитель (option (b) ADR-0014) остаётся отдельным решением, и
  dry-run получит его бесплатно, потому что вызывает общий хелпер.
- **Только улучшить диагностику в apply, без dry-run** — отклонено: дешевле, но
  отладка остаётся после заморозки, то есть исходная проблема не снимается.
- **Ослабить sandbox, чтобы код падал реже** — отклонено: ограничения ADR-0014
  fail-closed и ловятся статикой при save; причина отказов — данные и контракт
  вывода, а не белые списки.

## Relation to ADR-0004 / ADR-0014 / ADR-0015

ADR-0004 остаётся в силе для agent- и pipeline-скиллов: сборка в момент
согласия, первый apply — replay-тест. Для script-скилла добавляется предшествующая
ступень: без зелёного прогона черновика сборка не проходит, и первый apply
перестаёт быть первым исполнением кода. ADR-0014 не меняется — ни песочница, ни
лимиты, ни контракт входа/выхода; dry-run их переиспользует и добавляет только
номер строки в диагностику отказа. ADR-0015 расширяется: у артефакта `script`
появляется не только статус статической валидации, но и статус прогона,
привязанный к хешу кода.
