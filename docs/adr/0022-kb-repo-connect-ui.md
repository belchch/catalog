# ADR 0022: Подключаемый KB-репозиторий вместо двух app-owned репо

- **Date:** 2026-07-24
- **Status:** Accepted
- **Supersedes:** ADR-0012 п.2 (два app-owned репо), п.4 (внешние репо — только read-source), п.6 (folder-picker = admin/env)
- **Related:** реализует шаг 2 роадмапа ADR-0010; закрывает долг ADR-0012/0018 («commit — только флаг статуса»); уточняет ADR-0005/0006/0016/0017/0019
- **План:** `docs/plan/next-shift/kb-git-rework.md`

## Context

ADR-0012 зафиксировало два app-owned git-репозитория (`documents/`, `skills/`)
под data-root, оба закрытые для пользователя (folder-picker — admin/env, не
UI), а внешние репозитории — только read-source, никогда не мутируемые. На
практике это означало: пользователь не выбирает, где живут его данные;
`results/` вообще не под git; `commit_skill` только флипал статус в SQLite —
ни один git-коммит нигде не делался.

Продукту нужна модель, где пользовательский репозиторий базы знаний — не
внутренняя деталь приложения, а то, что пользователь сам подключает (локальный
путь, опционально remote для бэкапа), и куда каждое подтверждённое действие в
UI (документ, скилл, результат) реально коммитится. Три сценария развёртывания
(on-prem, SaaS, локально) должны работать одинаково — без зависимости от
системного `git`.

## Decision

1. **Один репозиторий, три подпапки.** `documents/` (входные документы),
   `results/` (result_md прогонов), `skills/` (материализованные конфиги
   скиллов) — одно подключение вместо двух отдельных репо. Одна git-история на
   всё содержимое.
2. **Подключение — конечно-пользовательское действие.** `POST /kb/connect`
   принимает локальный путь (+ опциональный remote, push-флаг); `init`/`open`
   идемпотентны. Выбор персистентен (`app_setting.kb_repo_path`) и переживает
   рестарт — при старте лифспан читает его раньше дефолта из `Settings`.
   Отменяет ADR-0012 п.6.
3. **Индекс — сканирование, не upload.** `scan_repo` (`app/documents/scan.py`)
   обходит `documents/`/`results/`, сопоставляет файлы со строками `document`
   по пути: новый файл → новая строка; изменённый → та же строка (id
   стабилен — ADR-0016 держит FK `session_document`/`skill_run`); исчезнувший
   → `reconcile_orphans`. `skills/` сканируется отдельно
   (`app/skills/repo_skill.scan_skills`) и **только добавляет** отсутствующие
   строки, чтобы не затирать несохранённый черновик правки поверх последнего
   коммита. SQLite остаётся пересобираемым индексом (инвариант ADR-0005/0012
   усиливается, не отменяется).
4. **Коммит — явной кнопкой, с двумя гранулярностями.** `POST /kb/commit`
   стейджит всё дерево (`git add -A` эквивалент) и коммитит одним сообщением
   от пользователя — документы и скиллы вместе. `POST /skills/{id}/commit`
   остаётся отдельной точечной операцией: материализует один JSON-файл
   скилла в `skills/` и коммитит только его, не трогая остальные pending
   изменения (сохраняет исторический смысл кнопки «Commit skill» и закрывает
   долг ADR-0018 п.4 — это больше не флаг в SQLite, а реальный git-коммит).
   Push — опционален, включается за коммит; неудачный push не откатывает уже
   сделанный локальный коммит (`PushResult.warning`).
5. **Git-движок остаётся dulwich**, теперь с полным набором транзакций
   (`app/storage/git.py`: `stage_paths`/`stage_all`/`stage_removal`/`status`/
   `commit`/`push`), а не только `ensure_repo`. Фиксированная app-identity
   (`Catalog <catalog@localhost>`) — по-прежнему без host-конфига. Каждая
   операция резолвит путь относительно `repo_root` и отклоняет выход за его
   пределы (`PathEscapesRepoError`) — защита от traversal/симлинков.
6. **Загрузка одиночного файла из UI сохранена как удобство**, не
   единственный путь: `POST /documents` по-прежнему пишет байты в
   `documents/` подключённого репо и сразу индексирует — эквивалент «положить
   файл и сделать Rescan» за один клик. Основной путь для существующих
   репозиториев — положить/отредактировать файлы на диске и нажать Rescan
   (`POST /kb/rescan`).
7. **Внешние корп-репозитории вне скоупа этого ADR** (ADR-0012 п.4 не
   отменяется целиком): подключённый репозиторий — рабочий репозиторий
   пользователя, который приложение осознанно мутирует и коммитит; это не
   «read-source клон авторитетного прод-репо заказчика», о котором говорил
   п.4.

## Consequences

**Плюсы:** пользователь управляет расположением и историей своих данных;
`results/` и `skills/` наконец под git; `commit_skill` даёт настоящий аудит
версий конфига; одна git-история на весь KB упрощает бэкап (один `git clone`/
`push`); модель одинакова для on-prem/SaaS/локального запуска — нет
зависимости от системного `git`.

**Минусы / долг:**
- **Миграция существующих данных не автоматизирована.** Инсталл с уже
  накопленным `workspace/documents` (старый layout ADR-0012) не переносится
  сам — пользователь должен явно подключить старый путь через `POST
  /kb/connect` (или указать его в `APP_KB_REPO`/legacy `APP_WORKSPACE`);
  ничего не удаляется, но и не переезжает само.
- **Credentials для push не реализованы** — push полагается на то, что
  окружение (SSH-агент, `.netrc`, credential helper) уже настроено; нет
  UI/хранилища для токенов/паролей. Приемлемо для локального/on-prem
  использования с уже настроенным доступом; не решение для SaaS-мультиарендности.
- **`skill.status` при `edit` (commited → draft)** не удаляет и не помечает
  файл в `skills/` как устаревший — он просто отстаёт от SQLite до
  следующего commit. Осознанный выбор (простота), не баг.

## Alternatives considered

- **Оставить два репо (`documents/`, `skills/`), добавить только коммиты** —
  отклонено: `results/` всё равно нуждался бы в третьем репо или в
  прикреплении к одному из двух произвольно; одна git-история на весь KB проще
  для бэкапа/аудита, чем координация нескольких.
- **Коммитить на каждое действие автоматически** (без явной кнопки) —
  отклонено: превращает историю в шум (коммит на каждый чекбокс), не даёт
  пользователю сформулировать сообщение; явная кнопка — это то, что описано в
  плане с самого начала.
- **`commit_skill` тоже стейджит всё дерево** (как `POST /kb/commit`) —
  отклонено: ломает исторический смысл отдельной кнопки «Commit skill» —
  пользователь мог держать незакоммиченные правки документов, коммитя только
  готовый скилл.
- **scan_skills перезаписывает существующие строки из файла** — отклонено:
  файл отражает последний **коммит**, а строка в SQLite может содержать
  несохранённый черновик правки; перезапись стёрла бы его молча.

## Открытые вопросы, оставленные вне этого ADR

- Хранилище credentials для push (keyring/env/зашифрованная настройка) —
  нужно решение до SaaS-раскатки с несколькими пользователями/репозиториями.
- Автоматическая миграция старого `workspace/documents` (два репо) в новый
  layout (один репо, три подпапки) — сейчас ручная операция через connect.
