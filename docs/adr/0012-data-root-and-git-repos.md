# ADR 0012: Data-root вне репо исходников + два app-owned git-репозитория

- **Date:** 2026-07-16
- **Status:** Accepted (частично superseded ADR-0016: модель воркспейса = user-folder + `.catalog/index.db`; отказ от dulwich git-репо и единого `catalog.db` как модели пользовательского воркспейса)
- **Supersedes:** частично ADR-0005 (реализует отложенный там git)
- **Superseded by:** частично ADR-0016

## Context

Два накопленных решения сошлись в одной задаче.

1. **Архитектурный баг.** `APP_WORKSPACE` и `APP_DB_PATH` (`app/config.py:13-14`) — **относительные пути**, резолвящиеся от CWD процесса. Данные приложения (`workspace/documents`, `workspace/results`, `catalog.db`, `prompt_logs`) физически лежат в дереве исходников. Пусть они и gitignored (`.gitignore:15`), модель порочна: проект непортативен, пути плывут от CWD, несколько инсталлов мешают друг другу.

2. **Git, отложенный в ADR-0005 / шаге 2 после среза (ADR-0010), теперь нужен.** Две независимые потребности:
   - **git для скиллов** — вынести конфиги из SQLite в ФС+git (review, аудит версий);
   - **git для документов** — версионирование: приходят новые версии документов, diff скармливается скиллу (напр. «summary по диффу»), существующие скиллы переприменяются на всех последующих версиях.

Доп. ограничение: продукт планируется **self-hosted в корп-среде**, поэтому приложение **не может владеть авторитетными репозиториями заказчика** и не может предполагать наличие настроенного `git` на хосте.

## Decision (минимальный дефолт)

Зафиксированы решения по умолчанию, чтобы прекратить обсуждение и начать реализацию:

1. **Data root — абсолютный путь вне дерева исходников.** Один корень для всех данных. Источник: env `APP_DATA_DIR`; дефолт — OS-каталог данных (`~/.local/share/catalog` на Linux, `~/Library/Application Support/catalog` на macOS). Под ним: `documents/`, `skills/`, `catalog.db`, `prompt_logs/`. Резолв один раз при старте в `get_settings()`. Это лечит баг п.1.

2. **Два app-owned git-репозитория** внутри data-root: `documents/` и `skills/`. Оба инициализируются самим приложением (`git init`). Разные жизненные циклы и аудитория — потому два, а не один.

3. **Git-движок — dulwich** (чистый Python). Ноль host-зависимостей и детерминированный identity — критично для self-hosted, где нельзя рассчитывать на системный `git` с настроенным `user.name/email`.

4. **Приложение владеет своими внутренними репозиториями** (клон/зеркало импортированного + сгенерированный контент). **Внешние корп-репозитории** — только read-source (clone/pull), **никогда не мутируются и не push-ятся**. В минимальном варианте внешних репо ещё нет — только два внутренних.

5. **Версия документа операется на git**, а не на колонки в SQLite: документ = путь; версия = коммит, трогающий путь; diff = `git diff`. **SQLite остаётся пересобираемым индексом** над git (держит инвариант ADR-0005).

6. **Folder-picker = admin/env-настройка** data-root при установке, **не** end-user UI.

## Consequences

**Плюсы:** баг «мутации репо исходников» устранён; фундамент для diff/reuse-on-new-version заложен без переизобретения версионирования; install чистый и портативный; git не зависит от хоста.

**Минусы / долг:** `commit_skill` (`api/skills.py:218`) пока флипает только статус в SQLite — миграция навыков в ФС+git и реальный git-коммит откладываются; модели «версии документа» и pipeline «reapply на новой версии» — отдельные шаги после этого ADR; dulwich — меньший фичсет, чем CLI.

## Alternatives considered (муки творчества)

- **In-place работа на checkout заказчика** vs **внутренний клон/зеркало**. In-place отклонён: мутация прод-репо, write-доступ к прод, связка с layout/identity/remote. Выбран внутренний клон — app владеет копией, не оригиналом; это не противоречит self-hosted.
- **Один общий репо** vs **два (`skills/` + `documents/`)**. Один отклонён: разные жизненные циклы, размеры, паттерны доступа.
- **Системный `git` (subprocess)** vs **dulwich**. Subprocess отклонён как дефолт для self-hosted: зависимость от установленного и сконфигурированного `git` на хосте заказчика. Допустим, если команда готова зафиксировать это требование.
- **Колонки version/parent в SQLite** vs **git-native версионирование**. SQL-колонки отклонены: дублирует git и ломает инвариант «DB выводима из ФС».
- **App-owned репо вообще** vs **«app не может владеть»**. Уточнено: не может владеть **авторитетными** репо заказчика, но **может** владеть внутренними рабочими.

## Open / будущие шаги

- Ингест внешних корп-репо (clone/pull) как read-source.
- Миграция скиллов из SQLite в `skills/`-репо + реальный git-коммит в `commit_skill`.
- Модель версии документа + diff-tool + pipeline «reapply на новой версии».
- Опциональный configured remote для бэкапа внутренних репо (off by default).
