# ADR 0022: Шаг pipeline типа skill — замороженный скилл как шаг

- **Date:** 2026-08-16
- **Status:** Accepted
- **Extends:** ADR-0002, ADR-0018, ADR-0019, ADR-0021
- **Related:** CATALOG-134…137

## Context

Композиция скиллов уже есть в сессии (ADR-0019): прикреплённый скилл
становится тулом, вложенный `apply` создаёт `skill_run` с
`parent_run_id`, `persist=False`, вход — текст, выход — `result_text`.
При сборке pipeline эта композиция пропадает.

`PIPELINE_STEP_TYPES` — только `script` и `llm`. Сборка
(`_build_skill_from_artifacts`) заливает в пустые шаги артефакты
`prompt` / `script`; чужой скилл в шаг не попадает. `allowed_tools`
шага сверяется с базовым реестром; top-level run оставляет только
документные тулы (fail-closed). Живой `skill_*` в конфиге шага
противоречил бы ADR-0002: собранный конфиг должен быть самодостаточен.

Класс задач «разбить → прогнать готовый скилл → собрать» сейчас
закрывается копипастом чужого промпта/скрипта в шаг или вызовом из
сессии, который не переживает сборку.

## Decision

Третий тип шага pipeline — `skill`, рядом с `script` и `llm`.

1. **Ссылка только в черновике.** В артефакте `steps` шаг несёт
   `skill_id`. Сборка резолвит его в полный снапшот конфига вызванного
   скилла и пишет рядом provenance: `skill_id`, `skill_name`,
   `config_hash` (SHA-256 префикс `config_json` через
   `SkillConfig.to_json()`, как ADR-0019 п.5). Собранный конфиг
   самодостаточен (ADR-0002): рантайм не ходит в таблицу `skill` по
   ссылке.

2. **Не живая ссылка.** Версионной таблицы у скилла нет. Пин по
   `updated_at` уже отклонён ADR-0019 п.5. Источник после сборки можно
   менять — уже собранный pipeline не следует за ним. Чтобы подтянуть
   новую версию, pipeline пересобирают.

3. **Рантайм — вложенный apply.** Шаг создаёт `skill_run` с
   `parent_run_id` родителя и `persist=False`. Вход — значение шага
   (строка либо список строк, ADR-0018) как `input_texts`. Выход шага —
   `result_text` вложенного запуска. Механика та же, что у
   session-тула (`skill_tools.py`, вложенный `apply_skill_collect`).
   Снапшот исполняется как есть; `skill_id` в собранном шаге —
   provenance, не резолв.

4. **Verify вложенного — постусловие шага.** `verify_checks`
   вызванного скилла гоняются внутри вложенного apply. Провал
   останавливает пайплайн: оркестрация детерминирована конфигом, модели,
   которая могла бы прочитать `ok: false` и продолжить, нет. Это
   отличается от session-тула (ADR-0021 п.7), где отказ остаётся в
   tool result. Финальный verify самого pipeline (ADR-0018) не
   меняется. Retry пайплайна по-прежнему нет.

5. **Потолок и бюджет — ADR-0021.** Вложенный шаг увеличивает
   `depth`; при `depth >= max_skill_depth` шаг не стартует. Резерв
   хода — оценка снапшота и 1 запуск. `estimate_skill_llm_calls` для
   `skill`-шага рекурсивен: оценка снапшота, а не
   `max_iterations` как у `llm`. Дедлайн хода проверяется до старта
   шага. Исчерпание бюджета или дедлайна останавливает пайплайн
   (нет модели на уровне оркестрации).

6. **Цикл невозможен by construction.** Снапшот развёрнут и наружу
   не ссылается. Вложенный pipeline, у которого на момент его сборки
   уже были `skill`-шаги, несёт свои снапшоты внутри. Живого резолва
   `skill_id` в рантайме нет — `A → B → A` через таблицу скиллов
   не собирается.

Сборка резолвит только committed-скилл известных `kind`
(`script` / `agent` / `pipeline`). Черновик и неизвестный id — ошибка
сборки, не рантайма. Схема шага и рантайм — CATALOG-135 / CATALOG-136;
UI — CATALOG-137.

## Consequences

**Плюсы:**
- Композиция переживает сборку: pipeline вызывает замороженный скилл
  без копипаста и без живого тула в `allowed_tools`.
- Собранный конфиг остаётся самодостаточным и воспроизводимым
  (ADR-0002).
- Вложенный apply, verify, `parent_run_id` и бюджет переиспользуются,
  а не дублируются.
- Цикл по живым ссылкам исключён конструкцией снапшота.

**Минусы / риски:**
- Снапшот не обновляется вслед за источником. Правка вызванного
  скилла не меняет уже собранные pipeline; расхождение видно только
  по `config_hash` / `skill_name`, пока pipeline не пересоберут.
- Стоимость и глубина складываются: широкий pipeline из нескольких
  `skill`-шагов режет бюджет хода вширь (ADR-0021).
- Провал вложенного verify глушит весь пайплайн без шанса обойти
  шаг — это намеренно, но жёстче, чем отказ session-тула.

## Alternatives considered

- **Живая ссылка + версионная таблица** — отложено: у скилла нет
  версий; пин по `updated_at` уже отклонён (ADR-0019 п.5). Живой
  резолв в рантайме ломает самодостаточность собранного конфига
  (ADR-0002) и открывает циклы `A → B → A`.
- **`skill_*` в `allowed_tools` шага** — отклонено: ломает
  воспроизводимость. Реестр session-тулов эфемерен (прикрепление к
  сессии), а `allowed_tools` сверяется с базовым реестром и на
  top-level run фильтруется до документных тул. Оркестрацию снова
  выбирала бы модель, а не замороженный порядок шагов (ADR-0018).
- **Копипаст чужого скилла руками** — отклонено как целевое решение:
  это текущий обходной путь (продублировать prompt/script в шаг).
  Нет provenance, расходится с источником молча, сборка по-прежнему
  не знает о чужом скилле.

## Relation to ADR-0002 / ADR-0018 / ADR-0019 / ADR-0021

ADR-0002 остаётся в силе: собранный шаг несёт снапшот, не дырку под
живой id. ADR-0018 остаётся в силе для контракта значения, финального
verify и детерминированной оркестрации; тип шага расширяется с двух
до трёх. ADR-0019 — источник механики вложенного apply; этот ADR
переносит её из сессии в замороженный шаг. ADR-0021 задаёт потолок,
бюджет и дедлайн; для `skill`-шага оценка LLM-вызовов становится
рекурсивной, а отказ на оркестрации останавливает пайплайн, а не
возвращается модели.
