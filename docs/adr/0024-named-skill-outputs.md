# ADR 0024: Именованные выходы скилла — primary + companions

- **Date:** 2026-08-20
- **Status:** Accepted
- **Extends:** ADR-0006, ADR-0014, ADR-0018
- **Does not change:** ADR-0019, ADR-0022
- **Related:** CATALOG-143…147

## Context

Один прогон скилла даёт один выход: один `result_text`, один
`output_doc_id`, один файл `result_md`. Хвост персиста пишет ровно один
`Document`; `POST /runs/{id}/save` материализует ровно один текст.
Входы уже множественные (`input_doc_ids`), выходы — нет.

Контракт значения pipeline несёт `str | list[str]` (ADR-0018), но
склейка списка через `---` — заготовка под будущий `map`, а не под N
документов: позиция в списке не несёт роли. Пример — псевдонимизация:
псевдонимизированный текст и таблица перекодировки. Это два документа с
разными ролями, а не «глава 1 / глава 2».

Нужен общий контракт именованных выходов для всех трёх `kind`
(`agent` / `script` / `pipeline`), не ломая пустой конфиг и не трогая
вложенный apply.

## Decision

Скилл объявляет именованные выходы в замороженном конфиге. Контракт
один для всех трёх `kind`; способ рождения набора зависит от типа.

1. **Декларация.** `SkillConfig.outputs` — список `{key, description}`,
   общий для `agent`, `script` и `pipeline`. Прецедент по форме —
   `input_arity`: поле в конфиге задаёт ожидание, отсутствие поля не
   ломает старые записи. Пустой `outputs` (или ключ отсутствует в
   `config_json`) = сегодняшнее поведение: один безымянный выход.
   Миграции старых конфигов нет; `to_json` / `from_json` дефолтят
   отсутствующий ключ, как уже делают для `kind` и `input_arity`.

2. **Primary = `outputs[0]`.** Порядок заморожен вместе со скиллом
   (ADR-0002). Primary идёт в `result_text`, в verify, в значение
   следующего шага pipeline и в ответ skill-as-tool. `output_doc_id`
   указывает на него. Схема `skill_run` не расширяется под набор:
   колонки `output_doc_id` и `result_text` остаются про primary.

3. **Companions** — остальные ключи декларации. Каждый персистится как
   отдельный `Document(kind="result_md")` в `results/`. Новый
   `result_*` kind не вводится: ADR-0006 уже допускает несколько
   документов-результатов; меняется только то, что top-level прогон
   может зарегистрировать больше одного.

4. **Граница финала.** Набор именованных значений рождается только на
   финале top-level прогона — либо у скилла без шагов, либо на
   последнем шаге pipeline. Между шагами контракт значения остаётся
   `str | list[str]` (ADR-0018). `dict` в середине цепочки — ошибка
   прогона, fail-closed. `list[str]` — одно значение (заготовка под
   `map`), не N документов и не набор именованных выходов.

5. **Рождение набора зависит от `kind`, контракт один.**
   - `script` — sandbox возвращает `dict[str, str]` с ключами из
     декларации.
   - `pipeline` — финальный шаг производит набор по своему типу
     (`script` → dict, `llm` / `agent` → `emit_output`).
   - `agent` — тул `emit_output(key, text)`. Разбор финальной простыни
     по разделителям отклонён: ключ должен быть явным вызовом, а не
     эвристикой над текстом.

6. **Неполный набор.** У `agent` — через существующий retry
   (ADR-0007): прогон не принят, список недостающих ключей уходит
   обратно в луп. У `script` — сразу ошибка прогона: sandbox
   детерминирован, повторять нечего.

7. **Вложенный apply не меняется.** ADR-0019 и ADR-0022 остаются в
   силе: `persist=False`, companions не становятся документами и не
   становятся значением шага. Значение шага и `result_text` — primary.
   В ответ session-тула допустимо поле `outputs` рядом с `text`, чтобы
   модель видела companions, не материализуя их в workspace.

8. **Verify на primary.** ADR-0007 не трогаем: реестр проверок по-
   прежнему видит один текст. Адресация verify на конкретный
   companion отложена.

9. **Fail-closed по форме.** Лимит декларации — 8 выходов. Ключ —
   `^[a-z][a-z0-9_]{0,31}$`. Пустое значение, незнакомый ключ,
   пропущенный ключ, превышение лимита — ошибка прогона. Неизвестный
   ключ не записывается «на всякий случай».

10. **Где живут описания.** Для `script` описание — артефакт сборки:
    в рантайме сверяются только ключи. Для `agent` и llm-шага
    описания попадают ещё в промпт и в схему тула `emit_output`,
    чтобы модель знала, что эмитить.

## Consequences

**Плюсы:**
- Один прогон может дать несколько документов с разными ролями, не
  плодя отдельные скиллы и не склеивая роли через `---`.
- Контракт общий для `agent` / `script` / `pipeline`; пустой `outputs`
  сохраняет текущее поведение без миграции.
- Primary остаётся единственным значением шага и единственной целью
  verify — ADR-0018 и ADR-0007 не ломаются.
- Вложенный apply (ADR-0019 / ADR-0022) не обрастает документами.

**Минусы / риски:**
- Companions вложенного вызова не всплывают: они не документы и не
  значение шага. Следующий шаг pipeline и родительский прогон видят
  только primary; чтобы поднять companion наружу, его нужно явно
  сделать primary вызванного скилла или переиздать на финале.
- У `agent` многовыходной прогон дороже по итерациям: каждый
  `emit_output` — tool call, неполный набор уходит в retry и может
  упереться в `max_iterations`.
- `output_doc_id` указывает только на primary; companions ищутся
  соседними `Document(kind="result_md")` того же прогона, отдельной
  колонки под набор нет.

## Alternatives considered

- **Persist `list[str]` как N документов** — отклонено: позиция в
  списке не несёт роли; это заготовка ADR-0018 под `map`, а не под
  именованные выходы. Псевдонимизированный текст и таблица
  перекодировки перепутались бы с «глава 1 / глава 2».
- **Скилл сам пишет файлы тулом** — отклонено: ломает единый хвост
  персиста (ADR-0006) и воспроизводимость замороженного конфига.
  Куда писать и под каким именем выбирал бы рантайм модели, а не
  декларация.
- **Конвенция ключей без декларации** (`result`, `table`, …) —
  отклонено: без списка в конфиге нельзя отличить опечатку от
  нового выхода, нельзя fail-closed сверить полноту, некуда повесить
  описание для промпта.
- **Разбор ответа модели по разделителям** — отклонено: эвристика
  над простынёй хрупкая, ключ должен быть явным (`emit_output` или
  `dict` из sandbox), а не парсингом текста.
- **Требование JSON в финальном сообщении** — отклонено: смешивает
  пользовательский текст primary с конвертом; ломает verify на
  «одном тексте» (ADR-0007) и текущий контракт `result_text`.

## Relation to ADR-0006 / ADR-0014 / ADR-0018 / ADR-0007 / ADR-0019 / ADR-0022

ADR-0006 остаётся в силе и усиливается: результат — по-прежнему
`Document(kind="result_md")`, только top-level прогон может
зарегистрировать несколько таких документов. Новый `result_*` kind
не вводится.

ADR-0014 остаётся в силе для песочницы, лимитов и отсутствия LLM в
рантайме script. Меняется только допустимый тип возврата: кроме
`str` / `list[str]` sandbox может вернуть `dict[str, str]` на финале,
если в конфиге объявлен `outputs`.

ADR-0018 остаётся в силе для контракта между шагами (`str | list[str]`)
и для verify только на финале. Именованный набор — свойство финала
top-level прогона, не промежуточного значения.

ADR-0007 не меняется: verify видит primary. Адресация проверки на
companion — отдельное решение.

ADR-0019 и ADR-0022 **не меняются**: вложенный apply по-прежнему
`persist=False`; companions не документы и не значение шага. Поле
`outputs` в ответе session-тула — необязательное расширение payload,
не смена модели персиста.
