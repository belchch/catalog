# ADR 0014: Детерминированные script-скилы (kind=script)

- **Date:** 2026-07-16
- **Status:** Accepted
- **Revises:** ADR-0002 (частично), ADR-0003 (частично)

> **Note on numbering:** План CATALOG-3 предусматривал файл `0013-script-skills.md`,
> но номер 0013 уже занят ADR-0013 (multi-provider-and-zai). Эта запись
> использует следующий свободный номер — **0014**.

## Context

ADR-0002 («Скилл = замороженный конфиг агента») и ADR-0003 («Code — слой
инструментов») **явно отклонили** генерацию `.py` под каждый скилл по двум
причинам:

1. **Безопасность** — исполнение произвольного сгенерированного кода без
   sandbox недопустимо.
2. **Недетерминизм кодогенерации** — LLM-сгенерированный код непредсказуем и
   не воспроизводим.

Однако на практике многие задачи скилов **полностью детерминированы**
(форматирование, подсчёт, регулярные преобразования, парсинг, сортировка) и
не требуют ни агент-лупа, ни вызова LLM в рантайме. Гонять для них
function-calling цикл — это лишние токены, задержка и недетерминизм там, где
его можно избежать.

CATALOG-3 вводит второй тип скила — `kind="script"` — который пересматривает
запрет ADR-0002/0003 **только в части детерминированных скриптов**.

## Decision

У скила появляется поле `kind` (`"agent"` | `"script"`, дефолт `"agent"` для
обратной совместимости):

- **`agent`** — текущее поведение (ADR-0002): замороженный конф агента,
  function-calling loop + LLM. `allowed_tools`, `model`, `system_prompt`
  определяют запуск.
- **`script`** — **детерминированный** исполнитель: чистый Python-код в поле
  `code`, выполняемый sandbox-runner'ом. **Нет агент-лупа, нет LLM-вызова в
  рантайме** — одинаковый вход всегда даёт одинаковый выход.
  `allowed_tools=[]`, `model` не важен.

### Выбор типа при создании

При `build_skill` модель **сначала оценивает детерминизм** задачи:

- Если задача сводится к чистой обработке текста/данных → `kind="script"` +
  генерирует валидный Python-код.
- Если нужны суждения/рассуждения → `kind="agent"` + заполняет
  `non_determinism_reason` объяснением.

### Sandbox-модель (option (a) из плана)

`backend/app/skills/script_runner.py` — process-local sandbox с защитой в
глубину (defence in depth):

1. **Статическая AST-валидация** (build-time, fail-closed): `ast.parse` +
   запрет `import`/`from-import`, dunder-атрибутов (`__builtins__`,
   `__subclasses__`, …) и опасных builtins (`eval`/`exec`/`compile`/`open`/
   `breakpoint`/`globals`/…). Динамические помощники атрибутов
   (`getattr`/`hasattr`/`setattr`/`delattr`) также запрещены: они принимают имя
   атрибута строкой и потому невидимы для dunder-гарда AST (классический побег
   `getattr(object, "__subclasses__")()`).
2. **Ограниченный namespace** (runtime): белый список builtins + кураторский
   набор безопасных stdlib-модулей (`json`, `re`, `math`, `statistics`,
   `collections`), предварительно разрешённых в namespace (без import-machinery).
3. **Таймаут** (`SIGALRM`/`setitimer`, дефолт 5с).
4. **Ограничение памяти** — **отложено**. In-process `RLIMIT_AS` применялся бы
   ко всему процессу-хосту (`run_script` выполняется в потоке event-loop) и
   может вызвать ложный `MemoryError` в постороннем коде / уронить хост. Memory
   isolation перенесена в subprocess-исполнитель (future work); пока беглый
   скрипт ограничен wall-clock таймаутом.

Скрипт получает входной текст в переменной `document` (alias `input_text`) и
возвращает результат через `return` из `main()`, через глобальную `result`
или через `print`.

### Contract персистенции не меняется

Результат script-скила сохраняется тем же путём, что и agent-скила:
`Document(kind="result_md")` + файл в `workspace/results/` + запись в
`skill_run` со статусом и trace. В trace для script-скила добавляется запись
`kind="script"`.

## Consequences

**Плюсы:**
- Детерминированные задачи решаются без LLM — ноль токенов, ноль задержки,
  полная воспроизводимость.
- Тип `kind` — единственный источник тегов `python`/`ai` для UI (CATALOG-8).
- Contract персистенции единый для обоих типов.

**Минусы / риски:**
- Process-local sandbox (option (a)) проще, но не даёт полной изоляции ОС-уровня.
  Усиление до subprocess + seccomp (option (b)) — future work.
- Белый список модулей требует расширения по мере роста потребностей.

## Alternatives considered

- **Subprocess + seccomp (option (b))** — надёжнее, но сложнее и тяжелее для
  MVP. Отложено как future work; текущая defence-in-depth (AST + restricted
  globals + timeout) достаточна для первого среза, а memory cap намеренно
  отсутствует in-process (см. выше) и войдёт вместе с subprocess-изоляцией.
- **Прокси-исполнитель (option (c))** — скрипт = зарегистрированная
  builtin-функция. Отклонено: слишком негибко, не покрывает пользовательские
  сценарии.
- **Тотальный запрет кода (как в ADR-0002/0003)** — отклонено: заказчик требует
  код как базовую фичу; детерминированный script-путь удовлетворяет это без
  рисков произвольной кодогенерации в рантайме.

## Relation to ADR-0002 / ADR-0003

ADR-0002 остаётся в силе для `kind="agent"`. ADR-0003 остаётся в силе
(инструменты — слой для agent-скилов). Этот ADR **дополняет**, а не заменяет
их: вводит новый тип скила с собственной детерминированной моделью исполнения.
